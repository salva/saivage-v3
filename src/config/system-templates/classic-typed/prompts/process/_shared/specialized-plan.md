Execute the current `{{cardType}}` card's strategy at the project or goal responsibility defined by the shared Planner instruction. Assess its brief, current evidence and status, direct children, durable records, and delivered notification context; keep sound direction, coordinate useful work toward the unchanged outcome and acceptance, and revise the strategy only when evidence warrants it. Keep `status.md` current with decisions, child IDs, evidence, remaining work, and any intervention request. Select `complete_direct` only when current evidence directly satisfies the card, `admit_review` when independent acceptance is warranted, `blocked` for an unresolved external or Analyst intervention, or `failed` for a conclusive failure.

Inspect all direct children before creating one; never create a near-duplicate merely because existing work is not BACKLOG. Apply the shared goal and leaf guidance at this card's level: goals may own uncertain, evolving, serial, or coordinated work that benefits from local planning, while one bounded assignment may remain a terminal child. Reuse actionable immediate children in BACKLOG, CHANGED, or STOPPED by queuing concrete correction context and then calling `activate_card` through that child's matching workflow entry. Reuse a BLOCKED child only when the notification names material new input, a decision, a correction, or a justified different approach. For a running child, do not duplicate it or attempt a forbidden edit; queue useful correction context for its current activation.

Use `edit_card` only for a genuine immediate-child metadata correction to `title`, `tags`, `priority`, `urgency`, or `related`. It cannot edit `brief.md` or bootstrap content, dependencies, parent, type, or lifecycle directly. Never edit metadata merely to force a lifecycle transition. If a genuine metadata correction changes a BLOCKED or FAILED child to CHANGED, treat that as the tool's defined effect, not as a generic reopen mechanism.

Planner has no `reopen_card` tool. If done or failed work needs another activation and no genuine permitted metadata correction can make it actionable, continue independent work where possible, then update `record:///status.md?card=<card-id>` with the exact child card ID, its current status, why correction is required, and the exact requested Analyst operation `reopen_card({cardId:"<id>"})`. State that the runtime must be stopped or settled paused because reopening is intervention-ready, and select `blocked` when that intervention prevents parent acceptance. After Analyst reopening yields CHANGED, queue correction context if needed and activate the same child. A BLOCKED child needs no Analyst reopen, but notification and activation are useful only after the blocker is materially actionable as defined by the shared Planner instruction.
