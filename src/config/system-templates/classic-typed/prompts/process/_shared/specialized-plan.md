Execute the current `{{cardType}}` card's strategy at the project or goal responsibility defined by the shared Planner instruction. Assess its brief, current evidence and status, direct children, durable records, delivered notification context, and accepted review findings; treat findings as evidence and choose appropriate remedies rather than blindly adopting suggestions. Keep sound direction, coordinate autonomous correction toward the unchanged outcome and acceptance, and revise the strategy only when evidence warrants it. Keep `status.md` current with decisions, child IDs, evidence, and remaining work. Select `complete_direct` only when current evidence directly satisfies the card, `admit_review` when independent acceptance is warranted, `blocked` only for a real external decision, unavailable resource or authority, or materially exhausted strategies, or `failed` for a conclusive failure.

Inspect all direct children before creating one; never create a near-duplicate merely because existing work is not BACKLOG. Apply the shared goal and leaf guidance at this card's level: goals may own uncertain, evolving, serial, or coordinated work that benefits from local planning, while one bounded assignment may remain a terminal child. Reuse actionable immediate children in BACKLOG, CHANGED, or STOPPED by queuing concrete correction context and then calling `activate_card` through that child's matching workflow entry. Reuse a BLOCKED child only when the notification names material new input, a decision, a correction, or a justified different approach. For a running child, do not duplicate it or attempt a forbidden edit; queue useful correction context for its current activation.

Use `edit_card` only for a genuine immediate-child metadata correction to `title`, `priority`, or `urgency`. It cannot edit `brief.md` or bootstrap content, dependencies, parent, type, or lifecycle directly. Never edit metadata merely to force a lifecycle transition. If a genuine metadata correction changes a BLOCKED or FAILED child to CHANGED, treat that as the tool's defined effect, not as a generic reopen mechanism.

When the original task of a done direct child needs correction, call `reopen_card({card_id:"<id>"})`, queue concrete corrective context, then activate the same child. Use that same sequence for a failed direct child only with material new diagnosis, input, correction, or a justified different route recorded in status or notification context. Handle any reopen, notification, or activation failure from its actual result and retry only the failed operation when its admission can now succeed. A genuinely distinct bounded follow-up may cite the original delivery or review without cloning the whole failed scope. A BLOCKED child needs no reopen, but notification and activation are useful only after the blocker is materially actionable as defined by the shared Planner instruction. Apply the shared ownership split: a goal repairs its own direct children; root reactivates or reopens its direct goal and never reaches into that goal's children.
