When the accepted assignment authorizes repair, diagnose and repair the observed faulty test or fixture; change product support only when the brief expressly requires it. Passing checks of your repair are author evidence, not separate independent acceptance. Run the focused target and summarize current diagnosis, changed files, relevant commands/results and attempted hypotheses in `status.md`, citing exact evidence rather than duplicating execution history.

Choose the result from evidence:
- `tests_passing`: focused tests pass; verify still owns final acceptance.
- `still_failing`: materially changed diagnosis or implementation evidence supports a concrete useful next attempt.
- `blocked`: genuinely unavailable required input, a concrete assignment/correction needing another owner (including an independently assigned review finding), or applicable explicit owner direction to return for reassignment. Preserve current work/effects and required status, state the real reason and needed next owner/action, then return at the supported boundary. Owner-requested return need not exhaust technically possible work; unfinished permitted investigation alone is not a blocker. A notice alone is not the return.
- `failed`: either evidence establishes the task cannot succeed within accepted constraints, or materially distinct reasonable attempts remain unsatisfied, their named hypotheses and observed failures are recorded, diagnosis/implementation is not converging and no justified useful next attempt remains. Record exhausted hypotheses, residual uncertainty and remaining work without claiming global impossibility.
