# Operator UI Specification

Conversation views are segment-backed. They render only the current indexed segment; compacted context is separate structured metadata, and immutable older segments are not concatenated into the current transcript.

The Dashboard projects the supervisor's coherent one-owner-map snapshot. `starting` already has prepared root ownership and current root. An admitted child becomes current only after successful running publication, while its exact planner LLM remains waiting until relationship release. Outcome-unknown publication exits before a runtime halt or status projection and never becomes a failed planner tool result. Ordinary Stop and actor-main containment retain `closing -> stopped|error`; **Stop project** is disabled in `closing` and enabled in `error`, where it joins the retained failed halt without retrying cleanup. Natural root completion may atomically win while Pause is pending or settled; the first stopped projection has null runtime/current card, no owners, a closed clean gate, and no later paused projection.

Card detail consumes status only from `card.lifecycle.status`; hierarchy summaries expose their displayed `status` directly. Detail has one `allowedActions` array and no top-level status/parent/depth, summary lifecycle-status duplicate, or action count. Tree depth and display path derive only from represented committed hierarchy slices. Files exposes semantic current or explicit-version `card.json[?v=N]` documents through `CanonicalCardFilesReadModel`; physical stream paths, physical stream bytes, and their metadata are never exposed.

Tombstoned cards are absent from active card/detail/tree, record, and inspection projections. Exact history/version/diff resources, direct Files `card.json[?v=N]`, and an already known exact retained card-scoped conversation remain readable for a committed tombstoned final target. Unknown or unlinked targets and descendants behind a tombstoned ancestor are not found. Active session inventories still omit tombstones. The UI has no deleted-card state, tombstone inventory, retained-evidence browser, restore action, or forensic view.

Cards expose immutable hierarchical Stable IDs whose segments come from each parent's local spreadsheet sequence, plus mutable display-path labels derived in the client from active indices in represented committed parent order. Consumed namespace segments do not give UI membership or order: each successful `GET /api/cards/:id/children` response owns one immutable `{ parent, children }` hierarchy slice for that stable parent ID, and its ordered active child summaries are the sole render authority for those edges. Every parent and child summary carries required `permitted_child_types` projected from that type's compiled workflow; this policy can rule out child discovery but is not a raw child ID or a fact that any child or descendant exists. Selected detail is a separate object populated only by `GET /api/cards/:id`; neither detail nor hierarchy completion updates the other authority. Incomplete, unlinked, and retained tombstoned namespaces produce no inferred row, warning, repair, or compatibility state.

Application bootstrap is the sole initial root owner and requests only `project/children`; Cards view mount does not issue a second request. Expanding an idle node requests only that node, collapse requests nothing, and ordinary re-expansion consumes its accepted slice. Same-parent initial callers share one exact keyed request-owner promise. A newer exact refresh aborts and replaces that owner; success, failure, finalization, and owner removal update state only while the exact object remains current. Reset aborts and clears all hierarchy, detail, record, history, entry, and diff owners before clearing accepted state, so old completions cannot alter reset or later state. Different exact scopes remain independent.

On a cold deep route, Cards loads root and each required ancestor-parent slice in order, and proceeds only across membership represented by an accepted non-stale containing slice. If a stale or refresh-failed slice blocks the next edge, reveal stops without requesting the descendant, inferring membership, or retrying. A successful replacement of a required ancestor invokes one continuation of the existing reveal action; it can follow multiple newly represented levels, requests only the next idle ancestor slices, shares already in-flight exact owners, and remains bounded by the [exact card identity contract](system-specification.md#exact-card-identity-contract). Apart from accepting those deeper valid IDs, route reveal behavior is unchanged. An irrelevant sibling replacement does nothing, and failed-stale membership cannot continue until explicit Retry succeeds. Current detail may still return 200 and remain visible while no selected tree row or Path can be rendered. A current-owner detail 404 instead retains only route identity plus typed terminal not-found, aborts and clears detail, records, history, selected entry, and diff, and neither retries nor certifies or clears hierarchy. Rapid route changes use separate action-local monotonic ownership: a superseded reveal stops after each await and before issuing any later ancestor request, but it never aborts shared children work or changes request/slice authority. Root and current-invalid Cards routes clear selected-card ownership and supersede reveal while retaining hierarchy. Route-owned selection, represented ancestor reveal, expand/collapse, independent loading/errors/scrolling, direct navigation, Back behavior, and Files API/VFS/client shapes remain; Files applies the canonical-card virtual projection specified below.

Reorder exact-reads one parent and each membership child once. A real active reorder preserves `child_membership` and appends one complete parent version with the requested active IDs first and all retained tombstones afterward in prior carrier-relative order; its `changed` value counts only mismatched active ordinals. It writes no child stream and changes no ID, namespace, parent relationship, or session. An active-order no-op appends nothing and causes no Analyst change propagation, status mutation, or notification; an Analyst real reorder propagates once, while Planner never propagates either outcome. `delete_card(ids)` is one all-request subtree-union operation: duplicate and overlapping roots occur once, every request/permission/dependency constraint is preflighted before mutation, and successful results follow deterministic dependent-before-dependency and child-before-parent tombstone order. Preflight has no partial success; only an append I/O failure can leave a valid committed prefix, with no event or hint for the uncertain append. Agent inventory derives only exact configured workflow-agent streams from active cards plus the selected global Analyst session (`agent:analyst:global` by default).

Card type is selected through card creation and is read-only thereafter. Type DTOs accept every valid configured identifier. The nine shipped default names retain their current friendly labels; every custom name, including `global`, renders as its exact raw configured value. Cards has no type editor, display-label configuration, prompt-authoring affordance, action, warning, normalization, or compatibility rendering.

Analyst UI operations accept no session argument; server contracts use the selected global-agent session (`agent:analyst:global` by default). Generic Agent selection, detail, conversation, LLM exchange, and live-sync use the shared exact named-agent session grammar. A malformed, empty, or multi-valued direct Agent route renders an invalid-session state without mounting detail, making Agent API calls, selecting store state, subscribing, redirecting, or falling back. Invalid raw subscription input receives no acknowledgement. There is no identity aliasing or UI normalization.

Direct persistence operations fail at their owning request and do not poison unrelated later mutations through a persistence-health latch. Provider-routing availability is explicitly live process-local state and resets after process restart; the UI must not present it as historical or durable. Auth-profile refresh uses strict direct file reads and optimistic complete replacement, with concurrent last-completed-write-wins risk left to operator retry. Returned `work:///tmp/stash/...` URLs retain their existing presentation but refer to disposable work output with no retention guarantee.

Status: current functional UI authority.

## 1. Purpose

The operator UI shows Saivage state and hosts the Analyst. It is projection-oriented and Analyst-mediated by default, with the Dashboard's direct **Stop project** and bearer-only, capability-gated, exactly confirmed **Restart server** actions as the two runtime-control exceptions.

The UI must help the user understand what the autonomous runtime is doing, inspect cards, workflow-defined record documents, named-agent sessions, files, and processes, and stay oriented during the configured global Analyst conversation. Ordinary mutations still go through that Analyst.

## 2. Layout

At typical desktop widths, ordinary workspace routes display a single screen with two always-visible regions:

- A left workspace area, roughly 70-80% of the viewport.
- A right Analyst panel, roughly 20-30% of the viewport.

On those routes, the Analyst panel contains the current Analyst session, chat history, and composer. It is not a drawer, modal, popover, slide-over, or hidden panel. At desktop widths there is no control whose job is to open, close, hide, reveal, expand-to-full-screen, or toggle the Analyst panel.

At narrow widths on ordinary workspace routes, the shell collapses to a single column and exposes a presentation-only `Workspace` / `Analyst` pane switch so the user can choose which region is visible. The switch changes only the local layout; it does not mutate server state and does not turn the Analyst into a modal or separate control surface.

Within the Cards workspace at desktop widths, the card tree and selected-card detail are independently vertically scrollable panes. Tree overflow does not move the detail, detail overflow does not move the tree, and normal Cards content does not create one combined Cards/page scrollbar. A valid loaded tree remains mounted, interactive, and at its existing scroll position while selected-card detail loads or fails; detail loading and error presentation is confined to the detail pane. A route outside the current card-ID grammar makes no detail request and shows the same **Card not found** state as a typed detail 404, explaining that the link may be obsolete after a reset. The URL is not normalized or automatically navigated, no Retry or global refresh is offered, and explicit **Back to Cards** pushes `/cards` with ordinary Back/Forward history. At widths below the Cards split breakpoint, `/cards` shows the tree alone and `/cards/:id` shows the detail alone; exactly the shell's **Back to Cards** action restores the tree, while desktop exposes exactly the state-local action.

On ordinary workspace routes, the current project name is shown in a slim header at the top of the Analyst panel only, occupying the top of the Analyst column rather than a full-width page bar.

The one layout exception is the canonical Agents detail route for the selected global Analyst session (`agent:analyst:global` by default). AppShell initiates the identity-only `GET /api/chat` request independently of Cards and arbitrates the resulting `pending | resolved | failed` identity projection. While a valid Agent detail route is pending, the persistent panel remains mounted and the routed inspector is withheld behind a workspace loading state; identity failure keeps the panel's explicit error and shows identity unavailable without guessing an ID or mounting the inspector. A resolved nonmatching Agent detail may coexist with the panel. For a resolved matching route, the shell first unmounts the persistent panel and waits one teardown tick before mounting the read-only conversation inspector; when leaving it, the shell first unmounts the inspector and waits one teardown tick before remounting the panel. A presentation-only monotonic token makes superseded teardown continuations inert and owns no identity, transcript, cursor, request, or lease state. The matching workspace inspector may show loading, unauthorized, error, empty, or loaded-conversation state and has no composer; the persistent project header, composer, and narrow `Analyst` pane switch are omitted. Each replacement panel mount uses the retained current configured identity, whose sole REST source remains `GET /api/chat`, to open a fresh exact acknowledged conversation lease even when Pinia's identity has not changed. Authorization, busy/admission, transport, provider, runtime, and persistence outcomes remain fallible. Chat-send success remains identity-free.

## 3. Workspace Area

The workspace area renders read-only projections of runtime state, including:

- lazy immediate-child hierarchy slices and separate current card detail;
- distinct structured card state, card `working_status`, accepted `result`, and the selected card type's compiled ordered record descriptors, tabs, content, and version history; record names are not a fixed UI-owned set;
- the lazy card tree;
- runtime dashboard/state;
- agent sessions and transcripts;
- files and file previews;
- processes and process output;
- runtime events, errors, debug views, and control-action audit records;
- configuration projections where appropriate.

These projections combine strict card/conversation reads with process-local runtime state. Conversation indexes and segment versions are durable authority; runtime state, actor snapshots, recovery diagnostics, and role cursors are not.

The web client has one owner for each separate core resource family. CardStore owns hierarchy slices, selected detail, compiled record descriptors/current content, card history/selection/diff, and independent per-record history/selected-version/diff state. Selected card/record history is already a row in one strict stream: a failed history or selected-version request is an ordinary selection-local error that preserves accepted current and metadata state, never a separate availability state. Each request family has its own abortable owner. Records components present CardStore state and actions and own no cache.

Every displayed hierarchy child begins in explicit `undiscovered` state. A row shows a disclosure affordance meaning “discover immediate children,” not “known non-leaf,” only when its configured `permitted_child_types` is nonempty and its load state is not `confirmed-leaf`; configured-empty types never show discovery, and an accepted empty slice removes discovery from a configured-nonempty type. Initial root rendering performs no child-slice lookahead. Interaction fetches exactly that child's own slice; loading, error with Retry, loaded nonempty, and confirmed leaf are distinct. Collapse retains accepted mounted slices, while deep-route reveal requests one ancestor-parent slice at a time and stops when the next active edge is absent. No UI type or fixture contains raw hierarchy `children`, `mayHaveChildren`, `has_children`, or descendant counts.

Card detail renders only title, type, lifecycle/result/error/completion, version, urgency, created/updated time, and allowed actions. It renders no dependency, assigned-to, started-at, duration, notes, or dead metadata branch. Detail never bundles records. The Records section first accepts `/api/cards/:id/records`, then renders tabs in that selected compiled declaration order and issues independent `/api/cards/:id/records/:name` requests; it never uses a fixed record-name inventory or generic Files URL. Under `classic-typed`, `project`, `goal`, and `architecture` expose `brief.md`, `status.md`, and `review.md`, while `code`, `test`, `doc`, `data`, `research`, and `ops` expose `brief.md` and `status.md`. Only the validated `cards.records.get` 404 discriminant `Card record not found`, correlated to the active card/name and for a non-bootstrap descriptor, becomes loaded-empty. A malformed, undeclared, wrong-operation, wrong-variant, or mismatched response cannot select that state. Generic Files remains an independently mounted feature. Stopped cards retain their inactive/recoverable success presentation with a purple circular marker without a ring.

DebugStore retains exact event-derived errors from `/api/debug/errors`. Debug has no event Timeline and makes no `/api/events` request. Debug Errors derives exactly both runtime event kinds plus failed MCP invocations and is the durable surface for command/precondition, activation, actionable, and other recorded runtime failures. Dashboard remains current runtime/activation ownership state only; it has no durable command-error, activation-error, recovery, or error ledger. Invalid kinds fail REST contract parsing rather than being silently filtered.

Debug tabs are State, Operator Control, Errors, Agents, Graphs, Processes, Doctor, and MCP. Debug loads only the selected tab. Errors issues `/api/debug/errors` only when selected; Processes and MCP issue only their list/hierarchy request when selected; Graphs loads on first selection; Doctor remains manual behind Fetch; State and Operator Control use the already-owned runtime state. The Agents tab alone acquires global Agent ownership. Hidden tabs have no process registration, eager observability fan-out, polling, or request. Dashboard likewise issues no Agent, event, or MCP request.

The read-only **Graphs** tab fetches `/api/debug/graphs` only when selected for the first time or when the operator presses Refresh. Its card-type selector contains exactly the selected compiled map in declaration order, including custom names. Provider/model candidates come from immutable startup bindings; each node's operational tools come from the same effective selection used by execution, so a leaf node omits conditional `create_card` even when its named-agent ceiling includes it, while child-capable nodes retain it. Topology comes directly from the singular compiled state tables. Initial loading/error, loaded-empty invariant failure, and retained-data refreshing/refresh-error states are separate; a failed refresh leaves the accepted diagrams visible. A card-type selector displays exactly one independently inspectable workflow at a time. The deterministic responsive SVG places lifecycle entries on the left, named-agent nodes in stable layered columns, and DONE/BLOCKED/FAILED terminals on the right; arrowed outcome labels, visibly distinct cycle/back edges and runtime-failure edges, compact agent/model/tool/record/child labels, and terminal export/promotion details make topology inspectable. Under `classic-typed`, architecture displays exact nodes `draft`, `component-review`, and `system-review`; the latter two are clean version cycles of the one declared `review.md`, not separate record names. Entry, node, edge, and terminal elements are keyboard focusable and have textual accessible descriptions. The adjacent detail panel exposes the selected element's complete safe projection plus graph records and permitted child types. Graphs has no set editor, workflow editor, hot reload, drag-to-change, save, or mutation action.

Cards WebSocket invalidations are exact `children(cardId)`, `detail(cardId)`, `history(cardId)`, `diff(cardId)`, or `record(cardId,record_name)` freshness hints. They carry identity and scope only; no history changed-fields activity event exists. A record hint refreshes only that exact accepted configured name for the selected card. Reconnect snapshots the accepted dynamic map and refreshes each eligible name once without discovery. Failed refresh retains accepted content and exact Retry; selected-detail 404 clears all record owners and state. There is no polling or sibling-record refresh.

Files reconnect refresh is a browser-local registration owned by the sync client. The mounted Files view registers only an authoritative active-view REST refetch; it uses the ordinary non-Cards connected-registration/open behavior and has no completion callback. Metadata and output listings have independent abortable latest-request owners: a newer request replaces only the owner for the same listing resource, and stale or aborted success, failure, finalization, logging, and cleanup are inert. The two listings may run concurrently without cancelling each other, and Files-store disposal aborts both owners. The current owner alone may publish its path/files, shared listing error and authorization state, loading completion, or freshness success. File-preview ownership remains separate and unchanged. Files freshness uses the actual latest accepted successful REST completion across metadata listings, output listings, and file previews. It becomes stale after 30 seconds without a later accepted success; a later success clears and restarts that age, while failures do not reset it. WebSocket event timestamps and provenance do not participate. This does not imply or accept a Files invalidation frame. The only unscoped invalidation resource is `runtime`; `files` and `processes` are not wire values.

Authored close invalidates only the selected exact record name when its card is selected; it does not refresh sibling records or card-version history. Open/edit/discard append one row and change the singular current effective-content projection. Record reads are independently abortable per configured record, and selection change aborts/removes old-card owners before loading the new card. Even a late completion after abort cannot install old content, empty state, loading, error, or stale state into the new selection. Record 404 presentation follows this complete status-and-state table and never parses backend message text:

| Request state and outcome | UI/CardStore state |
| --- | --- |
| Initial required `brief` 200 | accepted content |
| Initial required `brief` 404 | required-record initial error; no accepted value |
| Initial optional `status`/`review` 200 | accepted content |
| Initial optional `status`/`review` 404 | accepted empty, current and successful |
| Any refresh 200 | replace with accepted content; clear stale/error |
| Refresh 404 after accepted content, all slots | retain exact content visibly stale with error and exact Retry |
| Refresh 404 after accepted-empty optional `status`/`review` | retain empty as unchanged success; clear transient stale/error and show no Retry |
| Any non-404 refresh failure after accepted content or empty | retain exact accepted state visibly stale with error and exact Retry |

Initial non-404 failure is an initial error, and required `brief` never accepts empty. Closed authored records are append-only: accepted content cannot legitimately disappear from an active card, but tombstone opacity and optional absence share the fixed HTTP 404, so accepted content must not be erased. A malformed canonical record stream, I/O failure, or other unexpected record-read failure is not absence and reaches the opaque strict HTTP 500 boundary; the UI never depends on exception prose. An already-empty optional slot still represents unchanged absence after 404. These are semantics of a record request while active detail exists; parent-detail 404 teardown clears record ownership as selected-card cleanup and does not reinterpret any record response. Independently refreshed hierarchy/detail communicates tombstone or path inaccessibility.

Every displayed **Diff vs current** request follows the source-derived request identity and currentness contract in the exact block below. CardStore receives only shared-contract-validated rows with required `{field,before,after}` members and performs no normalization. Malformed valid JSON at declared status 200 fails shared status-indexed parsing before state admission and is a contract/protocol failure, not an `OperatorApiError`. A diff refresh failure retains its rows visibly stale with exact Retry.

The runtime dashboard is current-state-only. It shows process-local runtime status and exact active-card evidence without a runtime-state file, command/run ledger, control audit, or durable actor cursor. Every projected owner has a ready processor and exact planning/terminal position. The runtime state's `current_card_id` is the sole current-card source. Displayed-card children are a projection of the already loaded committed hierarchy slice, remain in that slice's committed order, and render lifecycle through the shared card-status badge projection; Dashboard neither fetches nor reorders that slice. Stopped is inactive/recoverable with a purple circular marker without a ring, while cancelled remains neutral/gray. The displayed Started value is the stable lifecycle-lock start time and does not change on refresh, Pause/Resume, leaf transition, Stop, or another Run in the same server process. Dashboard exposes **Stop project** while starting, running, pausing, paused, or retained error; closing and stopped disable it. Stop is a runtime halt, not domain cancellation. It may abandon a near-terminal result whose durable append is already present or absent. Successful halt projects stopped only after every frozen owner and runtime process joins; a later Run resets the durable running chain leaf-to-root and activates only project through configured STOPPED. Failed halt stays error and requires service restart. The success wire shape remains `{status:'stopped',contained:boolean}`: a delegated/joined live halt is true and a missing/dead or no-runtime no-op is false.

Dashboard, Header, and Debug distinguish a never-accepted response from an accepted null payload. Before any accepted response, RuntimeStore availability is null and displays **Unknown**/**Not loaded** with the applicable initial loading or error. Every accepted validated runtime response carries concrete availability. Components display the producer's declaration-level [exact availability vocabulary](system-specification.md#exact-availability-vocabulary); degraded and unknown diagnostic detail remains distinct from the pre-load null state. A booted server's readiness response is always 200 ready with this concrete availability, and runtime observation failure appears as degraded rather than unavailable. Accepted null runtime still displays **Stopped** and **No live runtime**; accepted non-null displays the payload status. Dashboard labels the exact socket state independently as **Connected**, **Connecting**, **Offline**, or **Unauthorized**; Header uses **Live** for connected and the same other labels. The socket detail always describes transport invalidations and does not claim REST payload authority. Runtime request presentation is **Loading**, **Refreshing**, **Refresh failed**, **Loaded**, or **Not loaded** as applicable. A refresh failure retains accepted state and appears separately from an initial error. The only displayed runtime timestamp is the absolute **Last successful refresh**, or **Never**. These surfaces do not infer runtime staleness from age and expose no WebSocket-event or callback provenance.

The Dashboard sends Stop as a bodyless request without JSON `Content-Type`; bearer `Authorization` and ordinary request headers remain independent and are preserved. A failed Stop request is a command error and starts no follow-up read. After Stop succeeds, RuntimeStore awaits one combined REST refresh; if that read fails, Stop still resolves and the classified initial or refresh resource error is the sole UI failure. The Dashboard never relabels that follow-up read failure as a command failure. The distinct **Restart server** action is rendered only when the required runtime-status field `restart_server_available` is true. That boolean is the sole public projection of the server-composed discriminated restart capability; the browser receives no port and does not infer capability from authentication. `DashboardView` owns the direct browser prompt, accepts only exact `RESTART SERVER`, and initiates the strict JSON request `{confirmation:'RESTART SERVER'}` with JSON `Content-Type` to the auth-gated `restart_server` operation. The Dashboard owns only that prompt and direct request initiation; the application-owned `RestartPort` owns terminal coordination shared with the separate Analyst restart path. When false, the UI does not offer the action; a stale direct request still receives typed `restart_unavailable`. Stop project never calls or aliases Restart server.

Dashboard also consumes the focused content-policy store. The store fetches authenticated `GET /api/runtime/content-policy` on application bootstrap and again after every accepted card invalidation, WebSocket reconnect, and auth-token reset; the existing single cards SyncClient registration composes those requests after preserving CardStore callbacks. Epoch/AbortController ownership discards superseded responses. There is no additional WebSocket resource, timer, watcher, or polling. A zero high-water is quiet. A failed read renders an honest unavailable warning. A nonzero value renders only the count, latest card and `blocked_at`, and an Agents link; it never renders provider response, first-pass evidence, candidate prose, request content, or a paraphrase.

`restart_scheduled` acknowledges accepted asynchronous intent, not replacement readiness. Terminal closer/leaf warnings do not retroactively alter acknowledgement or normal restart behavior. The internal immutable shutdown report is for direct App callers and process adapters; it is not a card outcome, containment result, or operator-editable state.

Agent conversation surfaces render the one stable append-only session in physical row order. They may show `model_recovered` uncertainty, the original-call paired failed tool result, node/edge transition rows, node prompts, correction rows, and a later fresh UUID continuation as separate facts; source UUIDs have no sequence or timestamp meaning. Notification-defeated candidates remain visible as ordinary failed `emit_result` rows followed by exact operator context and correction. Reviewer revision routes appear as ordinary transition context containing the accepted review record URL and summary; no special UI row type, durable reviewer phase, or recovered outcome exists. Run recovery never shows a reconstructed child result: every unmatched parent call is ordinary interruption, and for each selected card Run stabilizes all configured conversations then settles that card stopped before advancing. An already visible exact `model_recovered` row does not resume or redispatch the old activation and does not waive that card stop. Project alone begins through STOPPED; descendants become eligible only through later ordinary immediate-parent activation. These separate conversation/card appends are not cross-file atomic. Recovery after a dirty shutdown is best-effort semantic: the operator may observe a stopped card resume or a done card reactivate because its completion trace was lost or its parent was not yet updated, and this is expected rather than a defect.

Natural project completion adds no UI state or control. After process-local child ownership has fully unwound, the runtime requires the strict durable running chain to be exactly project-only before publishing the terminal root version. Missing, branching, discontinuous, empty, or additional running topology therefore blocks completion while the existing root `running` version remains visible; no terminal root version is published for that rejected outcome.

Agent-list, selected-summary, selected-conversation transcript, and selected-LLM-exchange resources have independent loaded/loading/refreshing/error/auth state. An accepted empty agent list is distinct from an initial failure. Direct Agent detail/conversation returns not found only when its one strict canonical read reports `ENOENT`; malformed conversation data, symlinks, non-regular objects, and other I/O failures remain errors rather than empty or not-found state. A same-session conversation refresh keeps the last accepted transcript visible on non-abort failure and reports the refresh error separately from an initial-load failure. A failed summary refresh retains accepted detail and labels any displayed progress last-known; before first summary success, unavailable/loading/error is not rendered as inactive. Only the validated `agents.llmExchange` 404 is an accepted loaded-empty result, including on refresh where it authoritatively clears an older exchange; a 404 for another operation and every malformed or undeclared response remain failures. Another refresh failure retains the accepted exchange or accepted-empty result and reports only a refresh error.

Debug keeps explicit session selection as presentation intent and derives its effective session as that explicit ID when it remains in the canonical agent list, otherwise the first row in canonical list order. Disappearance falls back without erasing intent, so reappearance restores the explicit session; an accepted empty list mounts no detail. The effective session and detail kind form the key of one Debug detail component. The primary Agents conversation is likewise keyed by route session, and its conditional Raw LLM Exchange panel is keyed by session. Each keyed conversation lifetime claims a fresh opaque current-consumer token, subscribes before fetching, and independently starts transcript and exact-summary reads on initial acknowledgement and reconnect. Reload requests both. Unregister happens before token-guarded clear, which aborts the selected summary request and invalidates stale detail responses/errors/finalizers. Exchange lifetimes claim and clear their independent token without opening a conversation subscription. Stale callbacks, completions, and delayed cleanup therefore cannot change or clear a newer consumer, and no consumer registry or copied agent rows exist.

Agent inventory summaries and list rows show the required compact pair `active · busy` or `inactive · idle`, derived only by exact canonical session-ID membership in one process-local executing-session snapshot capture. Inventory lists omit tombstoned-card sessions; direct navigation to a known tombstoned session retains its exact historical summary and conversation, but detail and conversation surfaces do not render the compact pair. Inventory rows have no provider phase, model, pending-call footer, heartbeat, elapsed time, message count, last-activity field, compaction badge, or terminal styling. Compaction rows remain durable transcript content, not a public activity phase. Selected Agents and Debug conversation details, including selected global Analyst detail, may separately show `Compacting history — N summary calls completed`, whether one summary call is in flight, and elapsed time. A refresh failure marks retained progress last-known; successful `compaction:null` clears it. The persistent Analyst composer panel is unchanged.

The Agents UI uses backend-decorated Agent summaries and exact transcript/exchange resources. It never consumes or recreates `runtime.status.actorRuntime.agents` and performs no browser-side runtime join. AppShell obtains only the configured global `session_id` from `GET /api/chat`; identity resolution does not fetch transcript and is independent of Cards. In selected Agents/Debug detail, transcript responses and inventory partitions never write `currentSession`; one selected-summary reader is its only writer/resetter. That reader admits one exact request plus one boolean-coalesced trailing reread. Exact-global matching hints, matching known card hints, and a whole-Agents baseline reconciliation are relevant; unrelated known scoped hints remain suppressed. Before first exact detail establishes scope, a card hint may exact-read only the selected summary. Inventory reconciliation never fetches transcript for progress, and the independently owned conversation transcript never writes the summary. ## 6. Analyst-Driven Navigation

The Analyst can change the workspace view on the user's behalf.

Examples:

- "Open card goal-7" navigates the workspace to that card.
- "Show me the latest planner session for goal-7" opens that session.
- "Open the errors view" switches the workspace to runtime errors.

Navigation can be combined with mutation in one Analyst turn. For example, the Analyst can open a relevant session, queue a card notification, and report both outcomes.

Failed navigation results are inert. Malformed or cross-wired successful results are contract failures after send acceptance and produce no navigation effect.

MCP topology and Debug Graphs remain read-only.

## 9. Secret Display

The Analyst may inspect secrets when authorized and necessary. Operator responses are nevertheless projected by the backend's narrowed typed owner contracts before the UI receives them; the frontend performs no effective-config redaction. The shared backend contract structurally omits provider/account `baseUrl`, replaces provider/account API keys and every stdio MCP environment value, and retains streamable-HTTP MCP URLs only after removal of userinfo credentials, query contents, and fragments.

If the Analyst needs to discuss or use a secret, it should avoid unnecessary disclosure and should summarize where possible. Frontend token/key/path heuristics are defense in depth for accidental display only. They do not define identity, do not replace backend owner projection, and cannot guarantee detection of arbitrary unmarked secrets in free text.

The Files backend read model, not client-side presentation, is authoritative for file browsing, card membership, metadata, and preview admission. Every reached active card namespace shows virtual `card.json`, present configured record URLs in declaration order, and the active hierarchy directory `children`; a directly addressed retained tombstone shows only `card.json`. `card.json?v=N` is an explicit selected-version read and exposes card artifact row format 2 with both durable `child_membership` and `active_child_order`, but no pending-notification field. Its ordinary wrapper is exactly `{format_version:2,kind,entry_id,card_id,version,published_at,card,change}`; a tombstone substitutes `final_card` and adds `prior_card_version`, retaining the same required nullable `change`. Non-null change is exactly ordinary `{summary,changed_fields,actor}` metadata; initial and queue-only publications use null, and mixed lifecycle/queue publications expose ordinary metadata only. History and diff views likewise display the public relationship fields while omitting queue state, direction, bodies, IDs, counts, membership, and receipts. Hierarchy/dashboard/tree wire order remains the backend's filtered active projection and gains no client ordering algorithm. The card-stream-v3 split is reset-only; old `children` records and row format 1 are rejected, not rendered compatibly. Physical stream files, conversation indexes, UUID segment filenames, and version directories are never browsable. A failed explicit historical read preserves listing/current state and offers one explicit Retry.

Unlinked and incomplete physical namespaces remain hidden, and tombstones are unavailable to active records, children, detail, and inspection. The direct Files `card.json[?v=N]`, exact history/version/diff, and known retained-conversation exceptions above do not make a tombstone active. Aliases into card storage have no physical fallback. Listing reports only present validated optional records and fails on malformed stream state, while preview performs strict definition/content validation and can fail. Unknown cards and missing optional record streams are 404; missing bootstrap is a strict server failure, distinct from optional/not-found 404. A selected document whose serialized bytes exceed the preview limit is 413 with that selected-document size; binary content is 415; reached malformed, empty, definition-mismatched, symlinked, non-regular, or unreadable canonical state is the ordinary safe server error.

Blocked secret paths and generic aliases to blocked targets are absent from browsable listings and cannot be previewed. Admitted explicitly redacted generic files and aliases remain visible and readable only through previews to which the backend directly applies the singular outbound redactor after reading; the UI must not reconstruct or request unredacted content. Card browsing introduces no client cache, scan, repository, membership inference, or fallback path.

A successful generic listing may omit policy-hidden or reserved children and a reached child whose metadata stat reports exact `ENOENT` because it disappeared during the snapshot. Any different reached-child metadata failure rejects the whole REST snapshot through the existing generic error state; the UI does not install an incomplete listing as authoritative. Exact `ENOENT` for the requested generic list or content target remains the declared 404, while other requested-target metadata failures use that same generic error state.

## 10. Process And Tool Output Projections

Process visibility is broader than termination authority. Conversation, chat-send invocation data, process-list rows, card detail/children, card history/diffs, and WebSocket tool activity arrive already source-projected by the backend. Process owner/process/session/card/status/time/exit/byte/work-URL identities remain exact; command, error, and diagnostic prose is redacted. `owner_kind`, `owner_id`, card association, labels, and displayed command/log metadata explain provenance only; a tool can terminate a process only through the exact direct scope capability and category that launched it. The UI must not infer authority from a visible owner match.

Process-list rows expose nullable `card_id`, explicit `owner_kind` / `owner_id`, and `logs.stdout` / `logs.stderr` as canonical `work:///cards/<cardId>/processes/<id>/{stdout,stderr}.log` URLs for card-owned processes or `work:///processes/<id>/{stdout,stderr}.log` URLs for non-card Analyst/operator/runtime processes. There is no process-detail endpoint or route; process navigation selects the Processes tab and highlights an ID from the accepted list. The Debug process-log Browse action forwards these `work:///` values to the independently mounted Files read model. The Debug agents area shows Conversation and Raw LLM Exchange views. Raw LLM Exchange reads the latest settled app-log `provider_exchange` metadata entry through `/api/agents/:id/llm-exchange` only while explicitly mounted and never exposes raw provider payloads or secrets.

Canonical Agent-session provider-exchange publication prompts Agent refresh only after persistence returns successfully. Event publication emits no UI freshness hint. Control-action, internal `internal:compaction-summary:*`, and other noncanonical-session provider-exchange rows do not prompt Agent refresh. Freshness remains a lossy prompt to reread authoritative REST state.

Current Raw LLM Exchange request-parameter metadata has no LLM `phase` key. The panel renders transport-specific request parameters generically; old rows that contain `phase` remain raw records and are neither interpreted nor normalized.

The backend reuses the provider-exchange owner projector on the latest canonical exchange before returning Raw LLM Exchange, even though new diagnostics already receive the same projection before publication. Contract/provider/model/account and relational identities remain exact; request parameters retain their direct transport shape, endpoint userinfo/query/fragment stay absent, and only classified error prose redacts. Raw HTTP bodies and provider-private context are unavailable. A strict canonical read or projection failure returns only the stable generic API error and writes only the stable operation and validated session identity to the server log; raw exception text, malformed content, stack, and project path are exposed to neither sink.

Canonical `work:///` is the browsable Files root for `.saivage/work`; content preview rejects that root as a directory. Concrete process-log Browse actions remain canonical descendant URLs, and the process API rejects `work:///` itself as a log reference.

Content supervision has been deleted. Debug has no supervision panel, review statistics, quarantine presentation, or `/api/debug/supervision` request. Path containment, blocked-secret policy, and command policy remain operational/API controls for predictable file admission, limiting operator-facing browsing, and constrained ordinary tool execution; they do not contain a trusted root-capable agent. Centralized outbound redaction separately preserves secret non-disclosure at the operator-facing projection boundary.

Tool-activity websocket projections use the unified metadata-only process result fields: `process_id`, `exit_code`, `status`, `stdout_url`, `stderr_url`, `stdout_bytes`, and `stderr_bytes`. Legacy inline-output fields such as `stdout`, `stderr`, `stdout_tail`, `stderr_tail`, `tail_truncated`, `truncated`, `log_path`, `running`, `terminated`, and `still_running` are not projected.

All three shared conversation surfaces present current built-in tools through one static descriptor per tool, which owns the action, knownness, grouping classification, call formatting, and optional successful-result formatting; the descriptor and backend identities follow the [exact shipped tool identities](../architecture/system-architecture.md#exact-shipped-tool-identities), so the record-version reader receives first-class call and result presentation rather than generic fallback. Complete live invocations, canonical call rows, and canonical result rows use the same source-aware projection; visible results remain the provider `ToolResult`, never internal settlement evidence. Unsupported tools and known tools rejected for malformed JSON or schema-invalid arguments remain readable with exact session/source/call/tool identity; their raw/rejected arguments receive text or opaque-value defense instead of making the transcript unreadable. A sole final durable unmatched call is displayed as neutral `no result recorded`, without an invented result or liveness state and without success, error, pending, active, or italic outcome treatment or a raw response.

Successful `glob` and `grep` rows always use the fixed headlines **glob completed** and **grep completed**. They never infer a whole-match count from returned entries because an entry may be one oversized-item slice. **Show raw response** exposes the exact opaque collection page, slices, and continuation for current results and exposes historical raw-array/plaintext-slice bodies unchanged apart from the normal outbound defense. The UI adds no search-page parser, decoder, pagination control, legacy formatter, or alternate presentation path.

Complete conversations permit zero or one unmatched call only as the final durable source row. Multiple or nonfinal unmatched calls and result-before-call fail. This rule is independent of runtime state and remains valid on later historical reads. Bounded `read_agent_session` validates the complete stream, then keeps the requested suffix and order and reports exact `total_visible_entries` and `returned_visible_entries` without pair expansion; an isolated result remains readable because its call may precede the boundary.

Result semantics recognize exactly two current envelopes: success is `success:true` with optional `data` and no `error` property, while failure is `success:false` with a string `error` and optional `data`. A valid success uses only intentional descriptor projection or a completion label. A valid failure displays its bounded string error with error tone, while its `data` and full envelope remain available only through **Show raw response**. Success with an `error`, failure without a string `error`, and every other non-envelope response—including objects, arrays, plain text, JSON primitives, `null`, and invalid JSON—receive one generic semantic status; their exact content appears only after **Show raw response**. Built-in call descriptors continue to project selected request arguments into Action, Target, and detail, with the backend-projected request separately available through **Show raw request**. Every unknown tool remains visibly generic and retains **Show raw request**. **Show raw response** and the italic generic-tool hint exist only when a durable result row is present, so an unmatched unknown call has neither while retaining raw-request access.

Successful no-save `webfetch` text always returns a redacted `head` with fetched, once-redacted, and head UTF-8 byte counts. The shared conversation presenter shows a one-line head/count summary even for an empty head, labels `head_complete` independently from `fetch_truncated`, and keeps **Show raw response** as authority for the complete returned head and opaque result. A complete head omits `content_url` and keeps `redacted_url` as its headline. An incomplete head requires `content_url`; only the literal current canonical `work:///tmp/stash/webfetch-<positive-decimal-timestamp>-<16-lowercase-hex>.txt` form becomes a browsable Files link to the matching `.saivage/work/tmp/stash/` file. Alternate encoding, query, fragment, traversal, empty/double/trailing or extra segments, wrong scheme/directory, and malformed filenames are never normalized or linked and remain inspectable only as raw evidence. Saved results retain their `saved_as` headline; metadata and binary results retain their redacted-URL headline. Successful metadata, body, save, redirect-final, and Analyst brief-write output exposes `redacted_url` and never a raw `url`; durable call rows likewise expose only their redacted invocation URL. Generic WebSocket projection forwards current fields unchanged. This applies in the Analyst panel, Agents conversation detail, and Debug agents conversation detail; disposable output has no retention guarantee.

The MCP tab renders one server/tool hierarchy from `/api/mcp/tools`. It derives server, tool, invocation, and error totals from nested tool statistics. There is no separate MCP status request, flat tool/server inventory, keyed all-stats table, polling interval, or hidden-tab load.

## 11. Acceptance Criteria

The UI satisfies this specification when:

- on ordinary workspace routes, the Analyst panel is visible on first paint at desktop widths; on the exact `analyst:global` Agents detail route, the workspace instead hosts the read-only conversation-inspection component and the persistent panel, header, composer, and narrow `Analyst` pane switch are omitted;
- no drawer/toggle control is required to reach the ordinary persistent Analyst panel;
- on ordinary workspace routes, the workspace remains visible beside the Analyst panel;
- card detail distinguishes structured card state, live `working_status`, accepted `result`, and every ordered record descriptor declared by the selected compiled card type, without assuming a fixed name set;
- card detail can expose record URLs, metadata, and history when available, while leaving record mutation to the Analyst;
- card history rows and selection render version, publication time, and conditional ordinary summary/field/recorded-actor metadata while null entries remain generic and pending-notification state remains absent; snapshots and current-relative public diffs remain inspectable;
- read-only workspace navigation/filtering/copy/refresh still works;
- no direct UI control performs an Analyst-only mutation;
- the Analyst receives active workspace context for deictic requests;
- the Analyst can navigate the workspace on the user's behalf;
- agent conversations in the Analyst panel, Agents conversation detail, and Debug agents conversation detail use durable rounds, tool rows, grouping, human-readable details, raw-payload access, cursor tails, compaction bounding, and live-update stability without phase or pending-call presentation;
- all three conversation surfaces auto-tail while near the bottom and not paused for new durable entries; the Debug agents conversation live-updates without manual Refresh; and each surface's `Pause auto-scroll` checkbox routes new content to the `Jump to latest · N new` unseen counter.
## Publication-fatal operator behavior

Ordinary failed halt and actor-main containment continue to use runtime `error`, retain
Stop-in-error, and preserve the degraded Dashboard and Workspace Header presentation.
A durable publication whose outcome is unknown instead terminates the server before a
status transition or API/WebSocket fatal response. Clients observe abrupt connection
loss; the only diagnostic is the fixed server-process stderr line. The abandoned lock
continues through positive dead-owner or malformed fail-closed classification and the
existing explicit manual-repair instructions before a genuinely new startup.

A captured process is not shown as terminal, and a successful kill/containment result
does not return, until managed-group absence and both output readables have drained.
Consequently terminal log links include trailing buffered chunks for confirmed-stopped
processes. Live, unverifiable, or unconfirmed failed groups remain failures and are not
awaited as terminal rows.

## Granular Agent ownership

Agents and the selected Debug Agents tab alone share the global Agents lease. The
accepted baseline is partitioned into one global partition and card-ID partitions.
Card membership hints reconcile only the affected card endpoint and atomically replace
or remove that partition; reconnect replaces the complete baseline. Card Conversations
owns a dedicated card endpoint and card lease and never requests or filters global
inventory.

Conversation and raw-exchange panels subscribe before their first REST read and wait
for the exact current acknowledgement. Each exact key has one local reference-counted
owner, one in-flight request, and one trailing invalidation. Final unmount aborts,
invalidates authority, and exact-unsubscribes; reconnect creates a fresh lease and
generation. A transcript accepts full or cursor-tail responses, using frame watermarks
only by equality. Raw Exchange accepts populated `200` or only the exact no-exchange
`404` as loaded-empty; every other failure remains an error. Conversation-only and
exchange-only modes acquire only their corresponding lease. Agent list and transcript
UI contain no model, active/waiting phase badge, pending-call footer, heartbeat, or
richer snapshot-derived state; Agent inventory lists show only the required `active · busy` or
`inactive · idle` pair, while provider/model appears only in an explicitly mounted Raw Exchange.
