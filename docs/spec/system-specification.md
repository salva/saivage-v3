# Saivage v3 System Specification

This is the canonical functional specification. The current storage and runtime format is reset-only. Mixed-version operation, migration, compatibility reading, and rollback against current generated state are unsupported.

## Current Activation Ownership Contract

`SupervisorRuntimeApi` owns one private `activationOwners` map and is the sole coordinator of owner structure, current card, run identity/status, intervention readiness, Pause state, terminal winners, and Stop/application containment. Each value is a plain `CardActivationOwner`, not an actor, with phase exactly `prepared_root | child_admission | active | settling | publication_unknown | settled_contained`, terminal winner `open | result | cancel`, and containment owner `none | stop | application_close`. `CardProcessActor` remains a micro-actor; `ConversationLLMActor` is the direct provider/tool phase state machine.

The direct Conversation LLM owner has no `BaseActor`, event queue, or actor lifecycle settlement. Concrete `CardService` remains the one card/root reader and the one strict `cardRecordSchema` remains unchanged.

Every live LLM tool call uses the complete frozen context from `ConversationLLMActor.toolInvocationContext(outcome)`. It contains exact session/source/call/tool identity, external/process waits, and one mandatory child reservation. `invokeToolForLlm` and `invokeToolCall` require that context before their optional abort signal; only lower-level non-LLM `invokeTool` may omit it. Analyst uses the same context but has neither `activate_card` nor a planner child-control port.

Planner activation and cancellation delegate through a port bound to the exact parent owner. The provider performs only schema and immediate-child ID checks. Supervisor ownership is consulted before target I/O. Fresh child admission installs owner, relationship, and admitted lease before the one running append; currentness remains at the parent until publication succeeds. Exact same-parent/same-lease active or settling calls join without I/O. Normal terminal work claims its winner before publication, joins local work, atomically removes structure/restores currentness/releases the lease, invalidates, and only then delivers the outcome.

A complete lifecycle append failure is outcome-unknown. The exact owner and child wait remain retained, runtime becomes `error/not_ready`, and the planner cannot receive a failed tool result or continue. No reread, retry, rollback, replay, compensation, or inferred outcome is permitted. Historical publication uncertainty is distinct from a new local-containment failure. Successful Stop may clear uncertain in-memory ownership only after interruption, invocation/processor/publication joins, and process termination succeed, without another lifecycle read or write. A newly failed interruption, join, or termination retains `error/not_ready` and the identical failed Stop settlement.

Accepted Run installs a ready `prepared_root` owner, run identity, current root, opaque launch token, and `starting/not_ready` before recovery or root-running publication. Global application admission closes permanently. `RuntimeControlService` delegates Run, Pause, Resume, and Stop and owns no readiness binding. Natural root release is valid from running, pausing, or paused and calls `RuntimeGate.completeRun()` in the same transition that clears owners/run/currentness and publishes `stopped/stopped-ready`, preventing an old Pause callback from later publishing paused. Stop-first alone clears for reuse; application-close-first retains contained ownership until exit.

Card streams use only `format_version: 2`. The one strict `cardRecordSchema` defines every current `CardRecord`, history snapshot, card-version row, and tombstone final state; operator schemas and inferred web types reuse that complete shape. Omission is invalid. `subtype`, `assigned_to`, `metrics`, `estimate`, `started_at`, `duration_ms`, `status_text_author_session_id`, `latest_self_report`, and `metadata` are required literal null. `status_text` and `status_text_updated_at` are required string-or-null terminal companions. Card creators are exactly `analyst | planner`. Backlog, running, changed, stopped, and cancelled lifecycle states require null result, error, and completion. Every snapshot has one status authority at `lifecycle.status` and contains no top-level `status`, persisted `parent`, persisted `depth`, or `allowedActions`. Operator cards add only `allowedActions` and the operator summary. Planner and Analyst creation expose no lifecycle or structural publication fields and always publish backlog.

This v2 change is an unconditional reset-only cutover: every deployment stops the service, preserves configuration, credentials, operator inputs, source, skills, instructions, prompts, and canonical project documentation, runs the current built `saivage reset`, and starts the current binary. V1 and v2 rows carrying any removed field fail strict card and virtual Files reads; they are never migrated, normalized, rendered, or read through a physical-files fallback.

## 1. Product Boundary

Saivage autonomously plans and executes software work represented by cards. It exposes an operator server, Analyst conversation, card/agent/file/debug read models, and process-local runtime controls. The runtime is the only dispatcher.

## 2. Cards

Card identity is exactly `project` or `card-<segment>[-<segment>...]`, with one to five lowercase alphabetic segments. Each parent has a deterministic local spreadsheet sequence (`a` through `z`, then `aa`, and so on). Every child-creation call starts at `a`, derives the exact candidate namespace, and advances only when exclusive candidate `mkdir` returns `EEXIST`; it never enumerates siblings or inspects a collided path. Successful directory creation is the sole claim authority and permanently consumes that segment, including when later publication or linking fails. Parent and depth are derived from identity and absent from durable card snapshots. Derivation never grants membership: only each reached parent's committed cumulative `children` snapshot does. API routes, records, sessions, events, process provenance, and UI links preserve the same value; the mutable one-based sibling-rank label is `logical_path`, is derived from active indices in committed parent order, and is null for root.

One non-root creation attempt accepts exactly `NewChildCardInput`, freshly admits its parent and existing dependencies, then directly claims the first candidate whose exclusive namespace `mkdir` succeeds, progressing within that call only across `EEXIST`. Every other claim error propagates immediately. `publishInitialChildCard()` constructs every card property and one closed initial brief; root bootstrap separately accepts only `{title,brief}` and `publishInitialProjectCard()` constructs the exact Analyst-owned project defaults. The successful child order is namespace claim, complete initial publication and proof, fresh parent reread/admission, second proof, cumulative parent `children` append, then fixed runtime/runtime `child_link` history and effects. Dependencies are immutable after version 1. Because a new child may depend only on already existing cards, creation cannot close a cycle; canonical whole-loaded-graph validation still rejects malformed dependency cycles. A claimed but unlinked namespace remains consumed and invisible, and reported write failure authorizes no follow-up read, retry, or reconciliation.

Cards form a strict tree. Project and goal cards are planning cards; architecture, code, test, doc, data, research, and ops are terminal cards. Card type is chosen exactly once in the initial card row, and every later card version and the optional tombstone retain it. A card's planning/terminal family and eligible session identities therefore cannot change during its durable lifetime. Card statuses are exactly `backlog | changed | running | blocked | stopped | done | failed | cancelled`.

`blocked` is an inactive, unresolved activation result. It settles the current activation and returns control to the parent, but it is not dependency-complete, cannot support successful ancestor completion, remains notification-capable, and is absent from the running chain. An exact parent planner may later re-enter its blocked immediate child only through `activate_card`, which selects the configured `BLOCKED` entry; this is not an operator start or restart action. A blocked planning card may create a backlog child subject to the ordinary caller, type, dependency, runtime, publication, and linking gates. Immediate-parent `edit_card` and an accepted Analyst brief edit reopen blocked to `changed`, while cancellation, deletion, and reorder retain their separate operation rules.

`stopped` is inactive, non-running, nonterminal, mutable, notification-capable, and incomplete for dependency and descendant-completion checks. It is never an active child or running-chain member and is never dispatched automatically. Existing intervention-ready Analyst brief/card operations and an immediate-parent planner `edit_card` may edit it without changing its status. Only explicit project Run or exact parent `activate_card` reuses it through the configured `STOPPED` entry; new child creation remains `BACKLOG`.

In the Cards operator view, the opaque ID in `/cards/:id` is the sole selected-card authority. CardStore is the singular Cards data and freshness owner: it owns disjoint immediate-child slices keyed by stable parent ID, route-selected detail, the three selected latest-closed authored-record slots, the mounted selected history list, its immutable selected entry, and its displayed current-relative diff. Bootstrap alone initiates the one ordinary `/api/cards/project/children` root request; Cards view mount does not duplicate it. Expansion requests only the selected node's exact children route, and the client derives mutable one-based display paths from represented active sibling order. Hierarchy and route-selected detail, records, history, and diff remain separate REST authorities, so one completion never merges or normalizes another.

Cards freshness frames are strict exact targets; the broad `{t:'invalidate',resource:'cards'}` frame is invalid. The complete wire union is:

```text
{t:'invalidate',resource:'cards',scope:'children',card_id:<parent-id>}
{t:'invalidate',resource:'cards',scope:'detail',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'history',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'diff',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'record',card_id:<card-id>,slot:'brief'|'status'|'review'}
```

`children.card_id` names the parent key of `GET /api/cards/:id/children`; `history` names descending card-version headers; `diff` names a displayed diff against current; and `record` names one latest closed authored slot. The mutation owner publishes targets only after successful canonical publication, according to this effect matrix:

| Successful mutation effect | Exact Cards targets |
| --- | --- |
| Any actual current card-version change to `C` | `detail(C)`, `history(C)`, `diff(C)`, `children(C)`, and `children(P)` when `C` has active parent `P` |
| Child link or reorder owned by parent `C` | the preceding version targets for `C`, including `children(C)` for membership/order and `children(P)` when `P` exists because `C`'s containing row changed |
| Tombstone of `C` | `detail(C)`, `history(C)`, `diff(C)`, `children(C)`, `children(P)` when non-root, and `record(C,brief|status|review)` |
| New latest closed authored slot for `C` | only `record(C,slot)` |

No-op and reported write failure emit nothing. Creation's pre-link initial brief emits no record target; the successful parent link emits its parent-version targets. Authored open, edit, and discard do not change the exposed latest-closed projection and emit nothing; close emits only its exact record slot and never card-version history. Subtree deletion emits each successfully committed tombstone's targets from its preflight-known parent before attempting the next append. Targets do not cascade above the containing parent.

An exact invalidation refreshes only an accepted loaded slice or the currently selected accepted and visible detail/record/history/diff scope. A reconnect takes one synchronous bounded snapshot of accepted hierarchy slices plus the selected accepted detail and record slots, mounted accepted history, and visible accepted current-relative diff, then refreshes each member once. It does not discover ancestors, preload branches, refresh hidden or unselected resources, or retry a scope already stale because its previous refresh failed. The initial socket open for each authentication/configuration identity is baseline-only; every `reconfigure()` resets this one-open suppression before replacing the connection. Bootstrap/token change reconfigures, resets CardStore, and starts exactly one ordinary root load whether that request is still pending or already accepted when the baseline socket opens. Later opens are reconnect-eligible.

Each exact scope has one current request-owner object containing its `AbortController` and promise. A newer same-scope request immediately aborts and replaces it; success, rejection, and finalization may mutate state only while that exact owner remains current. Selected record reads pass their per-slot abort signal through the Files request and additionally require the same selected `{cardId,slot}` owner, so a completion after route change cannot affect the new card. Reset aborts and removes every owner before clearing accepted state. Refresh starts by marking only that accepted scope stale; success atomically replaces it and clears stale state. Non-404 failure retains exact accepted data, marks only that scope `refresh-failed`, displays the error, and waits for exact Retry. A current-owner selected-detail 404 is the exception: it aborts and removes every selected record/history/entry/diff owner, clears all accepted selected-card state, and installs fresh non-retryable typed absence while retaining route identity. Late completions cannot repopulate cleared state, and selected-card invalidation/reconnect admits no read until a new explicit route fetch succeeds. Retry performs one immediate REST request, does not refresh siblings, and schedules no further work. There is no Cards polling, timer, automatic retry, trailing refresh, sequence ledger, acknowledgement, replay, persistent cache, or global refetch.

Every displayed “Diff vs current” request has the singular identity `{cardId,fromSeq,to:'current'}` and serializes literal `?from=<positive-safe-integer>&to=current`. The numeric response `to` records which authoritative current version was compared; it never becomes a later request pivot. Diff refresh is therefore independent of detail completion order or failure.

Current authored-record 404 handling depends only on HTTP status, slot, request phase, and the preceding accepted state; the client never parses backend error text:

| Request state and outcome | CardStore result |
| --- | --- |
| Initial required `brief` 200 | accept content |
| Initial required `brief` 404 | initial error, with no accepted value |
| Initial optional `status`/`review` 200 | accept content |
| Initial optional `status`/`review` 404 | successfully accept empty |
| Any refresh 200 | accept returned content and clear stale/error |
| Refresh 404 after accepted content, for any slot | retain exact content stale, expose the refresh error and exact Retry |
| Refresh 404 after accepted empty optional `status`/`review` | accept unchanged empty successfully and clear transient stale/error |
| Any non-404 refresh failure after accepted content or empty | retain that exact accepted state stale, expose the refresh error and exact Retry |

An initial non-404 failure is an initial error; required `brief` has no accepted-empty state. This distinction follows the append-only latest-closed model: accepted closed content cannot disappear or revert on an active card, while tombstone/path opacity uses the same 404 as optional absence, so a refresh 404 cannot authorize discarding content. An optional slot already accepted empty still represents the same absence after another 404, so that refresh is successful unchanged-empty. This table governs record responses while active detail exists; clearing records after parent-detail 404 is selected-card teardown, not changed record-404 interpretation. Independently invalidated hierarchy/detail surfaces expose card inaccessibility without inventing authored content.

On a cold store, route reveal loads each required ancestor-parent slice in order and follows an edge only when the containing accepted non-stale slice represents it. A stale or failed required slice stops traversal without consuming obsolete membership or auto-retrying. After a relevant ancestor slice is successfully replaced, CardsView invokes the existing reveal action once; that action may continue through newly represented idle descendants, sharing exact in-flight owners, and is bounded by the five-segment card-ID depth. An irrelevant branch replacement does nothing, and a failed-stale ancestor waits for explicit Retry. Successful detail or detail retained after non-404 refresh failure may remain visible while an absent or stale represented edge leaves the selected tree row and Path unrevealed. Detail 404 instead clears the selected-card resource scope while neither clearing nor certifying hierarchy. A direct route outside the current grammar makes no detail read, is not accepted or normalized, and exposes the same explicit not-found/**Back to Cards** recovery state. Root/current-invalid routes clear route ownership and supersede reveal without cancelling shared hierarchy work. Route-required reveal takes precedence over collapse intent only along represented edges. Desktop uses independently scrolling tree and detail panes with no combined Cards scroll, while mobile presents the tree or selected detail as one pane with Back returning to the tree.

Every card requires ordered `pending_notifications`. Notifications are allowed on backlog, changed, running, blocked, and stopped cards. Done, failed, and cancelled cards require an empty list and reject enqueue with `terminal_card`. Unrelated mutations preserve the list; transitions to done, failed, or cancelled clear it. Reopening supported statuses to changed uses only the supported `setStatus('changed')` transition; no actor callback or lifecycle-repair authority exists. No `next_role`, retry count, reviewer phase, recovery cursor, or autonomous-round counter exists.

The card-stream row schema is the sole structural parser for each raw row at a read or write stream boundary. The resulting typed rows then undergo non-parsing semantic stream validation of identity, history, transitions, ordering, children, and tombstones; semantic validation does not invoke another Zod parse.

Card state/history and tombstone use one exact strict append-only `card.jsonl` whose row grammar is exactly `card-version | card-tombstone`. Card versions are contiguous from 1, retain immutable fields including the initial `type`, and enforce strict history, lifecycle, children, and child-link-only mutation transitions. At most one tombstone may occur; it is forbidden for root, must be the final physical row, exactly preserves the final card including immutable type, and carries valid delete history. The deletion history `card_id` equals the tombstone `card_id`, its `changed_at` equals `deleted_at`, and its `version_seq` equals `final_card.version_seq`. Authored records are exact `brief.jsonl`, `status.jsonl`, and `review.jsonl` streams of `record-revision` rows with logical versions and contiguous stream-local revision sequences. The first brief row is closed logical version 1; status/review begin open at version 1. Open edits preserve opening facts and change content, close/discard terminalizes that version, and only then may the next logical version open. Complete initial publication requires and proves the closed initial brief, but card-only hierarchy, detail, and card-version-history reads do not read authored streams. An explicit current authored-record request alone strictly validates its requested slot stream; optional missing status/review retains its existing empty behavior, while required missing or malformed brief and malformed reached authored data fail that resource. `AuthoredRecordNotFoundError` is the sole clean card-or-selector absence signal emitted after those strict reads; malformed complete data, required-file absence, I/O errors, and invariant failures propagate unchanged and are never normalized as absence. Current card state is the last validated card-version row. A tombstone remains parent-linked and ends descendant traversal. Normal active reads walk root-to-target committed links before touching each exact child namespace and never enumerate physical entries. Card-domain detail/history/version/diff/record reads treat a tombstoned target exactly like an unknown card; this opacity does not gate direct access to an already known exact conversation identity.

The complete, duplicate-free cumulative `children` array in each parent version is the sole linked-membership and semantic sibling-order authority, including retained links to tombstoned children. `CardRecord` has no `position` field in the current reset-only format. `listChildren(parent)` reads one exact linked active parent, follows its committed immediate-child IDs in array order, and omits tombstoned children without sorting or changing the retained order. Creation admits only active planning-card parents whose status is exactly backlog, changed, running, blocked, or stopped, checks dependencies before claiming a namespace, and repeats complete parent type/status admission before namespace claim and again before linking. Analyst creation additionally rejects a running parent and always creates the child in backlog. It appends the newly and completely published child at the end of one fresh cumulative parent snapshot; directory claim consumes identity, but only that later parent append grants membership and order.

A reorder request must be a duplicate-free permutation of the exact current active child IDs. An active-order no-op appends and emits nothing. A real reorder writes no child stream: it appends one parent version whose complete `children` array places the requested active IDs first and then every retained non-active link in its prior relative order. The old and new parent versions are each complete valid prefixes. Canonical parent-stream validation permits this dedicated reorder only as a nonidentity, same-length, same-membership permutation changing no local card field other than `children`, version, and update time; it does not classify child liveness. Link append and reorder are the only post-creation writers of `children`; generic card patches, including equal-value patches, cannot carry it. A Planner reorder is evidenced by this canonical parent card/history state and its normal tool result; it creates no current control-action audit row and adds no operator control action.

Deletion accepts one non-empty requested-root list and performs one fresh complete active linked-tree preflight. Duplicate and ancestor/descendant roots are unioned; unknown/root/permission-denied requests, surviving external dependents, and conflicting hierarchy/dependency constraints reject before mutation. The call-local graph orders intended dependents before dependencies and children before parents, choosing IDs deterministically among ready vertices. Each confirmed tombstone emits its ordinary deletion history event and card/runtime hints before the next append. A reported append failure stops immediately and emits nothing for the uncertain append; every possible visible prefix remains dependency- and hierarchy-valid.

Current card history has exactly eight discriminants: `update`, `notification_enqueue`, `notification_remove`, `status`, `terminal`, `child_link`, `reorder`, and `delete`. Update provenance is fixed planner/runtime, delete is Analyst/runtime, and every other family is runtime/runtime. Planner edit changes only title, tags, priority, urgency, or related from backlog, changed, or stopped; blocked/failed are first reopened through the exact changed status operation. Generic status targets are only running (from backlog/blocked/changed), changed (from blocked/done/failed), and cancelled (from backlog/running/blocked/changed/stopped/failed); running-to-changed is not an operation. Running/changed preserve notifications, cancellation clears them, and the ordered delta contains `pending_notifications` only when a nonempty list changed. Recovery running-to-stopped and STOPPED stopped-to-running remain disjoint fixed-reason status families.

Terminal completion is owned only by a non-cancelled activation outcome on a running card. Done/failed/blocked results are respectively `DoneResult`, `FailedResult`, and `BlockedResult`; there is no rework result variant. The outcome summary must equal its result summary. Publication always assigns `status_text = summary`, `status_text_updated_at = settledAt`, and empty notifications. Done has null error and completion equal to that timestamp; failed has error equal to summary and the same completion; blocked has error equal to summary and null completion. Ordered changed fields are lifecycle, then each actually changed status companion, then notification clear when needed; `change_summary` is exactly those names joined in order plus ` updated`. Every family rejects relabelling, wrong provenance/reason, wrong or reordered deltas, and piggyback fields.

## 3. Configured Card Processes And Sessions

The required `card_processes` configuration contains exactly `planning` and `terminal` family graphs. Each graph requires separate lifecycle entries `BACKLOG | CHANGED | BLOCKED | STOPPED`; each entry targets an ordinary node, and `STOPPED` requires a prompt. A node selects one code-owned compatible role, one node prompt, one corrective prompt, required record slots, and outcome-keyed strict edges. Edge targets are tagged exactly `{node:<id>}` or `{terminal:DONE|FAILED|BLOCKED}`. Only node-target edges may name a prompt. Prompt IDs are reusable references; configuration contains no prompt text, path, action, variable, counter, cursor, parallelism, or retry policy.

The authoritative default planning graph is `plan.complete_direct -> DONE`, `plan.admit_review -> review`, `review.approved -> DONE`, and `review.revision_required -> plan`, with `blocked` and `failed` from each node mapped to their terminal ports. `recover` has the planner routes of `plan` and is the default planning `STOPPED` target. Planner prompt authority chooses `complete_direct` versus `admit_review`; reviewer prompt authority chooses `approved` versus `revision_required`. Child count never selects review, so a zero-child card may enter reviewer. The default terminal graph runs executor node `execute`, whose `done | blocked | failed` outcomes map to `DONE | BLOCKED | FAILED`.

Each family is compiled once at startup into a shared immutable micro-actor definition. Lifecycle entries, configured nodes, and terminal sinks are actor states; accepted typed outcomes are events and configured edges are transitions. Same-node edges explicitly reenter, aborting the old state task and starting one new node task. Plain text, malformed results, pending notifications, record/evidence failures, reviewer freshness failures, and completion-gate rejection are hidden corrections inside one node task and do not transition or increment. One activation tracker owns its raw node operation and matching completion/failure consumer through containment reporting while sharing the low-level FIFO containment mechanics with the separate provider invocation lifecycle. Activation `run` admits an activation operation; provider invocation `begin` admits one exact lease, whose later `runExternal` remains valid after non-aborting admission close. This FIFO ownership matches one operation at each current frontier and does not promise generalized concurrent matching. Promptless BACKLOG/CHANGED/BLOCKED entry contributes no transition message; STOPPED contributes the fixed discarded-position notice and its required configured prompt. The first node ordinal is `0`; the entry bridge does not increment it, and each accepted cross-node or self-reentry advances exactly once (`0 -> 1 -> 2`). Live runtime status reports node `executionOrdinal` as a required nonnegative safe integer. No state ID or ordinal is durable.

`CardProcessActor` executes one node at a time and keeps graph position only in live activation memory. Each Planner, Reviewer, or Executor node has one ordered operational tool surface projected from its role providers. Prompt rendering receives that operational array without `emit_result`; the final provider array appends the sole terminal tool `emit_result` exactly once and last. That terminal tool accepts strict parsed `{outcome,summary}`: the object must be non-array, contain no unknown fields, use one exact configured edge key, and contain a trimmed non-empty summary of at most 2,000 characters. Validation begins after `JSON.parse` and therefore makes no raw duplicate-key promise. Generated `contractDescription` is the sole base-role-prompt authority for these fields and values. Every effective planner/reviewer/executor role template contains it exactly once and may not define a competing `status` field or fixed result list. Executor base prose describes the current configured node step under node/edge context and does not imply one executor node or card completion per activation. Analyst uses its ordered operational surface unchanged for prompt and provider input and has no terminal tool.

The optional on-demand skill catalog is the exact `.saivage/skills/index.json` JSON array. Each entry is one strict three-field object:

```json
{
  "name": "typescript-testing",
  "file": "typescript-testing.md",
  "target_agents": ["executor", "reviewer"]
}
```

`name` and `file` are nonempty. `target_agents` is a nonempty, duplicate-free array containing only `executor`, `reviewer`, and/or `analyst`; Planner has no `skill` tool. Entry names are unique. `file` is a normalized relative path beneath `.saivage/skills`, with no absolute, empty, `.`, or `..` segment. Unknown entry fields, including the removed `triggers` and `updated_at`, fail the complete index read. Index order is listing order.

Reviewer, Executor, and Analyst invoke `skill` explicitly; Saivage performs no automatic matching, ranking, selection, preload, or prompt injection. Omitted `name` lists only entries targeted to the caller and returns the complete tool result `{success:true,data:{skills:[{name}]}}`. Supplied `name` loads only an entry targeted to the caller and returns `{success:true,data:{skill_name,skill_content}}`, where `skill_content` is the exact UTF-8 file text. The result contains no target metadata, delimiter, or `loaded` flag. A missing exact index is an optional-capability case: listing succeeds with `{success:true,data:{skills:[]}}`, named loading returns the generic `{success:false,error:string}` unavailable result, and absence is not cached or replaced by a created file. A present malformed index, old-schema entry, duplicate name, invalid path, missing selected skill file, or other read failure returns that same generic failed ToolResult shape with its actionable error; there is no fallback, normalization, or skill-specific failure projection. A name absent from the caller's filtered catalog and a name targeted only to another role are both unavailable.

At node entry the owner appends role context, then immediate lifecycle/edge transition context when present, then the node prompt. Same-role nodes reuse the stable session; cross-role routing explicitly hands current execution to the target role. Immediate edge context contains only source node, accepted outcome and summary, accepted record URLs, and its optional edge prompt. No accumulated graph state is persisted.

One hidden corrective loop owns plain text, malformed or unknown results, record violations, pending notifications, planning completion, and reviewer currentness. Terminal completion is enforced by strict actor verification and these acceptance gates, not by a provider terminal phase. Corrections remain in the same logical node, session, baseline, and role. After all read-only gates, terminal edges synchronously claim the result before record close, accepted tool settlement, cleanup, and later supervisor-owned publication through the exact activation owner. Intermediate edges retain the same close/settle/node-local cleanup ordering.

Reviewer stale rejection discards the stale open review, captures one new exact descendant context and semantic snapshot pair, appends that exact refreshed context, replaces the comparison snapshot, and continues the same node. A later semantic change may reject again; unchanged refreshed context may succeed.

Stable session IDs are exactly `analyst:global`, `planner:<planning-card-id>`, `reviewer:<planning-card-id>`, and `executor:<terminal-card-id>`, where every card suffix uses the hierarchical card grammar. One shared schema/parser owns this grammar for canonical `AgentMessage.session_id`, persistence, conversation source/session validation, `ConversationLLMActor` admission, chat and generic Agent APIs, direct conversation live-sync frames, and web contracts. A complete persisted message with any other identity is malformed and fails without normalization or repair. Card-role conversations use fixed exact `conversations/<role>.jsonl` files under their card namespace; the singleton Analyst uses `.saivage/agents/conversations/analyst%3Aglobal.jsonl`. No session directory is claimed or enumerated. Project-wide inventory builds one fresh active linked-card projection, derives only card-type-eligible role candidates, attempts one canonical read of each exact candidate stream, validates each present result, and adds exact `analyst:global`; `ENOENT` alone means that candidate is absent. Those current-type candidates are complete because type is lifelong; a malformed history that changes type fails card-stream validation instead of triggering historical-role discovery. Direct known-session read/first-publish/append derives only the exact path and remains available after card tombstone; aggregate inventory omits tombstoned-card sessions.

The Analyst runtime owns at most one lazily created actor and accepts no caller-selected session identity. Parameterized chat routes compose `AnalystConversationSessionIdSchema` directly; after successful operator authentication, `ContractRuntime` rejects every noncanonical value with the standard `400` validation response before handler work. Chat exact-get/send success, WebSocket connection and turn acknowledgement, and final Analyst tool activities all carry literal `analyst:global`; no route alias exists, and a canonical GET with no conversation returns an empty successful transcript. Generic Agent detail, conversation, and LLM-exchange params use the full shared grammar; list/detail/conversation successes are role-discriminated, conversation entries match their enclosing session, and LLM-exchange success includes its exact `sessionId`. Conversation subscribe, unsubscribe, subscribed, and invalidate frames use the same exact union. Invalid raw frames are rejected before subscription mutation or acknowledgement. `ConversationSessionId` remains exact through direct owner-published SyncHub effects, socket state, web parsing, stores, and components. After each successful physical conversation envelope, the append owner calls `conversationChanged(session)` and `agentsChanged()` directly, then synchronously observes each non-`provider_private` row in physical order through a narrow five-field callback composed by the application. A private/visible pair exposes only its visible row. There is no event-to-SyncHub mapping, EventBus, or read-model listener registry. Observation failure is a confirmed post-publication failure and causes no read, retry, rollback, or later-row synthesis. The Vue Agent route is a raw ingress boundary: malformed or multi-valued IDs render an invalid-session state without mounting detail, REST, or live-sync work. While retaining its acquired lock, reset recursively force-removes exactly `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work` as whole trees, without probing or enumerating their descendants, then publishes a new canonical `project` root card and releases only its exact lock. Every path outside those four roots is preserved, including configuration, credentials, project identity, operator inputs, source, skills, instructions, and canonical project documentation. Reset never inventories or cleans lock siblings or other noncanonical paths. Incomplete namespaces and publication temps require no action. Malformed exact canonical targets require operator repair or reset.

File persistence provides no no-data-loss guarantee. Interrupted external effects may repeat, notification context may duplicate, process-local availability resets, concurrent auth refresh may overwrite credentials, and orphan files may remain permanently.
