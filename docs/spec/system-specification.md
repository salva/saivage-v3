# Saivage v3 System Specification

This is the canonical functional specification. The current storage and runtime format is reset-only. Mixed-version operation, migration, compatibility reading, and rollback against current generated state are unsupported.

## 1. Product Boundary

Saivage autonomously plans and executes software work represented by cards. It exposes an operator server, Analyst conversation, card/agent/file/debug read models, and process-local runtime controls. The runtime is the only dispatcher.

## 2. Cards

Card identity is exactly `project` or `card-<segment>[-<segment>...]`, with one to five lowercase alphabetic segments. Each parent has a deterministic local spreadsheet sequence (`a` through `z`, then `aa`, and so on). Every child-creation call starts at `a`, derives the exact candidate namespace, and advances only when exclusive candidate `mkdir` returns `EEXIST`; it never enumerates siblings or inspects a collided path. Successful directory creation is the sole claim authority and permanently consumes that segment, including when later publication or linking fails. Parent and depth are identity-derived. API routes, records, sessions, events, process provenance, and UI links preserve the same value; the mutable one-based sibling-rank label is `logical_path`, is derived from active indices in committed parent order, and is null for root.

One non-root creation attempt freshly admits its parent, then directly claims the first candidate whose exclusive namespace `mkdir` succeeds, progressing within that call only across `EEXIST`. Every other claim error propagates immediately without another candidate or follow-up inspection. The exact successful order is namespace claim, closed initial `brief.jsonl` and card-version-1 `card.jsonl` publication, the complete-publication proof inside `publishInitialCard()`, a fresh parent reread and admission, a second complete-publication proof in `CardService`, one cumulative parent `children` snapshot append, and only then parent `child_link` history, card, and runtime effects. The child becomes visible to authoritative list/tree readers only after the parent-link append returns; even complete readable unlinked initial streams are not membership. Any failure after successful claim ends that call without another candidate, adoption, cleanup, follow-up read, or effects, and the namespace remains consumed. Any reported append or replacement failure may be outcome-unknown and authorizes no post-error read, probe, retry, reconciliation, or affected canonical or domain artifact inspection. Production and verification perform no such inspection; verification proves stopping, ordering, and descriptor cleanup from operation traces and proves effects or their absence from spies.

Cards form a strict tree. Project and goal cards are planning cards; architecture, code, test, doc, data, research, and ops are terminal cards. Card type is chosen exactly once in the initial card row, and every later card version and the optional tombstone retain it. A card's planning/terminal role, processor, and eligible session identities therefore cannot change during its durable lifetime. Card statuses are `backlog | changed | running | blocked | done | failed | cancelled`. Running cards form one ancestor chain and only the deepest leaf performs work.

In the Cards operator view, the opaque ID in `/cards/:id` is the sole selected-card authority. CardStore is the singular Cards data and freshness owner: it owns disjoint immediate-child slices keyed by stable parent ID, route-selected detail, the three selected latest-closed authored-record slots, the mounted selected history list, its immutable selected entry, and its displayed current-relative diff. Bootstrap alone initiates the one ordinary `/api/cards/project/children` root request; Cards view mount does not duplicate it. Expansion requests only the selected node's exact children route, and the client derives mutable one-based display paths from represented active sibling order. Hierarchy and route-selected detail, records, history, and diff remain separate REST authorities, so one completion never merges or normalizes another.

Cards freshness frames are strict exact targets; the broad `{t:'invalidate',resource:'cards'}` frame is invalid. The complete wire union is:

```text
{t:'invalidate',resource:'cards',scope:'children',card_id:<parent-id>}
{t:'invalidate',resource:'cards',scope:'detail',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'history',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'diff',card_id:<card-id>}
{t:'invalidate',resource:'cards',scope:'record',card_id:<card-id>,slot:'brief'|'status'|'review'}
```

`children.card_id` names the parent key of `GET /api/cards/:id/children`; `history` names descending card-version headers; `diff` names a displayed diff against current; and `record` names one latest closed authored slot. The mutation owner publishes targets only after successful canonical publication, according to this effect matrix:

| Successful mutation effect | Exact Cards targets |
| --- | --- |
| Any actual current card-version change to `C` | `detail(C)`, `history(C)`, `diff(C)`, `children(C)`, and `children(P)` when `C` has active parent `P` |
| Child link or reorder owned by parent `C` | the preceding version targets for `C`, including `children(C)` for membership/order and `children(P)` when `P` exists because `C`'s containing row changed |
| Tombstone of `C` | `detail(C)`, `history(C)`, `diff(C)`, `children(C)`, `children(P)` when non-root, and `record(C,brief|status|review)` |
| New latest closed authored slot for `C` | only `record(C,slot)` |

No-op and reported write failure emit nothing. Creation's pre-link initial brief emits no record target; the successful parent link emits its parent-version targets. Authored open, edit, and discard do not change the exposed latest-closed projection and emit nothing; close emits only its exact record slot and never card-version history. Subtree deletion emits each successfully committed tombstone's targets from its preflight-known parent before attempting the next append. Targets do not cascade above the containing parent.

An exact invalidation refreshes only an accepted loaded slice or the currently selected accepted and visible detail/record/history/diff scope. A reconnect takes one synchronous bounded snapshot of accepted hierarchy slices plus the selected accepted detail and record slots, mounted accepted history, and visible accepted current-relative diff, then refreshes each member once. It does not discover ancestors, preload branches, refresh hidden or unselected resources, or retry a scope already stale because its previous refresh failed. The initial socket open for each authentication/configuration identity is baseline-only; every `reconfigure()` resets this one-open suppression before replacing the connection. Bootstrap/token change reconfigures, resets CardStore, and starts exactly one ordinary root load whether that request is still pending or already accepted when the baseline socket opens. Later opens are reconnect-eligible.

Each exact scope has one current request-owner object containing its `AbortController` and promise. A newer same-scope request immediately aborts and replaces it; success, rejection, and finalization may mutate state only while that exact owner remains current. Selected record reads pass their per-slot abort signal through the Files request and additionally require the same selected `{cardId,slot}` owner, so a completion after route change cannot affect the new card. Reset aborts and removes every owner before clearing accepted state. Refresh starts by marking only that accepted scope stale; success atomically replaces it and clears stale state. Failure retains the exact accepted data, marks only that scope `refresh-failed`, displays the error, and waits for its explicit exact Retry. Retry performs one immediate REST request, does not refresh siblings, and schedules no further work. There is no Cards polling, timer, automatic retry, trailing refresh, sequence ledger, acknowledgement, replay, persistent cache, or global refetch.

Every displayed “Diff vs current” request has the singular identity `{cardId,fromSeq,to:'current'}` and serializes literal `?from=<positive-safe-integer>&to=current`. The numeric response `to` records which authoritative current version was compared; it never becomes a later request pivot. Diff refresh is therefore independent of detail completion order or failure.

Current authored-record 404 handling depends only on HTTP status, slot, request phase, and the preceding accepted state; the client never parses backend error text:

| Request state and outcome | CardStore result |
| --- | --- |
| Initial required `brief` 200 | accept content |
| Initial required `brief` 404 | initial error, with no accepted value |
| Initial optional `status`/`review` 200 | accept content |
| Initial optional `status`/`review` 404 | successfully accept empty |
| Any refresh 200 | accept returned content and clear stale/error |
| Refresh 404 after accepted content, for any slot | retain exact content stale, expose the refresh error and exact Retry |
| Refresh 404 after accepted empty optional `status`/`review` | accept unchanged empty successfully and clear transient stale/error |
| Any non-404 refresh failure after accepted content or empty | retain that exact accepted state stale, expose the refresh error and exact Retry |

An initial non-404 failure is an initial error; required `brief` has no accepted-empty state. This distinction follows the append-only latest-closed model: accepted closed content cannot disappear or revert on an active card, while tombstone/path opacity uses the same 404 as optional absence, so a refresh 404 cannot authorize discarding content. An optional slot already accepted empty still represents the same absence after another 404, so that refresh is successful unchanged-empty. Independently invalidated hierarchy/detail surfaces expose card inaccessibility without inventing or erasing authored content.

On a cold store, route reveal loads each required ancestor-parent slice in order and follows an edge only when the containing accepted non-stale slice represents it. A stale or failed required slice stops traversal without consuming obsolete membership or auto-retrying. After a relevant ancestor slice is successfully replaced, CardsView invokes the existing reveal action once; that action may continue through newly represented idle descendants, sharing exact in-flight owners, and is bounded by the five-segment card-ID depth. An irrelevant branch replacement does nothing, and a failed-stale ancestor waits for explicit Retry. Current detail may remain visible while an absent or stale represented edge leaves the selected tree row and Path unrevealed; detail 404 establishes only detail-resource absence and neither clears nor certifies hierarchy. Route-required reveal takes precedence over collapse intent only along represented edges. Desktop uses independently scrolling tree and detail panes with no combined Cards scroll, while mobile presents the tree or selected detail as one pane with Back returning to the tree.

Every card requires ordered `pending_notifications`. Notifications are allowed on backlog, changed, running, and blocked cards. Done, failed, and cancelled cards require an empty list and reject enqueue with `terminal_card`. Unrelated mutations preserve the list; terminal transitions clear it. Reopening a terminal card uses only the supported `setStatus('changed')` transition; no actor callback or lifecycle-repair authority exists. No `next_role`, retry count, reviewer phase, recovery cursor, or autonomous-round counter exists.

Card state/history and tombstone use one exact strict append-only `card.jsonl` whose row grammar is exactly `card-version | card-tombstone`. Card versions are contiguous from 1, retain immutable fields including the initial `type`, and enforce strict history, lifecycle, children, and child-link-only mutation transitions. At most one tombstone may occur; it is forbidden for root, must be the final physical row, exactly preserves the final card including immutable type, and carries valid delete history. The deletion history `card_id` equals the tombstone `card_id`, its `changed_at` equals `deleted_at`, and its `version_seq` equals `final_card.version_seq`. Authored records are exact `brief.jsonl`, `status.jsonl`, and `review.jsonl` streams of `record-revision` rows with logical versions and contiguous stream-local revision sequences. The first brief row is closed logical version 1; status/review begin open at version 1. Open edits preserve opening facts and change content, close/discard terminalizes that version, and only then may the next logical version open. Complete initial publication requires and proves the closed initial brief, but card-only hierarchy, detail, and card-version-history reads do not read authored streams. An explicit current authored-record request alone strictly validates its requested slot stream; optional missing status/review retains its existing empty behavior, while required missing or malformed brief and malformed reached authored data fail that resource. Current card state is the last validated card-version row. A tombstone remains parent-linked and ends descendant traversal. Normal active reads walk root-to-target committed links before touching each exact child namespace and never enumerate physical entries. Card-domain detail/history/version/diff/record reads treat a tombstoned target exactly like an unknown card; this opacity does not gate direct access to an already known exact conversation identity.

The complete, duplicate-free cumulative `children` array in each parent version is the sole linked-membership and semantic sibling-order authority, including retained links to tombstoned children. `CardRecord` has no `position` field in the current reset-only format. `listChildren(parent)` reads one exact linked active parent, follows its committed immediate-child IDs in array order, and omits tombstoned children without sorting or changing the retained order. Creation admits only active planning-card parents in nonterminal statuses, checks dependencies before claiming a namespace, and repeats complete parent type/status admission before namespace claim and again before linking. It appends the newly and completely published child at the end of one fresh cumulative parent snapshot; directory claim consumes identity, but only that later parent append grants membership and order.

A reorder request must be a duplicate-free permutation of the exact current active child IDs. An active-order no-op appends and emits nothing. A real reorder writes no child stream: it appends one parent version whose complete `children` array places the requested active IDs first and then every retained non-active link in its prior relative order. The old and new parent versions are each complete valid prefixes. Canonical parent-stream validation permits this dedicated reorder only as a nonidentity, same-length, same-membership permutation changing no local card field other than `children`, version, and update time; it does not classify child liveness. Link append and reorder are the only post-creation writers of `children`; generic card patches, including equal-value patches, cannot carry it.

Deletion accepts one non-empty requested-root list and performs one fresh complete active linked-tree preflight. Duplicate and ancestor/descendant roots are unioned; unknown/root/permission-denied requests, surviving external dependents, and conflicting hierarchy/dependency constraints reject before mutation. The call-local graph orders intended dependents before dependencies and children before parents, choosing IDs deterministically among ready vertices. Each confirmed tombstone emits its ordinary deletion history event and card/runtime hints before the next append. A reported append failure stops immediately and emits nothing for the uncertain append; every possible visible prefix remains dependency- and hierarchy-valid.

## 3. Agent Selection And Sessions

Every nonterminal project/goal activation begins planner. Every nonterminal terminal-card activation begins executor. Reviewer is nested live planner work and is never selected at restart. After accepted reviewer rework closes `review.md` and settles the reviewer terminal result, and before admitting the fresh planner activation, the owner appends exactly one ordinary canonical user-text row to `planner:<card-id>`. That row contains the exact closed review URL and reviewer summary, so ordinary conversation projection supplies both to the fresh activation. This handoff uses no notification, retry counter, or durable reviewer phase. Stale review refresh has no count limit.

Stable session IDs are exactly `analyst:global`, `planner:<planning-card-id>`, `reviewer:<planning-card-id>`, and `executor:<terminal-card-id>`, where every card suffix uses the hierarchical card grammar. One shared schema/parser owns this grammar for canonical `AgentMessage.session_id`, persistence, source and actor classification, chat and generic Agent APIs, operator events, logged `conversation_changed` envelopes, live-sync frames, and web contracts. A complete persisted message with any other identity is malformed and fails without normalization or repair. Card-role conversations use fixed exact `conversations/<role>.jsonl` files under their card namespace; the singleton Analyst uses `.saivage/agents/conversations/analyst%3Aglobal.jsonl`. No session directory is claimed or enumerated. Project-wide inventory builds one fresh active linked-card projection, derives only card-type-eligible role candidates, probes their exact streams, and adds exact `analyst:global`. Those current-type candidates are complete because type is lifelong; a malformed history that changes type fails card-stream validation instead of triggering historical-role discovery. Direct known-session probe/read/first-publish/append derives only the exact path and remains available after card tombstone; aggregate inventory omits tombstoned-card sessions.

The Analyst runtime owns at most one lazily created actor and accepts no caller-selected session identity. Parameterized chat routes compose `AnalystConversationSessionIdSchema` directly; after successful operator authentication, `ContractRuntime` rejects every noncanonical value with the standard `400` validation response before handler work. Chat list/get/send success, WebSocket connection and turn acknowledgement, and Analyst tool events all carry literal `analyst:global`; no route alias exists, and a canonical GET with no conversation returns an empty successful transcript. Generic Agent detail, conversation, and LLM-exchange params use the full shared grammar; list/detail/conversation successes are role-discriminated, conversation entries match their enclosing session, and LLM-exchange success includes its exact `sessionId`. Conversation subscribe, unsubscribe, subscribed, and invalidate frames use the same exact union. Invalid raw frames are rejected before subscription mutation or acknowledgement. `ConversationSessionId` remains exact through owner-published read-model changes, SyncHub, socket state, web parsing, stores, and components. `conversation_changed` is validated by the shared schema and reparsed by its publisher before emission, but remains excluded from event-to-SyncHub mapping; owner-driven read-model changes remain the only conversation invalidation path. The Vue Agent route is a raw ingress boundary: malformed or multi-valued IDs render an invalid-session state without mounting detail, REST, or live-sync work. The former external chat integration, config, runtime lifecycle, and dynamic Analyst identities do not exist in the current format.

Each Analyst submission starts one strict source round with an exact system/activity marker payload `{event:'activation_open',role:'analyst',input_id,timestamp}` and no `card_id`. Ordinary model-backed submissions append that marker, one workspace-context system-text row, and one operator user-text row as one ordered batch; confirmed restart appends only its marker and user confirmation row. Analyst conversations permit no preamble. Unmarked, malformed, wrong-role, or mixed Analyst history fails strict ordinary reads rather than receiving an inferred boundary.

Every autonomous, Analyst, repair, continuation, individual-summary, and merge-summary invocation receives a fresh opaque UUID source input generated by its owner. That per-call input identity and the invocation owner's session identity are distinct from the stable source-session identity carried by the validated provider conversation projection. Ordinary persisted actor turns require the invocation and source-session identities to be equal. For original source UUID `S` and provider tool-call ID `T`, settlement identities are `${S}:tool-call:${T}` and `${S}:tool-result:${T}`. Success and failure both use `tool_result`; the next invocation UUID is unrelated. Attempt index orders transport attempts only within one invocation.

## 4. Optimistic Interruption Recovery

Startup has no runtime instance and performs no execution or conversation mutation. Only explicit Run validates the durable running chain, installs fresh process-local actors and immediate-child structural waits, and starts its deepest leaf by card type. Old runtime actors, callbacks, waits, processes, reviewer phase, and lifecycle state are never reconstructed.

Ordinarily, when a stable session is reused, its owner validates the complete canonical stream and latest-round pairing. One unmatched call in an interrupted latest round receives a provider-visible failed tool result stating that external or domain effects may or may not have happened, with `outcome_unknown:true`; the fresh activation then includes an unknown-effect recovery notice. Multiple unmatched calls, an older unmatched call, or unmatched work in a clean closure fails. Card and record facts never infer interrupted external success.

There is one narrower same-Run exception for a reconstructed planner's immediate-child `activate_card` barrier. The fresh child actor first publishes its actual terminal or cancelled lifecycle, finalizes and releases its local owner, and only then resolves its activation promise. While that same Run still owns an open parent continuation and Stop has not won, the fresh structural callback may carry the exact immediate child ID and outcome as a one-shot candidate to the parent's fresh planner activation. This does not recover an old callback, read a terminal sibling, or infer an outcome from durable card state.

The parent validates the entire canonical conversation before using that candidate. The latest interrupted planner activation must contain exactly one unmatched call. Its embedded payload ID and name must equal the top-level `tool_call_id` and `tool`; both names must be `activate_card`; its arguments must be exactly `{card_id}` with no missing or extra field; and that card ID must be the immediate structural child. Every mismatch fails before a fresh activation marker, recovery notice, conversation projection, or provider invocation and never falls back to outcome-unknown. A valid candidate is formatted with the same canonical result contract as live `activate_card`: `done`, `blocked`, and `failed` retain their successful child-outcome envelopes, while `cancelled` is the failed cancellation result.

Settlement checks the same activation signal immediately before and immediately after one direct synchronous result append. Stop before the first check preserves the exact `RuntimeStoppedInterruption` and permits no result append. Successful append includes synchronous conversation-change publication; such a callback may initiate Stop before the append function returns. The immediate second check then throws that same signal reason. Exactly the one paired result remains durable, while the fresh marker, reconstruction notice and its event publication, notification selection/rows/removal, conversation reread/projection, and provider invocation do not occur. Only after the second check passes may those later activation effects begin. The admitted order is therefore child terminal publication and release → child-promise resolution → fresh parent callback → strict association and result construction → pre-append signal check → one result append and synchronous publication → post-append signal check → fresh activation rows and later work.

The Stop windows have three distinct later-Run consequences. If Stop wins before the child settles, both parent and child remain durably running; a later Run installs a fresh full-chain wait, settles the leaf's own ordinary interruption as outcome-unknown, lets that leaf publish its real outcome, and then gives the parent that real immediate-child result rather than outcome-unknown. If the child was already terminal when Stop won before the parent's pre-append admission, only the parent remains running; a later Run starts that parent as the deepest leaf and settles its call ordinarily as outcome-unknown without reading or reconnecting the terminal child. If Stop starts synchronously during successful result publication and wins the post-append check, the parent remains running with an already paired call; a later Run appends no second result and begins only fresh activation work.

## 5. Notifications And Reviewer Arbitration

The durable notification target is one `card_id`. Public tools accept `card_id`, `kind`, and `body`; they do not accept role/session recipients and do not report session deliveries.

Planner/executor safe-point delivery is no-await append ordered notification context → remove those exact card IDs → admit provider request. Crash after append and before removal may duplicate context; stable notification IDs expose duplicates.

Immediately before planner/executor terminal acceptance, the owner rereads the card. Empty pending context permits record close and accepted tool-result settlement, followed by processor cleanup/final-outcome selection and then `CardActor` publication. Pending context defeats the candidate: append its paired failed `emit_result`, append ordered notifications, remove those exact IDs, and require another model round.

Reviewer never drains notifications. Before accepting `done`, `blocked`, `failed`, or `rework`, it recomputes semantic currentness then rereads pending context. Pending context wins even when stale: discard open `review.md` first, append the paired reviewer-defer failure second, transition nothing, and return to planner. With no pending context, stale review discards first, appends a failed stale result, appends refreshed context, and retries. Every fresh reviewer activation unconditionally discards an existing open review before its activation marker. A crash after discard but before paired failure is settled only as an ordinary unmatched session call.

Pause does not interrupt these synchronous terminal sections; it blocks the next admission frontier.

## 6. Activation Outcomes And Cancellation

Planner `activate_card` admission reads the target's current declared `depends_on` list and requires every dependency's current durable card status to be exactly `done`; every other status rejects, in declared dependency order, before child actor lookup. A missing target retains the ordinary not-found result, while malformed canonical state or an impossible missing declared dependency fails strictly. An empty dependency list is vacuously admitted. This is one request-time admission rule only: it does not schedule dependencies, propagate status, cancel work, or continuously enforce completion after admission.

For a rejected new activation, the request stops before `children.get()`, so it causes no child `CardActor` construction or registration, processor construction or idle processor-actor start, `running` write, live ownership, current-leaf or parent-wait transition, processor activation, provider call, tool, record, or process work. For a rejected request to join an already-running child, the same boundary precedes `children.get()` and `awaitSettlement()`, so this request adds no parent wait/currentness relationship and starts no duplicate work. The pre-existing actor, owner, current leaf, processor/provider work, and settlement remain untouched by the rejection and may continue or settle independently.

`CardActor` is the sole publisher of every non-cancellation activation outcome (`done`, `blocked`, or `failed`). Processors own role-specific terminal acceptance and return one final outcome only after required record/tool work and, for executors, invocation-surface cleanup. Provider failure, pre-provider failure, malformed provider metadata, processor failure, and cleanup failure all select the same failed outcome path. Cleanup therefore completes before publication and can replace an earlier accepted candidate with the one failed outcome that is durably published.

For a non-cancellation result, the synchronous order is one strict terminal-lifecycle publication → process-local activation finalization and queueing the existing `settled` event → exact natural release from both supervisor ownership maps when the runtime is not closing → deferred activation resolution and caller/parent continuation. Exact release means the actor no longer owns a live activation or runtime projection; it does not wait for the detached micro-actor object to consume the queued cosmetic event. The publication call includes its synchronous mutation callbacks.

If terminal publication throws, whether before replacement or from a later publication callback, canonical visibility is outcome-unknown: REST may later observe either the prior version or the newly canonical terminal version. The actor fails in place. It does not retry, reread, reconcile, make a further lifecycle write, settle the activation caller, or naturally release ownership. A later explicit Stop may contain the process-local winner and aggregate-clear the frozen maps without deciding the durable outcome.

The installed runtime's exact live-card map is the only resolver for running cancellation. If a target or cancellable descendant is live, the request routes to those exact actors. A running card with missing or duplicate live ownership is impossible and fails fast; no direct write fallback exists.

The sole exception is the exact process-local fatal owner disposition after a reconstructed immediate-child result append reports an error and its durable outcome is unknown. Explicit card cancellation is then unavailable until process restart. The supervisor rejects cancellation through the existing runtime-control conflict contract as its first supervisor-side operation, before any supervisor-side target-card read, run-identity capture, owner lookup or traversal, cancellation claim or settlement, durable write, or ownership-map mutation. Upstream Analyst/tool request validation and admission are separate and may already have performed their own reads before invoking the supervisor. This narrow guard does not restrict independent notification admission or writes.

`CardActor` synchronously claims cancellation versus result, closes admission and revokes callbacks, and exposes one exact actor-local cancellation settlement. Cancellation remains a distinct publication authority: that settlement contains activation processes and live descendants, directly publishes cancellation, and settles its caller exactly once. When the runtime is not closing, the supervisor then synchronously verifies the exact actor in both its live-activation map and retained-actor map and removes it from both. Done descendants remain done; inactive cancellable descendants use direct domain cancellation. Late provider, tool, process, child, reviewer, record, notification, and caller callbacks cannot commit after the claim.

Planner cancellation remains limited to an immediate child. Analyst cancellation may reach the runtime port while running/pausing/paused. Direct domain cancellation is for verified nonrunning/stopped work under lifecycle-lock and permission admission.

## 7. Run, Pause, Resume, Stop, And Restart

Runtime status is process-local: stopped when no instance exists, ordinarily starting, running, pausing, paused, or closing, and `error` for the exact retained fatal-owner case described below. Run preparation may select and durably admit the running chain, but returns only an opaque one-shot launch plan and leaves status stopped with no process-local current card. Launch validates and installs complete live ownership before publishing the run identity and deepest active leaf; only then may Run return the same authoritative runtime-state projection as `/api/state`. A synchronous launch failure returns no successful Run result and never projects the prepared durable leaf as live.

The non-null runtime state is built on demand and contains exactly supervisor status, fixed project identity, lifecycle-lock PID/start time, `current_card_id`, and the read observation `updated_at`. The lifecycle identity is injected from the acquired lock handle and remains stable for the server process; only `updated_at` changes with observation. `RuntimeControlService` keeps no state cache. Pause and Resume are state-free commands: the supervisor alone validates and mutates lifecycle status and gate state, while the service coordinates only intervention readiness. Pause sets one request flag. Actors check it before every provider, ordinary tool, process, child, reviewer, or next-round admission. At most one frontier parks; Resume clears and schedules it once. Runtime state and compact status contain no synthetic counters, tick values, active-work classifier, actor diagnostics, phase, caller, or session telemetry.

The scheduler-owned active leaf is the sole current-card authority. Launch publishes the deepest installed leaf; child entry publishes that child only after live ownership exists; every done, failed, blocked, or cancelled child settlement restores the immediate parent before parent continuation, and a later sibling entry then publishes that exact sibling. Pause and closing retain the leaf. Natural root completion and successful Stop clear run identity and leaf together, yielding stopped compact status with null current card and null runtime state. Status/state reads use only process-local owners and never enumerate card inventory, children, ancestry, histories, conversations, or sessions; mutation-time preparation and continuation may select the durable running chain.

REST Pause, Resume, and `stop_project` are bodyless operations. Absence is their only accepted request shape; every supplied payload, including `{}` and `null`, receives that route's local 400 validation response before runtime mutation. `restart_server` is the only operation in this group with a request body and accepts exactly the strict JSON object `{confirmation:'RESTART SERVER'}`.

Every Run validates one contiguous project-rooted durable running chain and installs one exact `CardActor` owner per chain card before opening admission. Ancestors enter process-local `structural_wait` on their immediate child and create no role/LLM actor; only the deepest card starts its type-derived planner or executor. After a normal result, `CardActor` publishes its durable terminal outcome, finalizes local activation fields and queues `settled`, and the supervisor synchronously releases that exact actor from both process-local ownership maps before the activation caller settles. Normal child settlement therefore wakes only its immediate parent into a fresh planner activation after publication and release. Any later legitimate activation of the released card constructs a fresh `CardActor` and processor rather than reusing the settled process-local owner.

If the one reconstructed-result append reports an error, its outcome may be unknown. The exact classified error propagates unchanged from planner processor through processor owner, card owner, structural ancestors, and root; it is not converted into a failed processor/card outcome. The failed activation performs no later marker, notice, event, notification, projection/provider, card lifecycle, retry, reread, release, or continuation effect. At the root, the supervisor enters one private process-lifetime fatal disposition, closes admission, sets existing runtime status `error`, and becomes not ready for intervention. It retains the exact run identity, currentness/current-card evidence, retained-card map, and live-card map; the actor read model therefore continues to expose the retained cards and agents with `pauseMode:'idle'`, meaning no admitted work rather than no owner. Compact status and runtime state both report `error` with the same retained current card.

That fatal disposition is never cleared in the supervisor instance. A later Run rejects with `status:'error'`, `started:false`, `stopped:false`, and `Runtime owner cannot Run again after reconstructed activation result append outcome became unknown; restart the server process.` before running-chain or other card reads, root-status writes, prepared-leaf selection, run-identity replacement, or gate mutation. Project Stop rejects through the existing `runtime_control_conflict` contract before its stopped/closing handling with `Runtime owner cannot be stopped after reconstructed activation result append outcome became unknown; restart the server process.` Explicit card cancellation has the first-operation supervisor-side rejection specified in Section 6, uses the same existing conflict code with `Runtime owner cannot cancel cards after reconstructed activation result append outcome became unknown; restart the server process.`, and applies to the errored card and every retained structural ancestor. Independent notifications remain admitted because this is not a generic mutation latch. Server/process restart is required before Run, project Stop, or explicit card cancellation can be admitted again.

`stop_project` is non-domain, restartable project containment. Starting/running/pausing/paused synchronously claims closing, globally closes continuation/admission, freezes both complete supervisor ownership maps, and creates one exact `RuntimeStoppedInterruption` plus one Stop-local containment collector. Stop never initiates domain cancellation and never itself writes a card, root result, child ToolResult, provider round, or Stop-caused durable event. Open owners become `claimed_stop`, use aborting revocation, and intentionally preserve durable `running` state. Result winners remain authoritative: Stop non-abortively closes their continuation plus processor-operation and provider-invocation admission, lets already-admitted winner work, cleanup, and publication finish, joins the closed trackers, and suppresses only later continuation. A cancellation that already won remains domain-authoritative, is not aborted or reclaimed, and Stop starts or joins its full actor-local settlement through durable `cancelled` publication and caller settlement. While closing, result and cancellation settlement perform no individual actor release; ownership remains frozen for Stop. Shared tool waits inspect the Stop signal after both fulfillment and rejection and throw the exact `signal.reason`.

After every owner, including every winning cancellation settlement, and runtime-process join, an empty collector atomically clears both frozen ownership maps and the current instance and returns `{status:'stopped',contained:true}`. This aggregate Stop clear is distinct from the supervisor's per-actor exact natural release. Cancellation-settlement, cleanup, or process failure rejects once with `RuntimeContainmentError`, retains both complete closed maps and the closing instance, and makes Run/Pause/Resume/second Stop conflict. With no installed instance Stop returns `{status:'stopped',contained:false}`. A later Run after successful Stop reconstructs ownership over the cards that remain in the running chain and activates only its deepest card.

The App terminal coordinator is separate and deliberately best effort. `App.stop()`, SIGINT/SIGTERM, startup failure, and acknowledged authenticated `restart_server` converge on the sole coordinator in `src/boot/app.ts`; no entry or cleanup leaf calls `stopProject`, cancellation, or the strict Stop collector. It sets application-closing and individually catches every synchronous admission closer before its first await. It then attempts cleanup leaves sequentially in reverse registration order, continuing after rejection or timeout. Exactly one `runtime`, one `analyst`, and one `mcp` component leaf coexist with independent LiveSync, Fastify, subscription, and lifecycle-lock leaves.

Application shutdown cleanup remains able to terminate and join owners retained by the exact reconstructed-append fatal disposition. It is the sole retained-owner settlement exception; project Stop, card cancellation, another Run, and independent notification behavior do not become cleanup paths.

Each process-owning component leaf closes admission/revokes callbacks and starts exactly one owned-root termination before any await, then awaits that termination with its actor/session/operation joins. A fulfilled `ProcessStopReport` is successful only when `failed` is empty. One shared runner/registry owns disjoint runtime, Analyst, and MCP roots; a timed-out component may continue only in its root while later leaves run, and App runtime termination may overlap project Stop on the runtime root. Repeated signals and already-exited/missing/removal observations are accepted without a global drain, deduplication, shared join, or collector coupling.

`run_command` executes its command as one argument to `bash -c`. A missing or empty cwd and canonical `project:///` select the project root; plain cwd values are project-relative and contained; `project:///...` selects a contained project descendant; and `system:///` or `system:///...` selects the system root or descendant. Malformed scoped URLs, query/fragment cwd values, unknown scoped schemes, and the `record`, `tmp`, and `work` schemes fail before launch. The managed-process registry consumes child `error` events immediately from spawn return, so a handled OS launch failure cannot independently crash the runtime, and it never registers a process group without a positive leader PID.

Every leaf uses the coordinator's referenced ten-second timer, above the managed-process five-second TERM grace plus two-second post-KILL verification. Fast settlement clears the timer; timeout does not cancel or retain the leaf. `App.stop()` resolves an immutable `ShutdownReport` containing only ordered allowlisted `{component, code}` warnings, where code is `closer_failed`, `cleanup_failed`, or `cleanup_timeout`; caught messages, paths, payloads, stacks, and causes are never inspected or exposed. It never logs or changes exit status. Process-owning signal/restart/startup adapters log only fixed component and code fields and preserve ordinary behavior. Public terminal access remains confirmed `restart_server` only with operator authentication; Stop remains available in both auth modes.

Run, Pause, Resume, and Stop produce no lifecycle-control audit entries. Unrelated audits remain.

## 8. Lifecycle Lock And CLI

Lock observation outcomes are missing, verified live, positively verified dead, indeterminate, and malformed. Indeterminate includes permission denial, unavailable process-start identity, and observation races. No outcome authorizes automatic lock deletion or takeover.

Initial project-card publication uses one three-outcome decision. A strictly validated canonical `project` card is existing initialized state; `null` authorizes publication only after direct proof that all four exact generated roots—`.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work`—are absent; every other result is an error and authorizes no publication. The exact cards root is classified first. A non-directory object or symlink there is partial generated state; a real directory is followed by the strict canonical-card read, whose valid current-format stream is accepted and whose malformed, missing-artifact, unsupported, or unreadable exact data fails unchanged. Only an absent cards root permits direct exact-path probes of the four roots. The decision never enumerates siblings or descendants and stops at the first obstruction.

`saivage init` acquires its init-mode lifecycle lock, strictly reads identity, and, when identity is absent, publishes and binds identity before classifying generated state. It then returns idempotently for a valid project card or publishes only after the decision returns `null`. If classification rejects retained generated state, the newly bound identity remains, generated roots remain untouched, and ordinary lock release makes the prescribed bound reset executable. `init --force` does not exist.

Server startup parses only the project root and `--create-runtime` intent needed before locking and requires the existing project identity needed for bound lock acquisition. It then performs full selected-config/environment validation inside terminal cleanup. Only after validation succeeds may `--create-runtime` invoke the shared initial-publication decision, create the cards directory after `null`, or publish the initial card; a returned existing card skips publication. Server start and control-endpoint publication follow. A configuration or classification failure releases the acquired lock through ordinary cleanup and performs no generated-state mutation. `saivage reset` likewise remains identity-bound.

CLI status, pause, resume, stop, and restart use only a verified live record's published non-null control endpoint and auth mode. Null fails exactly `active lifecycle owner; runtime control unavailable`; it never implies a lifecycle phase. The shared client never reads current YAML, host/port flags, host/port environment, defaults, runtime files, or current process config to select authority.

- missing/dead status succeeds with stopped/no-current-card;
- missing/dead stop succeeds with `contained:false`;
- missing/dead pause/resume fails because no live runtime exists;
- dead additionally reports abandoned-lock manual repair;
- indeterminate/malformed fails closed;
- delegation, authentication, response, and schema failure never falls back.

Published disabled auth omits Authorization. Published bearer requires nonempty `SAIVAGE_API_TOKEN` and sends it only as a header. CLI `stop` delegates to REST operation `stop_project`; there is no `stop_project` CLI alias.

## 10. Progressive Compaction

Compaction is mandatory for a bootable server. Configuration requires literal `enabled: true`, a positive route-independent `input_budget_tokens`, and a strict structured `summarizer_candidate` with exact non-empty `provider` and `model` plus required nullable `account`. Omission, false, incomplete or malformed fields, and a candidate not emitted by the configured Provider Registry fail startup. `account: null` is the implicit provider account; explicit `_implicit` and `_` are exact distinct names, and slash-bearing model IDs are preserved without parsing. Registry membership is exact and has no role routing, equivalent, failover, credential probe, or network fallback. `/api/providers` exposes Registry-backed ordered structured availability entries and never uses or leaks an internal implicit-account sentinel.

For each new planner, reviewer, or executor activation, the exact role prompt and ordered tools produce one ephemeral prepared compaction value before stabilization or transcript I/O. Each Analyst submission likewise resolves its exact role surface, ordered tools, rendered prompt with current project context, configured output request, and temperature, then prepares before marker or turn publication. Preparation validates budget, fraction ordering, positive reserved/requested completion tokens, requested completion not exceeding reserve, trigger plus reserve, escalated tail/middle widths no greater than normal, and static-token trigger/hard capacity. Autonomous tool-result and repair calls and Analyst tool-result continuations retain their submission's exact prompt, tools, and prepared object while refreshing source input ID and canonical projection; a later activation or Analyst submission prepares anew. Application composition retains candidate identity only in the summarizer's fixed one-candidate invocation route; runtime/Analyst policy, prepared policy, compactor arguments, prompts, and episode context are identity-free. The singular `ConversationLLMActor` requires prepared input for every persisted planner, reviewer, executor, and Analyst provider turn and rejects an unprepared call before transition or persistence.

The full config schema requires the effective Analyst output request—role-specific `models.max_tokens.analyst`, then `models.max_tokens.default`, then hard default 4096—to be no greater than `floor(input_budget_tokens * completion_reserve_fraction)`. That requested value remains the exact Analyst provider output authority; it is never clamped to the reserve. An impossible relationship fails selected-config loading with the effective source and both capacity facts, before runtime composition or generated root-card access. Dynamic prompt/tool overflow still fails preparation before Analyst marker/source append, summarizer/provider I/O, or tool effect.

Compaction treats only non-compaction raw rows as source. It applies newest-relative completed-round tail and middle windows backward from the newest round; current/open work remains verbatim normally. Escalation must produce suffix-subset retained windows. Each payload has one ordered non-empty `summaries` array: an optional single leading `merged` group followed by `individual` groups. A group owns ordered round descriptors; each round owns ordered non-empty `initial`/`repair` segments whose `source_message_ids` are the sole persisted covered-source identity. Completeness and one SHA-256 source hash are retained semantic/integrity facts. Round labels, repair anchors, cutoff message/index, and rendered context are derived rather than persisted. Cutoff never retreats. Hard fallback handles only residual oversize and never splits tool pairs, Responses bundles, static units, or an open call.

Each compaction is one strict system message containing canonical JSON. One source-aware validation pass processes physical rows left to right and validates every complete compaction row only against non-compaction source rows physically preceding it. It requires canonical contiguous source order, exact complete or permitted final partial rounds, classifier-derived segment boundaries, matching hashes, eligible retained static rows, and the represented semantic boundary. A later source or valid metadata row cannot legitimize an earlier invalid row. Every provider transport and compaction summarizer consumes one source-identified validated provider conversation projection. Projection selects the physically latest validated compaction, inserts only its derived rendered system context, retains eligible static rows and the uncovered raw suffix, and preserves each eligible uncovered OpenAI Responses private/visible bundle as an exact pair. No physical compaction metadata, older rendered context, or compacted-away source row enters provider or summarizer input.

The strict durable `applied_policy` stores only `mode`, selected `band`, `input_budget_tokens`, `canonical_estimated_static_tokens`, `trigger_fraction`, `completion_reserve_fraction`, the selected band's `merge_line_fraction` and `summary_line_fraction`, and `snap`. Requested completion, hard ceiling, trigger line/threshold, and tail/middle token budgets are exact ephemeral derivations and are not persisted. Source rows retain one visible-message estimate during an attempt, rounds retain one aggregate for partitioning, and each distinct rendered candidate is fit-tested once.

Provider-private rows have exactly zero actor compaction weight; their marked visible projection carries the actor-level conversational weight, and protected bundles remain indivisible. This policy is separate from candidate admission: each protocol candidate builds and canonical-serializes its actual transport body once, so a Responses estimate includes private output bytes present in that exact body. `ceil(UTF8 bytes / 4)` is a deterministic best-effort estimate, not a fit proof. Hashing, admission, retries, and final send reuse that same serialized body without rebuilding it. Prepared autonomous requests omit ordinary `modelParams.maxTokens`; their one prepared `requestedCompletionTokens` controls hard ceiling, candidate context/output admission, model authority, and the Chat and public Responses wire output limits. The Codex backend transport uses it for admission/options authority but intentionally serializes no output-limit field.

Provider input-context evidence is strict and structured. `input_context_exhausted` requires the supported transport's exact direct code/type/param shape: an eligible parsed HTTP 400 error object, a failed public Responses terminal object, or a Codex error/failed event from an opened stream. Matching is case-sensitive; message prose, recursive/nested markers, malformed bodies, status alone, generic token language, and output-limit evidence do not qualify. Responses `incomplete_details.reason: 'max_output_tokens'` is the distinct `output_token_limit_exceeded` failure. An error event from an HTTP response that successfully opened records that actual HTTP status, normally 200; its typed classification does not synthesize status 400. The durable lifecycle `blocker_cause: 'token_budget_exceeded'` is an independent current card-result value and remains unchanged.

After ordinary admission and route-pass ordering, a prepared planner, reviewer, executor, or Analyst logical input may use last-chance recovery. The first route pass must throw authoritative `input_context_exhausted` evidence with only error attempts, null terminal-tool evidence, no accepted completion or assistant output, no persisted tool call for that provider pass, and no entry into completion persistence. That context rejection ends pass one before another candidate. The stable actor consumes its one recovery allowance, forces escalated compaction and then safe hard fallback if needed, and retries one fresh ordinary route pass only when it constructs a strictly smaller projection. A successful forced compaction appends exactly one canonical `context_compaction` row. The retry preserves the logical input/source identity, prompt, tools, prepared budget, temperature, and session, does not append source rows again, and changes only the provider conversation projection. Attempts from both passes are combined chronologically and reindexed under that same input. A second context rejection is terminal: there is no third pass, second forced compaction, or route-by-compaction expansion. Non-context routing and recovery behavior is unchanged.

A clean `no_smaller_projection` result appends no compaction, performs no second provider pass, and produces the ordinary final model-issue/provider-exchange failure for the first rejection. A non-cancelled summary construction failure follows the same normal final-outcome boundary with a safe construction diagnostic. Strict source/candidate validation failures, summary-exchange publication failure, returned projection identity failure, and append failure are fatal local failures: they do not become provider errors and cause no further conversation write or triggering-input exchange projection; append publication may be outcome-unknown and is never inspected or retried. Cancellation remains the exact cancellation outcome with no final model issue; a valid compaction row already appended before cancellation remains canonical. Round and merge summarizer attempts are projected exactly once to the existing app log under their own `summary:<round-id>` or `summary:merge` session and fresh source-input identity, with no assistant output IDs, and are never merged into the triggering persisted input.

For an ordinary Analyst submission, successful preparation precedes one physical `[activation_open marker, workspace context, user text]` append and publication. The session then rereads its canonical conversation once and constructs the sole source-identified provider projection; there is no pending-row concatenation or second projection owner. Preventive compaction runs before the initial provider call and before every continuation whose refreshed canonical projection reaches threshold. A tool continuation first settles the waiting call, appends its one canonical result, allocates a fresh continuation UUID, rereads canonical history, and retains the same prepared prompt/tool/capacity value. The newest Analyst round is open; a following exact marker completes the prior round and makes it eligible for ordinary completed-round bands. Safe hard fallback alone may summarize a classifier-derived safe prefix of residual oversized open work without splitting protected units.

An accepted Analyst tool invocation and its external/domain effect occur before the continuation provider seam. If that continuation receives eligible authoritative context rejection, recovery retries only the same continuation UUID after one strictly reducing compaction: it does not replay or rebroadcast the tool, repeat its result, or append another marker/workspace/user batch. Successful initial output containing a tool call likewise leaves the recovery seam before the tool runs. Direct summarizers are the explicit unprepared, nonpersisting exception; each individual/merge summary uses the one fixed Registry-validated `summarizer_candidate`, fixed 2000-token no-tools prose request, distinct `summary:*` evidence identity, and no self-compaction or replay. Analyst primary and continuation calls continue to use ordinary Analyst role routing and failover.

The operator card representation is current strict card state plus operator actions and the pure card-only summary; it contains no backend `logical_path` or authored content. The hierarchy operation is `GET /api/cards/:id/children`, returning the requested active card and only its active immediate children in committed parent order. Retained tombstone links are read and omitted, and traversal stops there. `GET /api/cards/:id` returns only selected current detail. Card-version history is separate: `GET /api/cards/:id/history` returns redacted embedded `card.jsonl` history headers in strictly descending `version_seq` order with `total` equal to the returned count; `GET /api/cards/:id/history/:seq` returns one embedded entry; and `GET /api/cards/:id/diff` compares two snapshots. Current authored Records are a sixth, separate exact slot resource and do not expose authored revision history through card-history routes.

For target depth `d` with root depth zero, detail, history list, history entry, and diff each prove the committed active path and read exactly `d + 1` card streams, with the target stream read once, and zero authored streams. Hierarchy reads those `d + 1` path streams plus exactly one card stream for each of the target's `C` committed child IDs, including a tombstone stream that is omitted, and zero authored streams. Tool JSON, direct application/read-model, and CardService/domain boundaries likewise reject zero, negative, fractional, non-finite, or unsafe supplied numbers before exact path/history reads. CardStore keeps hierarchy slices, selected detail, and selected history as disjoint authorities: only a children response can install its complete parent slice, and only detail can install selected detail. Completion order never merges them. Each parent key has at most one exact in-flight owner object; same-parent callers share that object's promise. ## 12. Reset And Failure Consequences

Hierarchical card IDs, directory-owned deterministic child claims, the exact two-kind card stream, card records without `position`, complete parent-owned `children` membership/order, immutable card type across every card version, exact card/record/conversation streams, the ordered summary-group compaction payload, minimal `applied_policy`, and strict marker-first/no-preamble Analyst source-round contract are reset-only durable-format cutovers. A successful namespace claim consumes its segment, while only a committed cumulative parent `children` snapshot grants and orders membership. Generated streams containing old `card-child-reservation` rows are unsupported current-format data and fail strict parsing; they are not ignored or compatibility-read. Every deployment unconditionally cuts over by stopping the service, invoking the current built `saivage reset`, and then starting the current binary; no scan or detection of whether old history appears compatible or retained type can exempt a deployment. Old flat UUID cards, version/session directories, generated compaction rows, and pre-marker or mixed Analyst histories are rejected rather than migrated, backfilled, inferred, normalized, or compatibility-rendered. A changed-type card stream encountered outside a valid cutover fails strict validation in place and is never migrated, normalized, or selectively repaired.

Initial publication is separately forbidden whenever any of the four exact generated roots remains without a valid canonical project card. Every exact-path object is an obstruction; Saivage does not inspect whether it is empty, complete, repairable, or directory-shaped. The failure names the first blocking exact path and directs the operator to stop Saivage, run the current built `saivage reset`, and retry. Neither `init` nor `start --create-runtime` repairs, adopts, combines with, or selectively deletes retained state.

Reset first acquires the exact `.saivage/locks/runtime.lock`; every pre-existing exact lock blocks the command before deletion. While retaining its acquired lock, reset recursively force-removes exactly `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work` as whole trees, without probing or enumerating their descendants, then publishes a new canonical `project` root card and releases only its exact lock. Every path outside those four roots is preserved, including configuration, credentials, project identity, operator inputs, source, skills, instructions, and canonical project documentation. Reset never inventories or cleans lock siblings or other noncanonical paths. Incomplete namespaces and publication temps require no action. Malformed exact canonical targets require operator repair or reset.

File persistence provides no no-data-loss guarantee. Interrupted external effects may repeat, notification context may duplicate, process-local availability resets, concurrent auth refresh may overwrite credentials, and orphan files may remain permanently.
