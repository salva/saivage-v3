# Saivage v3 System Specification

This is the canonical functional specification. The current storage and runtime format is reset-only. Mixed-version operation, migration, compatibility reading, and rollback against current generated state are unsupported.

## 1. Product Boundary

Saivage autonomously plans and executes software work represented by cards. It exposes an operator server, Analyst conversation, card/agent/file/debug read models, and process-local runtime controls. The runtime is the only dispatcher.

## 2. Cards

Card identity is exactly the root literal `project` or a canonical lowercase UUID for a non-root card. UUIDs are opaque. API routes, records, sessions, events, process provenance, and UI links preserve the same value; display uses title and hierarchy facts rather than ID parsing.

One non-root creation attempt generates one card UUID, claims its namespace once with non-recursive exclusive directory creation, and reuses that UUID throughout the attempt. Collision or publication failure ends the attempt without retry, scanning, alternate identity, adoption, or reuse. Brief version 1 publishes first and canonical card version 1 last. Each physical publication independently generates its own replacement-temp UUID.

Cards form a strict tree. Project and goal cards are planning cards; architecture, code, test, doc, data, research, and ops are terminal cards. Card statuses are `backlog | changed | running | blocked | done | failed | cancelled`. Running cards form one ancestor chain and only the deepest leaf performs work.

Every card requires ordered `pending_notifications`. Notifications are allowed on backlog, changed, running, and blocked cards. Done, failed, and cancelled cards require an empty list and reject enqueue with `terminal_card`. Unrelated mutations preserve the list; terminal transitions clear it. Reopening a terminal card uses only the supported `setStatus('changed')` transition; no actor callback or lifecycle-repair authority exists. No `next_role`, retry count, reviewer phase, recovery cursor, or autonomous-round counter exists.

Authored `brief.md`, `status.md`, and `review.md` records use strict card-owned versions. A processor owns terminal validation, record closure, accepted tool-result settlement, and executor cleanup; it returns the final selected outcome without writing terminal card lifecycle. `CardActor` then owns the one non-cancellation terminal card publication. Tombstone publication is semantic deletion. A valid non-root tombstone reserves and excludes the UUID and makes retained namespace evidence opaque to active APIs. The root cannot be tombstoned.

## 3. Agent Selection And Sessions

Every nonterminal project/goal activation begins planner. Every nonterminal terminal-card activation begins executor. Reviewer is nested live planner work and is never selected at restart. After accepted reviewer rework closes `review.md` and settles the reviewer terminal result, and before admitting the fresh planner activation, the owner appends exactly one ordinary canonical user-text row to `planner:<card-id>`. That row contains the exact closed review URL and reviewer summary, so ordinary conversation projection supplies both to the fresh activation. This handoff uses no notification, retry counter, or durable reviewer phase. Stale review refresh has no count limit.

Stable session IDs are `planner:<card-id>`, `executor:<card-id>`, and `reviewer:<card-id>`. Each session has one append-only canonical conversation. There are no versions, sidecars, active-session pointers, snapshot cursors, or reconstructed provider/tool continuations.

Every autonomous, Analyst, repair, continuation, individual-summary, and merge-summary invocation receives a fresh opaque UUID source input generated by its owner. That per-call input identity and the invocation owner's session identity are distinct from the stable source-session identity carried by the validated provider conversation projection. Ordinary persisted actor turns require the invocation and source-session identities to be equal. For original source UUID `S` and provider tool-call ID `T`, settlement identities are `${S}:tool-call:${T}` and `${S}:tool-result:${T}`. Success and failure both use `tool_result`; the next invocation UUID is unrelated. Attempt index orders transport attempts only within one invocation.

## 4. Optimistic Interruption Recovery

Startup has no runtime instance. Explicit Run validates the running chain and starts its deepest leaf by card type. Runtime actors, provider callbacks, parent waits, processes, reviewer phase, and lifecycle state are process-local and are not reconstructed.

When a stable session is reused, its owner validates complete rows and latest-round pairing. One unmatched call in an interrupted latest round receives a provider-visible failed tool result stating that external or domain effects may or may not have happened, with `outcome_unknown:true`. The new activation includes a system recovery notice. Multiple unmatched calls, an older unmatched call, or unmatched work in a clean closure fails. Card and record facts never infer interrupted external success.

## 5. Notifications And Reviewer Arbitration

The durable notification target is one `card_id`. Public tools accept `card_id`, `kind`, and `body`; they do not accept role/session recipients and do not report session deliveries.

Planner/executor safe-point delivery is no-await append ordered notification context → remove those exact card IDs → admit provider request. Crash after append and before removal may duplicate context; stable notification IDs expose duplicates.

Immediately before planner/executor terminal acceptance, the owner rereads the card. Empty pending context permits record close and accepted tool-result settlement, followed by processor cleanup/final-outcome selection and then `CardActor` publication. Pending context defeats the candidate: append its paired failed `emit_result`, append ordered notifications, remove those exact IDs, and require another model round.

Reviewer never drains notifications. Before accepting `done`, `blocked`, `failed`, or `rework`, it recomputes semantic currentness then rereads pending context. Pending context wins even when stale: discard open `review.md` first, append the paired reviewer-defer failure second, transition nothing, and return to planner. With no pending context, stale review discards first, appends a failed stale result, appends refreshed context, and retries. Every fresh reviewer activation unconditionally discards an existing open review before its activation marker. A crash after discard but before paired failure is settled only as an ordinary unmatched session call.

Pause does not interrupt these synchronous terminal sections; it blocks the next admission frontier.

## 6. Activation Outcomes And Cancellation

`CardActor` is the sole publisher of every non-cancellation activation outcome (`done`, `blocked`, or `failed`). Processors own role-specific terminal acceptance and return one final outcome only after required record/tool work and, for executors, invocation-surface cleanup. Provider failure, pre-provider failure, malformed provider metadata, processor failure, and cleanup failure all select the same failed outcome path. Cleanup therefore completes before publication and can replace an earlier accepted candidate with the one failed outcome that is durably published.

For a non-cancellation result, the synchronous order is one strict terminal-lifecycle publication → process-local activation finalization and queueing the existing `settled` event → exact natural release from both supervisor ownership maps when the runtime is not closing → deferred activation resolution and caller/parent continuation. Exact release means the actor no longer owns a live activation or runtime projection; it does not wait for the detached micro-actor object to consume the queued cosmetic event. The publication call includes its synchronous mutation callbacks.

If terminal publication throws, whether before replacement or from a later publication callback, canonical visibility is outcome-unknown: REST may later observe either the prior version or the newly canonical terminal version. The actor fails in place. It does not retry, reread, reconcile, make a further lifecycle write, settle the activation caller, or naturally release ownership. A later explicit Stop may contain the process-local winner and aggregate-clear the frozen maps without deciding the durable outcome.

The installed runtime's exact live-card map is the only resolver for running cancellation. If a target or cancellable descendant is live, the request routes to those exact actors. A running card with missing or duplicate live ownership is impossible and fails fast; no direct write fallback exists.

`CardActor` synchronously claims cancellation versus result, closes admission and revokes callbacks, and exposes one exact actor-local cancellation settlement. Cancellation remains a distinct publication authority: that settlement contains activation processes and live descendants, directly publishes cancellation, and settles its caller exactly once. When the runtime is not closing, the supervisor then synchronously verifies the exact actor in both its live-activation map and retained-actor map and removes it from both. Done descendants remain done; inactive cancellable descendants use direct domain cancellation. Late provider, tool, process, child, reviewer, record, notification, and caller callbacks cannot commit after the claim.

Planner cancellation remains limited to an immediate child. Analyst cancellation may reach the runtime port while running/pausing/paused. Direct domain cancellation is for verified nonrunning/stopped work under lifecycle-lock and permission admission.

## 7. Run, Pause, Resume, Stop, And Restart

Runtime status is process-local: stopped when no instance exists, otherwise starting, running, pausing, paused, or closing. Pause sets one request flag. Actors check it before every provider, ordinary tool, process, child, reviewer, or next-round admission. At most one frontier parks; Resume clears and schedules it once.

REST Pause, Resume, and `stop_project` are bodyless operations. Absence is their only accepted request shape; every supplied payload, including `{}` and `null`, receives that route's local 400 validation response before runtime mutation. `restart_server` is the only operation in this group with a request body and accepts exactly the strict JSON object `{confirmation:'RESTART SERVER'}`.

Every Run validates one contiguous project-rooted durable running chain and installs one exact `CardActor` owner per chain card before opening admission. Ancestors enter process-local `structural_wait` on their immediate child and create no role/LLM actor; only the deepest card starts its type-derived planner or executor. After a normal result, `CardActor` publishes its durable terminal outcome, finalizes local activation fields and queues `settled`, and the supervisor synchronously releases that exact actor from both process-local ownership maps before the activation caller settles. Normal child settlement therefore wakes only its immediate parent into a fresh planner activation after publication and release. Any later legitimate activation of the released card constructs a fresh `CardActor` and processor rather than reusing the settled process-local owner.

`stop_project` is non-domain, restartable project containment. Starting/running/pausing/paused synchronously claims closing, globally closes continuation/admission, freezes both complete supervisor ownership maps, and creates one exact `RuntimeStoppedInterruption` plus one Stop-local containment collector. Stop never initiates domain cancellation and never itself writes a card, root result, child ToolResult, provider round, or Stop-caused durable event. Open owners become `claimed_stop`, use aborting revocation, and intentionally preserve durable `running` state. Result winners remain authoritative: Stop non-abortively closes their continuation plus processor-operation and provider-invocation admission, lets already-admitted winner work, cleanup, and publication finish, joins the closed trackers, and suppresses only later continuation. A cancellation that already won remains domain-authoritative, is not aborted or reclaimed, and Stop starts or joins its full actor-local settlement through durable `cancelled` publication and caller settlement. While closing, result and cancellation settlement perform no individual actor release; ownership remains frozen for Stop. Shared tool waits inspect the Stop signal after both fulfillment and rejection and throw the exact `signal.reason`.

After every owner, including every winning cancellation settlement, and runtime-process join, an empty collector atomically clears both frozen ownership maps and the current instance and returns `{status:'stopped',contained:true}`. This aggregate Stop clear is distinct from the supervisor's per-actor exact natural release. Cancellation-settlement, cleanup, or process failure rejects once with `RuntimeContainmentError`, retains both complete closed maps and the closing instance, and makes Run/Pause/Resume/second Stop conflict. With no installed instance Stop returns `{status:'stopped',contained:false}`. A later Run after successful Stop reconstructs ownership over the cards that remain in the running chain and activates only its deepest card.

The App terminal coordinator is separate and deliberately best effort. `App.stop()`, SIGINT/SIGTERM, startup failure, and acknowledged authenticated `restart_server` converge on the sole coordinator in `src/boot/app.ts`; no entry or cleanup leaf calls `stopProject`, cancellation, or the strict Stop collector. It sets application-closing and individually catches every synchronous admission closer before its first await. It then attempts cleanup leaves sequentially in reverse registration order, continuing after rejection or timeout. Exactly one `runtime`, one `analyst`, and one `mcp` component leaf coexist with independent LiveSync, Fastify, Telegram, subscription, and lifecycle-lock leaves.

Each process-owning component leaf closes admission/revokes callbacks and starts exactly one owned-root termination before any await, then awaits that termination with its actor/session/operation joins. A fulfilled `ProcessStopReport` is successful only when `failed` is empty. One shared runner/registry owns disjoint runtime, Analyst, and MCP roots; a timed-out component may continue only in its root while later leaves run, and App runtime termination may overlap project Stop on the runtime root. Repeated signals and already-exited/missing/removal observations are accepted without a global drain, deduplication, shared join, or collector coupling.

`run_command` executes its command as one argument to `bash -c`. A missing or empty cwd and canonical `project:///` select the project root; plain cwd values are project-relative and contained; `project:///...` selects a contained project descendant; and `system:///` or `system:///...` selects the system root or descendant. Malformed scoped URLs, query/fragment cwd values, unknown scoped schemes, and the `record`, `tmp`, and `work` schemes fail before launch. The managed-process registry consumes child `error` events immediately from spawn return, so a handled OS launch failure cannot independently crash the runtime, and it never registers a process group without a positive leader PID.

Every leaf uses the coordinator's referenced ten-second timer, above the managed-process five-second TERM grace plus two-second post-KILL verification. Fast settlement clears the timer; timeout does not cancel or retain the leaf. `App.stop()` resolves an immutable `ShutdownReport` containing only ordered allowlisted `{component, code}` warnings, where code is `closer_failed`, `cleanup_failed`, or `cleanup_timeout`; caught messages, paths, payloads, stacks, and causes are never inspected or exposed. It never logs or changes exit status. Process-owning signal/restart/startup adapters log only fixed component and code fields and preserve ordinary behavior. Public terminal access remains confirmed `restart_server` only with operator authentication; Stop remains available in both auth modes.

Run, Pause, Resume, and Stop produce no lifecycle-control audit entries. Unrelated audits remain.

## 8. Lifecycle Lock And CLI

Lock observation outcomes are missing, verified live, positively verified dead, indeterminate, and malformed. Indeterminate includes permission denial, unavailable process-start identity, and observation races. No outcome authorizes automatic lock deletion or takeover.

CLI status, pause, resume, stop, and restart use only a verified live record's published non-null control endpoint and auth mode. Null fails exactly `active lifecycle owner; runtime control unavailable`; it never implies a lifecycle phase. The shared client never reads current YAML, host/port flags, host/port environment, defaults, runtime files, or current process config to select authority.

- missing/dead status succeeds with stopped/no-current-card;
- missing/dead stop succeeds with `contained:false`;
- missing/dead pause/resume fails because no live runtime exists;
- dead additionally reports abandoned-lock manual repair;
- indeterminate/malformed fails closed;
- delegation, authentication, response, and schema failure never falls back.

Published disabled auth omits Authorization. Published bearer requires nonempty `SAIVAGE_API_TOKEN` and sends it only as a header. CLI `stop` delegates to REST operation `stop_project`; there is no `stop_project` CLI alias.

## 9. Direct File Persistence

Saivage durable state uses direct synchronous named file functions. `CardService` rereads current facts and invokes card/record functions; disposable indexes do not authorize later writes. Conversation and app-log owners append strict envelopes directly. Config, identity, and auth-profile owners read and replace one canonical file. Candidate availability is process-local only. There are no repositories, generic stores, persistence-health latch, runtime-state file, actor snapshots, recovery diagnostics, queues, writer registries, transactions, or repair orchestrators.

Replacement and first publication use one fresh random UUID same-directory temp opened exactly once with `O_CREAT | O_EXCL | O_WRONLY`, then write/fsync/rename/parent-fsync. Collisions and failures propagate without retry or cleanup. Crash-left noncanonical files and incomplete card namespaces are silently ignored forever. Canonical discovery probes tombstone first and then exact card artifacts; complete malformed canonical state fails.

All creation uses ordinary Node defaults under process umask with no mode arguments, chmod, mode probing, or repair. Canonical growing JSONL may truncate only an identifiable unterminated final suffix. Complete malformed envelopes remain and fail.

Auth profile refresh uses strict direct reads and optimistic whole-file replacement. The original invocation signal is checked after response/body awaits and immediately before the synchronous latest-file reread and replacement. Concurrent refresh is last-completed-write-wins with accepted credential-loss risk and no revision, CAS, lock, or merge.

## 10. Progressive Compaction

Compaction is mandatory for a bootable server. Configuration requires literal `enabled: true`, a positive route-independent `input_budget_tokens`, and a strict structured `summarizer_candidate` with exact non-empty `provider` and `model` plus required nullable `account`. Omission, false, incomplete or malformed fields, and a candidate not emitted by the configured Provider Registry fail startup. `account: null` is the implicit provider account; explicit `_implicit` and `_` are exact distinct names, and slash-bearing model IDs are preserved without parsing. Registry membership is exact and has no role routing, equivalent, failover, credential probe, or network fallback. `/api/providers` exposes Registry-backed ordered structured availability entries and never uses or leaks an internal implicit-account sentinel.

For each new planner, reviewer, or executor activation, the exact role prompt and ordered tools produce one ephemeral prepared compaction value before stabilization or transcript I/O. Preparation validates budget, fraction ordering, positive derived completion tokens, trigger plus reserve, escalated tail/middle widths no greater than normal, and static-token trigger/hard capacity. Tool-result and plain-text-repair calls retain that exact prompt, tools, and prepared object while refreshing source input ID, context, replay, and episode facts; each refreshed projection is tested against the unchanged threshold. A later activation prepares anew. Application composition retains candidate identity only in the summarizer's fixed one-candidate invocation route; runtime factory/actor policy, prepared policy, compactor arguments, prompts, and episode context are identity-free. Every autonomous `LLMActor` requires prepared input at admission and rejects an unprepared call before transition or persistence.

Compaction treats only non-compaction raw rows as source. It applies newest-relative completed-round tail and middle windows backward from the newest round; current/open work remains verbatim normally. Escalation must produce suffix-subset retained windows. Each payload has one ordered non-empty `summaries` array: an optional single leading `merged` group followed by `individual` groups. A group owns ordered round descriptors; each round owns ordered non-empty `initial`/`repair` segments whose `source_message_ids` are the sole persisted covered-source identity. Completeness and one SHA-256 source hash are retained semantic/integrity facts. Round labels, repair anchors, cutoff message/index, and rendered context are derived rather than persisted. Cutoff never retreats. Hard fallback handles only residual oversize and never splits tool pairs, Responses bundles, static units, or an open call.

Each compaction is one strict system message containing canonical JSON. One source-aware validation pass processes physical rows left to right and validates every complete compaction row only against non-compaction source rows physically preceding it. It requires canonical contiguous source order, exact complete or permitted final partial rounds, classifier-derived segment boundaries, matching hashes, eligible retained static rows, and the represented semantic boundary. A later source or valid metadata row cannot legitimize an earlier invalid row. Every provider transport and compaction summarizer consumes one source-identified validated provider conversation projection. Projection selects the physically latest validated compaction, inserts only its derived rendered system context, retains eligible static rows and the uncovered raw suffix, and preserves each eligible uncovered OpenAI Responses private/visible bundle as an exact pair. No physical compaction metadata, older rendered context, or compacted-away source row enters provider or summarizer input.

The strict durable `applied_policy` stores only `mode`, selected `band`, `input_budget_tokens`, `canonical_estimated_static_tokens`, `trigger_fraction`, `completion_reserve_fraction`, the selected band's `merge_line_fraction` and `summary_line_fraction`, and `snap`. Requested completion, hard ceiling, trigger line/threshold, and tail/middle token budgets are exact ephemeral derivations and are not persisted. Source rows retain one visible-message estimate during an attempt, rounds retain one aggregate for partitioning, and each distinct rendered candidate is fit-tested once.

Provider-private rows have exactly zero actor compaction weight; their marked visible projection carries the actor-level conversational weight, and protected bundles remain indivisible. This policy is separate from candidate admission: each protocol candidate builds and canonical-serializes its actual transport body once, so a Responses estimate includes private output bytes present in that exact body. `ceil(UTF8 bytes / 4)` is a deterministic best-effort estimate, not a fit proof. Hashing, admission, retries, and final send reuse that same serialized body without rebuilding it. Provider rejection remains authoritative and does not trigger candidate-specific recompaction. Prepared autonomous requests omit ordinary `modelParams.maxTokens`; their one prepared `requestedCompletionTokens` controls hard ceiling, candidate context/output admission, model authority, and the Chat and public Responses wire output limits. The Codex backend transport uses it for admission/options authority but intentionally serializes no output-limit field. Analyst and compaction summarizer requests have no prepared compaction and use only ordinary `modelParams.maxTokens`; summarizers retain `2000`.

This preventive guarantee covers autonomous project-runtime planner, reviewer, and executor activations. Analyst remains on ordinary `ConversationLLMActor` input: one operator submission may make multiple distinct tool continuations without prepared compaction and may exhaust context. Analyst continuation compaction is deferred and no universal conversation-boundedness claim is made.

## 11. API And Operator Projection

REST is authoritative; WebSocket supplies lossy freshness hints that cause clients to refetch REST. Runtime, card, and agent facts come from their separate REST owners; debug routes are distinct diagnostic projections, not a combined runtime/card state aggregate. The web client has one canonical owner for each separate runtime, card, and agent resource family; initial bootstrap and token changes read those owners directly, and live hints refetch those same owners rather than route-local or Debug copies. Direct mutation owners publish synchronously after successful projected mutations: `CardService` does so for the complete runtime-index mutation set of create, delete, and actual pruned changes to `status` and/or `type`; runtime owners do so for lifecycle/run-identity boundaries, active-leaf changes, every retained card or agent membership mutation, and autonomous-agent public phase changes. A mutation that remains visible when a later synchronous operation throws must already have published its hint. Non-index card edits do not require runtime invalidation, and successful no-ops or failed mutations publish none. `ActiveCardLeaf` is the sole current-card authority, and `SyncHub` is the only debounce/coalescing boundary; hints add no delivery, replay, or acknowledgement guarantee. Cards expose pending notifications and opaque IDs, not role/retry/recovery fields. Runtime and readiness responses expose process-local runtime state and no persistence-health, runtime-file, snapshot, or recovery component; diagnostic projections add no persistence-health authority. Provider routing labels availability `process_local_reset_on_restart`.

The Files read model accepts canonical `work:///` as the listable `.saivage/work` root and returns canonical `work:///...` child paths. Content reads of `work:///` reject it as a directory, and process-log fields continue to require concrete canonical log URLs.

The UI displays title/hierarchy labels and preserves UUID links. It exposes Stop project with contained/no-op/conflict results. Restart server appears only when required `restart_server_available` is true and requires confirmation. No UI action optimistically writes a running card cancelled. Raw conversations preserve canonical compaction JSON while rendered views show one synthetic system context.

## 12. Reset And Failure Consequences

The ordered summary-group compaction payload and minimal `applied_policy` are reset-only durable-format cutovers. Operators cut over by stopping the service, invoking the current built `saivage reset`, and then starting the current binary. Old generated compaction rows, including rows containing superseded derived policy fields, are rejected rather than migrated, normalized, or compatibility-rendered. Reset first acquires the exact `.saivage/locks/runtime.lock`; every pre-existing exact lock blocks the command before deletion. While retaining its acquired lock, reset recursively force-removes exactly `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work` as whole trees, without probing or enumerating their descendants, then publishes a new canonical `project` root card and releases only its exact lock. Every path outside those four roots is preserved, including configuration, credentials, project identity, operator inputs, source, skills, instructions, and canonical project documentation. Reset never inventories or cleans lock siblings or other noncanonical paths. Incomplete namespaces and publication temps require no action. Malformed exact canonical targets require operator repair or reset.

File persistence provides no no-data-loss guarantee. Interrupted external effects may repeat, notification context may duplicate, process-local availability resets, concurrent auth refresh may overwrite credentials, and orphan files may remain permanently.
