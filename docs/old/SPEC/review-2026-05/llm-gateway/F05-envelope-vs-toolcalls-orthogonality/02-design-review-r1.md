# F05 — Design review r1

1. Terminal result tools are not made exclusive, so Proposal L can still lose action tool calls or accept ambiguous results.

   What is wrong: the recommended design adds `emit_<role>_result` to the same `tools[]` catalog as normal action tools and keeps `tool_choice: 'auto'`. The adapter pseudocode then accepts the first terminal tool call it finds and immediately returns the envelope. That is not a sound terminal protocol when providers can return multiple tool calls in one assistant turn. If an assistant turn contains both `create_card` and `emit_planner_result`, or two terminal result calls, the design either drops side-effecting work or accepts an ambiguous final result. This misses the approved A.1 requirement that the result be a terminal action with exactly one result carrier.

   Evidence: the approved analysis says the A.1 result tool must be called as the terminal action and that observability is unambiguous because there is exactly one result tool call ([01-analysis-r2.md#L184](01-analysis-r2.md#L184), [01-analysis-r2.md#L191](01-analysis-r2.md#L191)). Proposal L uses `tool_choice: 'auto'` ([02-design-r1.md#L336](02-design-r1.md#L336)) and describes chat/Codex responses as `tools[]` with `emit_<role>_result` beside the action tools ([02-design-r1.md#L377-L378](02-design-r1.md#L377-L378)). The adapter pseudocode looks for a terminal call with `find(...)` and returns it before executing the rest of `result.calls` ([02-design-r1.md#L388-L401](02-design-r1.md#L388-L401)). Current provider parsing already returns arrays of tool calls, not a singleton: OpenAI chat builds `toolCalls: ToolCall[]` and returns it ([../../../../src/agents/llm-stream-parser.ts#L100-L113](../../../../src/agents/llm-stream-parser.ts#L100-L113)); Codex accumulates an array and sets `finishReason = 'tool_calls'` when any exist ([../../../../src/agents/llm-codex-parser.ts#L12-L36](../../../../src/agents/llm-codex-parser.ts#L12-L36)). The current Codex request builder also enables `parallel_tool_calls` when tools are present ([../../../../src/agents/llm-openai-codex-gateway.ts#L119-L123](../../../../src/agents/llm-openai-codex-gateway.ts#L119-L123)).

   Required change: define the terminal-result protocol as an explicit invariant. Either make result emission a separate forced terminal turn/tool choice, or keep the single-loop design but require `emit_<role>_result` to be the only tool call in that assistant message, exactly once, with no sibling action tools; reject duplicates, terminal-plus-action mixtures, terminal calls for the wrong role, and prose-only terminal attempts with `LlmContractMismatchError`. For Codex, specify whether `parallel_tool_calls` is disabled for role-result turns or whether any parallel terminal/action mixture is rejected. Add tests for action+terminal, duplicate terminal, wrong terminal tool, terminal after max-turn exhaustion, and prose-only responses.

2. The per-provider wire shape overclaims that tool-call arguments are already typed JSON.

   What is wrong: Proposal L's recommendation says the envelope is delivered as a typed object end-to-end and that the wire spec guarantees the tool-call `arguments` field is valid JSON. That is too strong for both supported transports. In the current code, both OpenAI chat and Codex parsers expose `function.arguments` as a string assembled from wire deltas/events; malformed JSON, partial JSON, and schema-invalid JSON are still real provider results and must be first-class contract mismatches. The design contains some invalid-argument tests, but the recommendation text and wire-shape rationale are unsound as written.

   Evidence: the approved analysis requires typed handling for "tool-call-with-unexpected-arguments" failures ([01-analysis-r2.md#L254](01-analysis-r2.md#L254)). Proposal L claims the wire spec guarantees valid JSON and that prose-around-envelope regressions are impossible by absence ([02-design-r1.md#L526](02-design-r1.md#L526)). Current OpenAI chat streaming concatenates argument fragments into `acc.arguments` and returns them as `function.arguments` strings ([../../../../src/agents/llm-stream-parser.ts#L86-L113](../../../../src/agents/llm-stream-parser.ts#L86-L113)). Current Codex parsing returns `function.arguments` from event strings and defaults to `'{}'` when absent ([../../../../src/agents/llm-codex-parser.ts#L85-L134](../../../../src/agents/llm-codex-parser.ts#L85-L134)).

   Required change: describe the result tool arguments as raw JSON text until Saivage parses and validates them. Add a single parse/validate boundary that converts `ToolCall.function.arguments` into the role envelope with strict `JSON.parse + Zod`, emits `LlmContractMismatchError` with schema issues and a redacted/raw preview, and preserves the raw assistant text/arguments for forensics. Update the provider matrix and recommendation text so correctness does not rely on provider guarantees that are not actually present.

3. The persisted tool-call row migration is incomplete; too many real readers and writers of the old `{toolCalls:[...]}` wrapper are not named.

   What is wrong: the design correctly rejects backward compatibility and changes assistant `tool_call` rows from `JSON.stringify({ toolCalls: [...] })` to a single serialized `ToolCall`, but the migration plan is not concrete enough to prevent dead old-shape code from surviving. It mentions the gateway readers, a generic persistence reader, the web session viewer, and the LLM-exchange viewer, but current code has several additional producers/consumers that parse or write the old wrapper directly. Leaving any of them behind violates invariant 9 and would either reintroduce a shim or break runtime/session behavior.

   Evidence: invariant 9 says no on-disk session row may keep the old `{toolCalls:[...]}` shape and old rows must be rejected rather than bridged ([01-analysis-r2.md#L256](01-analysis-r2.md#L256)). The design changes row shape and says old rows are rejected ([02-design-r1.md#L270-L280](02-design-r1.md#L270-L280), [02-design-r1.md#L432-L437](02-design-r1.md#L432-L437)), but the implementation order only says to update "persistence reader", "web UI session viewer", and "LLM-exchange viewer" ([02-design-r1.md#L546](02-design-r1.md#L546)). Current direct old-wrapper consumers include `session-persistence.ts`'s private `parseToolCalls` used by unresolved `activate_card` lookup ([../../../../src/agents/session-persistence.ts#L379-L420](../../../../src/agents/session-persistence.ts#L379-L420)), runtime activation scanning ([../../../../src/runtime/runtime.ts#L235-L264](../../../../src/runtime/runtime.ts#L235-L264)), analyst history trimming and persistence ([../../../../src/agents/analyst-handler.ts#L70-L106](../../../../src/agents/analyst-handler.ts#L70-L106), [../../../../src/agents/analyst-handler.ts#L286-L300](../../../../src/agents/analyst-handler.ts#L286-L300)), the web tool presenter parser ([../../../../web/src/utils/tool-presenters/helpers.ts#L68-L78](../../../../web/src/utils/tool-presenters/helpers.ts#L68-L78)), and analyst chat pending-tool matching ([../../../../web/src/stores/analystChat.ts#L99-L108](../../../../web/src/stores/analystChat.ts#L99-L108)). The search surface also includes fixtures/tests and `fake-agent.ts` producers that still serialize `{ toolCalls: [...] }`.

   Required change: add an explicit migration inventory for every old-wrapper reader/writer and replace them with one canonical `serializeToolCallMessage` / `parseToolCallMessage` (or equivalent) that accepts only the new single-`ToolCall` shape and rejects the old wrapper with `LegacyMessageShapeError`. The plan must name and migrate at least `agent-adapter`, `analyst-handler`, `fake-agent`, `llm-openai-chat-gateway`, `llm-openai-codex-gateway`, `session-persistence`, `runtime`, web tool presenters, analyst chat matching, and all tests/fixtures that currently assert the wrapper.

4. The `terminalTool` observability design is ambiguous and not tied to the real schemas.

   What is wrong: Proposal L says the event recorder gains a per-call `terminalTool` field, while the test plan says `invocation_succeeded` includes `terminalTool`. Those are different surfaces in this codebase. The LLM exchange recorder writes `LlmExchange` records; `invocation_succeeded` is an event-log/bus payload. The design must choose the exact schema location(s) and update the server/web contracts, otherwise the UI and API either cannot rely on the field or the change lands as untyped passthrough noise.

   Evidence: Proposal L puts `terminalTool` on the event recorder / LLM-exchange viewer ([02-design-r1.md#L435](02-design-r1.md#L435)) and then snapshots it on `invocation_succeeded` ([02-design-r1.md#L467](02-design-r1.md#L467)). Current `llmExchangeSchema` contains `sessionId`, `capturedAt`, `transport`, `candidate`, and `attempts`; there is no per-attempt or per-exchange `terminalTool` field ([../../../../src/contracts/llm-exchange.ts#L23-L40](../../../../src/contracts/llm-exchange.ts#L23-L40)). Current `invocation_succeeded` declares only `session_id`, `role`, `attempt`, and `duration_ms` as its typed payload fields ([../../../../src/schemas/event-catalog.ts#L49-L51](../../../../src/schemas/event-catalog.ts#L49-L51)). The web API re-exports the LLM exchange contract directly ([../../../../web/src/api/contracts.ts#L80-L95](../../../../web/src/api/contracts.ts#L80-L95)), so contract drift will surface in the operator UI.

   Required change: specify whether `terminalTool` belongs on `LlmExchange` attempts, agent invocation events, session messages, or more than one of those. Then list the exact schema/type/test updates: `src/contracts/llm-exchange.ts`, `src/schemas/event-catalog.ts` and generated/consumer types, operator API contracts, web API types/stores/viewer, and the LLM-exchange/event-log tests. Do not rely on passthrough fields for a new architectural observability contract.

5. The test plan does not yet satisfy the approved matrix-and-consumer invariant.

   What is wrong: Proposal L's tests are mostly gateway-family tests plus one manual live probe. That is not enough for the approved invariant, which says the provider matrix is the test plan and every direct consumer must be covered. Under Proposal L, the matrix can be simpler, but it still needs parameterized assertions for every configured provider key and it needs regression tests for every consumer whose public type or persisted row shape changes.

   Evidence: invariant 10 requires a test for each provider entry and each mode, plus direct consumer tests for the adapter and analyst paths ([01-analysis-r2.md#L258-L260](01-analysis-r2.md#L258-L260)). Proposal L's unit plan covers `OpenAIChatGateway`, `OpenAICodexGateway`, `assertCandidateCapabilities`, and recovery policy, and leaves the provider-by-provider check to a manual live probe ([02-design-r1.md#L459-L470](02-design-r1.md#L459-L470)). Current tests still assert the old result shape and wrapper in many places, including `result-parser.test.ts`, `llm-client-integration.test.ts`, `agent-tool-executor.test.ts`, `agent-runtime.test.ts`, `codex-deferred-activate-card.test.ts`, `session-persistence.test.ts`, and web tests that hard-code `{ toolCalls: [...] }` rows.

   Required change: make the test plan matrix-driven and implementation-blocking, not mostly manual. Add parameterized unit tests for `opencode`, `opencode-go`, `github-copilot`, `nvidia-nim`/DeepSeek, and `openai-codex` request construction/capability selection under the recommended tools-only contract. Add direct consumer tests for `AgentAdapter.invokeAgent`, `LlmIntentResolver.chat` plus `analyst-handler`, session-persistence/runtime activation lookup, the provider stream parsers, web tool presenters/timeline, LLM exchange/event schemas, and removal of old `result-parser` tests. The live probe can remain as an opt-in supplement, not the only provider-matrix coverage.
