# F03 - Conversation rounds analysis r1 review

Reviewed against [F03-conversation-rounds.md](../F03-conversation-rounds.md), [00-SUBSYSTEM-MAP.md](../00-SUBSYSTEM-MAP.md), approved [F02 r2](../F02-component-hierarchy/01-analysis-r2.md), approved [F05 r2](../F05-tool-detail-rendering/01-analysis-r2.md), v2 split source under [saivage/web/src/components/agents](../../../../../saivage/web/src/components/agents), v2 formatter [saivage/web/src/utils/toolFormatters.ts](../../../../../saivage/web/src/utils/toolFormatters.ts), and current v3 files [web/src/components/agents/AgentConversationView.vue](../../../../web/src/components/agents/AgentConversationView.vue), [web/src/stores/agents.ts](../../../../web/src/stores/agents.ts), [web/src/api/types.ts](../../../../web/src/api/types.ts), and [src/server/routes/runtime-config-notes.ts](../../../../src/server/routes/runtime-config-notes.ts).

## Assessment

r1 correctly identifies the core v2 behavior: round bucketing, the five-valued `ToolPairStatus` (`pending | ok | error | orphan | missing`), diagnostic item promotion, compacted clusters, ambient model labeling, pending-call footer, expansion keys, and scroll stickiness. The route-level wire claim is also correct: the current v3 conversation route reads JSONL records and returns `{ session, messages }` verbatim, while the current v3 `AgentMessage` type/schema lacks `round_id`, `message_index`, `block_index`, `model_spec`, `requested_model_spec`, and `activity_status`.

I cannot approve r1 yet. The draft is close on behavior, but it diverges from approved F02/F05 architecture, leaves compatibility shims in the plan, and does not specify enough backend detail for the wire contract to be implementable without guesswork.

## Required Changes

1. Align the component locations and names with approved F02. r1 puts `AgentRoundCard`, `ToolChip`, `DiagnosticRow`, `CompactedCluster`, `PendingCallFooter`, `ContextBlock`, `FormattedContent`, and the timeline types under agent-local paths such as `web/src/components/agents/*`. F02 r2 established the shared layers as `components/ui/`, `components/content/`, and `components/conversation/`, with conversation composites such as `RoundCard`, `ToolChip`, `DiagnosticRow`, `PendingCallFooter`, and `CompactedCluster` living in `components/conversation/`. Revise F03 so `AgentConversationView.vue` is only the store/surface container, shared renderers live in the F02-approved folders, and pure non-SFC logic is clearly separated from those render components.

2. Replace the r1 `ToolChip`/formatter proposal with the approved F05 contract. r1 still proposes porting v2 `formatToolPair`, a v3-side `toolFormatters.ts`, v2-style `FormattedToolPair`, `InlinePart` roots `project | saivage`, and a button-like row derived from `ToolCallRow.vue`. F05 r2 explicitly dropped that layer: `presentToolCall` and `presentToolResult` are independent, `InlinePart` is exported from `tool-presenters.ts` with `file.root: 'meta' | 'output'`, text tones use `danger` rather than v2 `error`, and chip markup is a non-button `role="group"` with one dedicated expand button plus sibling file/url links. F03 must express how a five-status `ToolPair` surface composes those F05 call/result presentations without reintroducing `formatToolPair` or nested-interactive chip markup.

3. Remove the compatibility adapter language from the wire plan. r1 says `AgentConversationResponse` is replaced with `entries`, but then proposes an API-client boundary that translates current wire `messages` into `entries` until the backend ships canonical camelCase/entries. That is a backward-compat shim. Per the project rule, F03 should require the backend route, API type, store, and component to move to one canonical response shape in the same change: `{ session, entries, activity_status }`. The flat `steps` machinery should be removed outright, not aliased, and the store should not retain `messages`, `steps`, or a `messages -> entries` fallback path.

4. Correct the `tool_call_id` gap analysis. The type has optional `tool_call_id`, but current v3 planner/executor/reviewer tool-call records are appended without that scalar field; `agent-adapter` persists each `tool_call` with `content: JSON.stringify({ toolCalls: [tc] })` and `tool`, while only result/error records carry `tool_call_id`. The analysis must call this out as a concrete backend delta: every `tool_call`, `tool_result`, and `tool_error` record must carry the same scalar `tool_call_id` so `toolUseId` is available without parsing the JSON payload in the UI. This also needs to be reflected in schemas and tests.

5. Specify the backend round-stamping contract instead of declaring derivation out of scope. The statement that runtime/adapter code is responsible for choosing `rK`, `r-msg:N`, `r-pre`, and `r-compacted-N` is directionally right but not implementable. The revised analysis must define where counters live, which append path stamps each field, how `message_index` and `block_index` are incremented, how context messages and compaction summaries are assigned, and how diagnostics attach to the current round versus standalone buckets. This should include schema updates in both `src/schemas/types.ts` and `src/schemas/validators.ts`, plus persistence writer updates for `session-persistence.ts` and the analyst append path if it remains in scope for the shared message type.

6. Make `activity_status` complete and non-optional for F03 completion. r1 describes the pending footer as required, then says `activity_status` may be deferred and the UI can omit the footer when missing. That fails the issue's completeness bar. It is acceptable for `activity_status.pending_call` to be `null` when no call is pending, but the response contract itself should exist in F03. The revised analysis must identify the authoritative source of pending state precisely. Current code exposes retry attempts and delay decisions through `agent-adapter`/recovery policy events, not through `llm-transport.ts`; there is no existing `retry_at` store. Define whether an `ActiveRuntime` method, an agent activity store, or event-bus maintained state owns `started_at`, `status`, `attempt`, `reason`, `retry_at`, and `last_activity_at`, and how the conversation route reads it.

7. Reconcile WS and polling without inventing an extra protocol. The non-goal of no streaming redesign is good, but r1's `activity_status` WS discussion is still vague. State the exact payload widening for existing `thinking`/`activity` envelopes if piggybacking is selected, how the Pinia store updates `activityStatus`, and how REST polling deduplicates by `entry.id`. Do not leave a new `agent-activity-status` event as an equally viable option unless the revised design explicitly rejects it with reasons.

8. Expand the test plan into explicit v3 cases. Referencing the v2 tests "as-is" is not enough because those tests do not cover every behavior this issue now depends on. List concrete tests for `entriesToTimeline()` and `parseRoundId()` covering: empty input, assistant round, `r-pre`/`r-msg:N`/`rK`/`r-compacted-N` sort ties, leading-zero round ids, malformed bucket drops, matched pairs, duplicate call overwrite, orphan result, missing result, pending upgrade, tool error, missing `toolUseId` warning/drop, context-only item, diagnostic-only promotion, compacted cluster item, model spec lift, and stable ids/keys. Separately list composable/store tests for pending-round derivation, default model selection, expansion key reset on agent switch, expand-all/collapse-all over timeline items, scroll stickiness, and REST/WS dedupe.

9. Remove the AnalystChatPanel contradiction. r1 says `ToolChip` is reusable by F04, but its non-goals say no analyst-chat changes. F02/F05 both require `AnalystChatPanel` to consume the same shared `ToolChip`/presenter contract. F03 should not create an agent-only chip implementation. Either include the AnalystChatPanel consumer update as part of the shared chip extraction, or state a strict dependency/order that prevents two divergent chip renderers from existing after F03/F05 land.

10. Add the required alternative analysis: backend-driven structured timeline versus view-side bucketing. The revised document should compare a server response that returns rounds directly against keeping the server response as canonical flat `entries` plus metadata and using a pure UI `entriesToTimeline()` utility. It should select one path and reject the other with concrete reasons. A plausible choice is view-side bucketing: it preserves v2's tested pure algorithm, keeps the server contract presentation-neutral, and still requires the backend to stamp canonical metadata. But r2 must make that argument explicitly.

11. Tighten scope around content renderers and tool details. F03 can depend on F05's `FormattedContent`, `JsonView`, `InlineParts`, and presenter work, but it should not independently port a 692-line v2 formatter or redefine content-rendering primitives. Keep the F03 analysis focused on timeline assembly, round rendering, state plumbing, and backend metadata needed to make those renderers usable.

VERDICT: CHANGES_REQUESTED
