# F22 — Analysis Review r1

## Analysis

The main root-cause diagnosis is verified by code. [src/boot/app.ts](../../../src/boot/app.ts#L16-L19) calls `loadEnvironment` synchronously before server startup, [src/config/environment.ts](../../../src/config/environment.ts#L177-L227) reads and validates the config synchronously and returns a deeply frozen `Environment`, [src/server/server.ts](../../../src/server/server.ts#L108) passes that already-parsed config into `ActiveRuntime`, [src/runtime/active-runtime.ts](../../../src/runtime/active-runtime.ts#L45-L70) stores it before constructing `AgentAdapter`, and [src/agents/agent-adapter.ts](../../../src/agents/agent-adapter.ts#L173-L178) passes the same config into `ModelRouter`. The matching runtime error comes from [src/agents/config-schema.ts](../../../src/agents/config-schema.ts#L399-L427), and `models = {}` is accepted because [src/agents/config-schema.ts](../../../src/agents/config-schema.ts#L62-L117) makes every model role optional while [src/agents/config-schema.ts](../../../src/agents/config-schema.ts#L228-L237) defaults `models` to `{}`. So the writer is right: this is not a boot-order race.

One analysis sentence needs correction before approval: the explanation that an operator may have written `models.planner` to `saivage.json` between the first and second cycle and "then the resolver started returning it" is impossible in the same process. Because [src/config/environment.ts](../../../src/config/environment.ts#L228) freezes the environment and no reload path is present, a disk edit alone cannot change the `ModelRouter` input; success after failure requires a restarted/new process, a different project/config, or some external evidence not currently documented. The document later says this correctly, so r2 should remove the contradictory earlier explanation.

The four-role validation target is acceptable as the current runtime contract: [src/agents/agent-adapter.ts](../../../src/agents/agent-adapter.ts#L40) defines `AgentRole` as `planner | executor | reviewer | analyst`, while the model schema accepts additional role-shaped keys that are not the current `ModelRouter` dispatch contract. The 15-role discrepancy is usefully flagged, but it is only partly actionable. Since Zod strips unknown `models` keys before the proposed parsed-config diagnostic can see them, r2 should either add a concrete follow-up to audit/reject unknown raw model-role keys or explicitly state that this finding only validates the recognized runtime roles and does not prove the operator/dashboard 15-role surface is correct.

## Design

Design A is justified over B. The audited chain already orders config load before runtime construction, so a `configReady` promise would add machinery without fixing a config that validates as empty. Fail-fast role completeness is the right architectural move for the workspace guidance.

The design and plan currently disagree on the core fail-fast behavior. The design promises an `EnvironmentLoadError`-equivalent boot refusal, systemd unit failure, and no started runtime. But the plan inserts validation inside `ActiveRuntime.open` and then says the existing [src/server/server.ts](../../../src/server/server.ts#L108) catch path can handle it as `runtimeStartupFailure` while the API keeps running. That is degraded availability, not fail-fast boot refusal, and it will not satisfy the live-probe expectation that `saivage-v3-getrich.service` enters `failed`. r2 must choose and specify one concrete path: validate during environment/config loading before `startServer`, or have `createServer` rethrow model-role precondition failures when `createRuntime` is requested.

The dead-code/invariant story is directionally fine: after boot validation, the resolver throw remains a guard for bypasses or future unknown-role calls. However, do not add a new invariant comment unless the implementation truly needs it; the guideline is to avoid new docstrings/comments in untouched code, and the invariant can be carried by tests plus the F22 design docs.

## Plan

The integration coverage is not strong enough for the stated design. `await ActiveRuntime.open(projectRoot, config)` rejecting proves early runtime construction rejects, but it does not prove server boot rejects, systemd fails, or `/api/runtime/status` is unreachable. Add a server/startApp-level integration test that exercises the same path [src/boot/app.ts](../../../src/boot/app.ts#L16-L19) and [src/server/server.ts](../../../src/server/server.ts#L108) use, and assert the selected fail-fast behavior. If r2 intentionally keeps degraded API availability, the design and live probe must stop claiming systemd failure.

The proposed unit-test shape has two contradictions. Test case 3 expects `configuredRoles` for an `{ ok: true }` result, but the proposed `ValidateModelRolesResult` type only returns `{ ok: true }`; either include `configuredRoles` in success results or remove that expectation. Also, Step 3 says to keep [tests/agents/config-schema.test.ts](../../../tests/agents/config-schema.test.ts#L348) unchanged while Step 5 changes the resolver throw message to `Internal invariant violated: ...`; that test currently expects `/No model list configured/`, so r2 must either keep the message unchanged or update the test deliberately.

Validation commands mostly use package scripts, which is good, but `npm run test:direct` should name the new focused tests before any broader gate, for example `npm run test:direct -- tests/config/validate-model-roles.test.ts tests/runtime/boot-missing-role.test.ts`. The live LXC target and service are correct for this issue (`10.0.3.170`, `saivage-v3-getrich.service`), but the recipe should follow the skill: prefer `ssh root@10.0.3.170 'systemctl restart ... && systemctl is-active ...'` and reserve `sudo lxc-attach` for fallback. Drop the background `tail -f` and `sleep 5` recipe; use bounded `journalctl`, line-count snapshots, and health/status probes so the validation is repeatable and non-interactive.
