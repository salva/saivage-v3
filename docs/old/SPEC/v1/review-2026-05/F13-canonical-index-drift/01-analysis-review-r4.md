## Analysis review

1. The pre-mutation `version_seq` contract is fixed for the ordinary mutation kinds, but the new `create` row is internally inconsistent and would make either schema validation, boot, or public reads fail. [01-analysis-r4.md](01-analysis-r4.md#L43) defines a visible `create` history row at `version_seq = 0`, with `status: 'placeholder'`, `history/<seq>=0`, and `diff?from=0&to=1`. That conflicts with the same document's contiguous-history invariant of rows `{1, ..., V - 1}` for current card `V` in [01-analysis-r4.md](01-analysis-r4.md#L30), and with the boot invariant in [02-design-r4.md](02-design-r4.md#L49-L50), which rejects any row for `V === 1` and rejects any `version_seq < 1`. It also conflicts with the current schema and route contracts: `cardRecordSchema` and `cardHistoryEntrySchema` require positive `version_seq` and valid card statuses in [src/schemas/validators.ts](../../../src/schemas/validators.ts#L22-L23), `cards.history.get` rejects `seq <= 0` in [src/server/routes/operator-contracts.ts](../../../src/server/routes/operator-contracts.ts#L128), `cards.diff` rejects `from <= 0` in [src/server/routes/operator-contracts.ts](../../../src/server/routes/operator-contracts.ts#L140), and `CardDiffResponseSchema` requires positive `from` / `to` in [src/contracts/operator-api.ts](../../../src/contracts/operator-api.ts#L158). Required change: choose one create model and propagate it everywhere. If `create` really has a visible seq-0 tombstone, make the history schema, route params, diff response, startup invariant, and tests explicitly allow seq 0 and a parseable tombstone shape. If seq 0 is not meant to be public, remove the visible create row from the table and adjust the "every state-changing call" / mutation-surface language accordingly.

2. The other r3 analysis asks are addressed well enough: the schema fanout includes backend contracts, agent tools, and web types; deleted-card history visibility is specified; JSONL truncation is loud; `transitionCard` is async; and the dead `canonicalHealth` surface is slated for deletion. No further analysis blocker there once the create semantics above are repaired.

## Design review

1. The lock model is still not mechanically implementable against the current `ProjectLock` API. The design says mutations call `await projectLock.acquire()` in [02-design-r4.md](02-design-r4.md#L21), and the plan later uses `ProjectLock.create(projectRoot)` plus `projectLock.release()` in [03-plan-r4.md](03-plan-r4.md#L79) and [03-plan-r4.md](03-plan-r4.md#L228). The source API is `new ProjectLock(lockPath)`, `withLockSync`, `withLock`, and `assertOwns` only; see [src/persistence/project-lock.ts](../../../src/persistence/project-lock.ts#L28), [src/persistence/project-lock.ts](../../../src/persistence/project-lock.ts#L33), [src/persistence/project-lock.ts](../../../src/persistence/project-lock.ts#L64), and [src/persistence/project-lock.ts](../../../src/persistence/project-lock.ts#L111). Required change: either add and plan the new `create` / `acquire` / `release` API explicitly, or express `applyMutation` in terms of `projectMutex.lock()` around `projectLock.withLock(async (handle) => { ... })`, passing the `LockHandle` to persistence code that needs ownership checks.

2. The plan's lock-release snippet releases the in-process mutex before the cross-process lock in [03-plan-r4.md](03-plan-r4.md#L223-L228), while the design says release the project lock first and then the mutex. That ordering matters: releasing the mutex first allows another same-process mutation into the critical section while the first process still owns the cross-process lock. Required change: make the pseudo-code and tests enforce one order, preferably `try { ... } finally { release project lock/handle; release project mutex; }`, with `card_history_appended` emitted only after both are released.

3. JSONL tail repair, group-marker recovery states (a)-(e), multi-card archive survivor rewrites, and event emission with a captured payload outside the lock are now specified at the right level. Those portions satisfy the r3 asks once the locking API/release mechanics are corrected.

## Plan review

1. The schema plan has a TypeScript/Zod mechanical error. [03-plan-r4.md](03-plan-r4.md#L167) says to define `cardHistoryHeaderSchema = cardHistoryEntrySchema.omit({ snapshot: true })`, but the current `cardHistoryEntrySchema` is typed as a generic `z.ZodType` produced by `z.lazy(...)` in [src/schemas/validators.ts](../../../src/schemas/validators.ts#L23); it will not expose `.omit()`. Required change: introduce a concrete base object schema before wrapping/typing it, or define a separate concrete header object schema. Also fold in the seq-0 decision from the analysis review before finalizing `version_seq` as positive/nonnegative.

2. The validation baseline says `MUST use package scripts only` in [03-plan-r4.md](03-plan-r4.md#L5), but the web block still runs a raw command, `cd web && npx vitest run src/__tests__/card-history-panel.test.ts`, in [03-plan-r4.md](03-plan-r4.md#L39-L44). Required change: add or reuse a `package.json` script for the card-history panel test and invoke it with `npm run ...`. The existing `web:test:operator-smoke` script is correctly used and exists in [package.json](../../../package.json#L70).

3. The slim-layout file-tree test is sharper than the planned directory edit. [03-plan-r4.md](03-plan-r4.md#L188) only removes `cards/tree` and `cards/dependencies` from `SAIVAGE_DIRS` and adds `cards/.commit`, but [03-plan-r4.md](03-plan-r4.md#L200) expects `ls .saivage/cards/` to show only `by-id/`, `history/`, and `.commit/`. Current `SAIVAGE_DIRS` also creates `cards/views` in [src/persistence/file-tree.ts](../../../src/persistence/file-tree.ts#L75). Required change: either remove `cards/views` as part of the slim layout, or relax the test expectation to match the intended retained directory set.

4. The async factory chain is otherwise mechanically corrected from r3: `ActiveRuntime.open` uses locals before construction, route registration is gated on the awaited factory, and the grep gate for public constructor removal is present. No `async-mutex` dependency is added.
