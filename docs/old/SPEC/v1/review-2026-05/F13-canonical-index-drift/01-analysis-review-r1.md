# F13 — Reviewer critique (r1)

## Analysis review

1. Tighten the concurrency claim. The write-order analysis around [src/cards/card-store.ts](../../../src/cards/card-store.ts#L646), [src/cards/card-store.ts](../../../src/cards/card-store.ts#L811), and [src/cards/card-store.ts](../../../src/cards/card-store.ts#L1090) is useful, but the document overstates same-process API races. The mutation bodies are synchronous and contain no `await`, so a normal Fastify handler cannot land between the by-id rename and the index write on the same event loop. The real proven classes are crash interruption, cross-process writers, and possible synchronous event-bus reentrancy from [src/cards/card-store.ts](../../../src/cards/card-store.ts#L544). Rewrite the analysis to separate those cases instead of treating operator HTTP reads as concurrently interleaving with the middle of a synchronous mutation.

2. Do not present the observed self-heal path as established fact without a reproduction. The analysis says a crash between by-id and index followed by startup recovery explains the transient error, but it has not shown the controlled crash sequence and the current code would normally throw during first validation before serving a healthy store. Keep this as a plausible hypothesis, then require an injected-failure test at the by-id/index boundary to prove whether the logged `project` mismatch is crash residue, cross-process drift, or another path.

3. Correct the F12 framing against existing tests. It is true that `update` and `setStatus` skip tracked history via [src/cards/card-store.ts](../../../src/cards/card-store.ts#L801) and [src/cards/card-store.ts](../../../src/cards/card-store.ts#L1090), but the current test suite explicitly encodes that behavior in [tests/utils/card-history.test.ts](../../../tests/utils/card-history.test.ts#L43). The revised analysis should call this out as stale/wrong product semantics that must be changed, not merely an absent code path.

4. Expand the affected mutation set beyond update/mutate/create. `archiveAndDeleteSubtree`, `delete`, dependency updates, block recomputation, and initialization all mutate the same canonical/projection files through [src/cards/card-store.ts](../../../src/cards/card-store.ts#L917), [src/cards/card-store.ts](../../../src/cards/card-store.ts#L965), [src/cards/card-store.ts](../../../src/cards/card-store.ts#L1039), and [src/persistence/file-tree.ts](../../../src/persistence/file-tree.ts#L148). The analysis should enumerate which invariants each path must preserve and which paths need history semantics.

5. Keep the good finding about `canonicalHealth`, but ground the API impact in the actual call sites. `getHealth()` only exposes the in-memory flag from [src/cards/card-store.ts](../../../src/cards/card-store.ts#L461), while the contract route currently hard-codes `{ canonical: 'ok' }` in [src/server/routes/operator-contracts.ts](../../../src/server/routes/operator-contracts.ts#L88) and websocket snapshots call the real store in [src/server/websocket.ts](../../../src/server/websocket.ts#L95). The analysis should distinguish those two surfaces.

## Design review

1. The recommendation for full event sourcing is not yet justified. Architecture-first does not mean picking the largest conceptual rewrite; it means deleting the faulty invariant at the lowest clean abstraction. Proposal B needs to prove why a simpler authoritative-state design is insufficient, such as making by-id records or a single `cards/state.json` snapshot the only source of truth and regenerating `index.json`, dependencies, blocks, and history as projections. The current cost claim that Proposal A and Proposal B are roughly equivalent is not honest: Proposal B adds an event schema, replay engine, state model, projection writer, log corruption policy, seed rewrite, health-contract removal, and a near-total rewrite of [src/cards/card-store.ts](../../../src/cards/card-store.ts#L329).

2. Proposal A's crash-safety story is incomplete. It says the commit marker contains `history_entry`, but the described recovery only completes temp-file renames; a crash after by-id/index renames and before `JsonlLedger.appendSync` still loses the history line while the card version has advanced. If Proposal A remains, the marker replay must include the history append exactly once or explicitly move history into the same authoritative artifact.

3. Proposal B removes the drift class only if the event log is truly the sole durable source. The design still duplicates `seq`, `version_seq`, and `snapshot.version_seq` in every event, which creates new drift surfaces unless one value is derived and the others are validated or removed. The writer should define one source for per-card version ordering and one source for global ordering.

4. The boot-time rebuild design is underspecified. Replaying `.saivage/cards/events.jsonl` and rewriting all projections before serving APIs can be correct, but the document gives no size bound, replay-time expectation, readiness gate, or rule that route registration/runtime startup waits until replay and projection regeneration complete. It also does not address dirtying every projection file on each boot when projections are intended to stay git-reviewable.

5. Do not claim existing ledger behavior solves truncated-line recovery. [src/persistence/jsonl-ledger.ts](../../../src/persistence/jsonl-ledger.ts#L70) quarantines malformed lines while reading and advances the cursor to the raw file length; it does not truncate a partial last line. If the event log is authoritative, the design must define whether a malformed final line is truncated, quarantined as a failed event, or fatal, and tests must cover that exact behavior.

6. The no-backward-compat rule is only partially applied. Proposal B correctly deletes much of the old canonical-health/history-projection code, but it also says the constructor creates an empty event log if missing. That silently discards existing projection-only card state if Step 4 lands before the seeding rewrite. Under this project's rules, missing `cards/events.jsonl` should be a clean-slate/reset condition or Step 4 and the init rewrite must land atomically; it should not be a migration shim or silent empty-state boot.

7. The derived-projection API contract needs a clearer read model. If all public `CardStore` reads come from in-memory state, projections can lag safely after an append. If any route or tool reads projection files directly, projection writes become part of the observable transaction again. The design should state that [src/cards/index.ts](../../../src/cards/index.ts#L1) remains the only card-store API and list any direct file readers that must be removed or converted.

## Plan review

1. Revise the plan after the design decision; it currently assumes Proposal B before earning approval. A revised plan should either choose a smaller authoritative-store/projection rebuild design or provide a quantified justification for event sourcing, including expected new/deleted LOC and the specific invariants eliminated.

2. Fix the step ordering. Step 4 says `CardStore` loads or creates the event log, while Step 6 later changes `initProjectTree` to seed via an event. That order can produce an empty event-log store over a projection-seeded project. Seed format, constructor boot policy, and old projection deletion/refusal must be changed in the same step or Step 6 must precede the `CardStore` rewrite.

3. Replace the validation commands. This repo's root tests are Jest via `npm test` / `npm run test:direct`, not Vitest, and there is no `tests/cards` directory. The baseline should be `npm run typecheck` plus focused Jest runs such as `npm run test:direct -- tests/utils/card-store.test.ts tests/utils/card-history.test.ts tests/projections/ledger-projections.test.ts tests/persistence/persistence-primitives.test.ts tests/api/cards-history.test.ts tests/agents/card-history-tools.test.ts tests/server/card-routes-authz-audit.test.ts tests/server/runtime-card-contract-routes.test.ts tests/server/operator-api-contracts.test.ts tests/server/websocket-analyst-safety.test.ts`. If contracts or web consumers change, use the npm web scripts from [package.json](../../../package.json#L31), not `pnpm -C web build`.

Those issues use `cardStore.update` and `setStatus`, so landing F13 changes the audit trail and potentially `version_seq` behavior under runtime lifecycle tests.
