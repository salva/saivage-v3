# System Architecture

This document is the canonical architecture authority for Saivage v3. The current durable-format cutover is reset-only; old binaries, mixed formats, migrations, compatibility readers, bridges, and normalization paths are unsupported.

## Deployment And Trust Model

Saivage is designed for an externally isolated LXC container. Deployment provides that isolation as the boundary against agent-caused host impact; Saivage neither creates nor verifies it. In-container agents are trusted and may execute shell commands as root.

Internal path, command, and process controls serve operational and API-contract purposes, and runtime/data invariants preserve ordinary correctness and integrity; none contains that trusted root-capable principal. Ordinary workflows may remain constrained despite that capability. External operator authentication and outbound secret non-disclosure remain genuine product boundaries.

## Activation Ownership Architecture

The supervisor owns one `Map<string, CardActivationOwner>` and one guarded synchronous `ownershipTransition`. `CardActivationOwner` is plain activation-local state and `CardProcessActor` is the remaining micro-actor. `ConversationLLMActor` is a separate direct provider/tool phase owner.

The direct Conversation LLM owner has no `BaseActor`, compiled topology, event queue, `start()`, or actor lifecycle settlement. The transition mutates only in-memory owner phases, parent/child links, currentness, run/token/status, readiness, containment axes, exact-run Pause state, and the linked child lease, then validates the graph and emits one coherent invalidation. Persistence, process calls, abort delivery, promise delivery, and joins occur outside it and continuations recheck exact identity. There is no owner repository, factory, registry, second map, transaction, recovery protocol, or callback bridge.

Each configured processor is directly constructed and started ready before its owner is observable. The supervisor constructs one `PlannerChildControlPort` bound to that exact parent activation and passes it through process/node/role composition. Provider code cannot select a parent or read an activation target before delegation. Concrete `CardService` remains the sole root/card reader.

`ConversationLLMActor.toolInvocationContext(outcome)` is the only production constructor of the complete invocation context for autonomous and Analyst calls. `invokeToolForLlm(surface,name,args,context,signal?)` and `invokeToolCall(surface,name,rawArgs,context,signal?)` have one required-context declaration each; no overload, default, fallback, partial context, or role subtype exists. Lower-level `invokeTool` remains context-optional for direct non-LLM use. Analyst cannot activate children because its surface and dependencies contain no planner port. Valid Analyst and Invocation Service app-log ownership remains; autonomous runtime and Planner dependencies remain free of `appLogs`.

`AnalystSession` is a plain serial phase coordinator. Admission moves one pending restart-confirmation capability into one accepted operation, whose immutable accepted ID is distinct from every fresh initial, tool-continuation, and repair invocation source. Its tracker consumer alone installs reusable idle, permanent failed, or disposed settlement and delivers the caller. Reusable non-scheduling outcomes restore confirmation before delivery; successful schedule return alone consumes it. Confirmed restart separates one accepted-ID activation/user batch from schedule entry and fences both after the complete writer boundary and immediately before scheduling.

The direct Conversation LLM union carries each exact canonical input, provider lease, parked tool context, and concrete child lease in its owning phase. Direct replacement is the sole transition authority. Provider entry creates the invocation lease; canonical writer entry owns publication plus every synchronous observer. Completion then publishes mandatory provider-exchange evidence, synchronously hands the exact terminal input to the enclosing Analyst or Card operation, and settles the direct promise. Analyst outer settlement writes a required terminal-source notice only after an error/model-issue row and evidence. No queued terminal event, lifecycle join, registry, ledger, or mutable latest-input authority exists.

Cancellation before Analyst ingress writes activation/workspace/user plus an accepted-source notice atomically; after ingress but before nested ownership it writes only that accepted-source notice. Nested-first cancellation instead claims the exact current LLM input. Parked-tool cancellation writes its failed tool result and notice under the parked source. Ordinary `settling_tool` has one nested first-winner terminal request: the claimed result or entered callback completes once, cancellation appends only one exact-current-source notice, and later continuation/provider effects are suppressed. Entered provider/model-error completion retains `${terminalSource}:error`, mandatory evidence, handoff, required `${terminalSource}:message`, and delivery despite disposal. Only later optional runtime/UI/read-model projection is suppressible. Append, observer, evidence, or handoff failure is preserved unchanged and authorizes no retry, read, fallback, or compensation.

Only positively classified pure pre-effect Analyst preparation rejection is reusable; every unclassified, persistence, observer, cleanup, invariant, and outcome-unknown rejection poisons admission. Disposal and shutdown snapshot exact operation, provider-lifecycle, and child-lease joins, start all joins, and propagate failure only after all settle. The supervisor's plain owner, `ownershipTransition`, parent-bound planner port, lease phases, and result-winner/Stop ordering remain unchanged: exact result claim installs direct `continuation_closed` before record publication, and Stop joins that winner without creating another activation authority.

Run preparation installs `prepared_root` before recovery/running publication. Result/cancel and Stop/application-close are orthogonal first-winner axes. Historical publication uncertainty never enters the new-containment-failure aggregate; successful Stop may forget locally quiescent uncertain ownership without stream access, while interruption/join/termination failure retains it. Runtime controls are delegation-only and the supervisor is the sole intervention-binding mutator. `RuntimeGate.completeRun()` closes the reusable gate and removes the exact run's Pause request/callback before stopped state is observable.

The exact card stream format is v2. Persistence, operator schemas, and inferred web types share one strict complete `CardRecord`: nine required literal-null fields, two required nullable terminal status companions, Analyst/planner creator identity, and exact lifecycle branches. There is no permissive transport overlay. `NewChildCardInput` contains only production child inputs and `CardEditPatch` only title, tags, priority, urgency, and related. Planner edit is admitted only from backlog/changed/stopped; blocked and failed are first reopened to changed. Dedicated notification, lifecycle, child-link, reorder, and deletion methods construct their exact candidates and fixed history metadata directly.

Identity derives structural parent/depth but never membership. Disposable `CardIndex` projections follow each reached parent's committed `children` array and filter it to active records. Operator and tool convenience fields are separately named explicit projections. `CanonicalCardFilesReadModel`, through CardService's canonical projections and descriptor-backed snapshot, is the sole `.saivage/cards/**` Files path: it returns exact v2 bytes and propagates strict v1/old-shape failure without generic filesystem fallback. Full-chain recovery remains leaf-to-root with valid partial prefixes, but v2 replay recognizes lifecycle-only stopped transitions.

The supported runtime is Node.js 24 with npm `>=10 <12`, matching `package.json` engines and CI.

## 1. Ownership Model

The runtime is card-centered. The runtime alone dispatches work. Project/goal cards select the compiled planning graph and terminal card types select the compiled terminal graph. Lifecycle entry chooses a configured ordinary node; role order is not code-owned topology.

One plain `CardActivationOwner` holds each mapped activation. `CardProcessActor` directly extends `BaseActor` and owns configured process position, activation tracking, LLM ownership, role handoff, and local join. `AgentNodeExecution` owns one node's role surface, prompt, correction, record, notification, and cleanup behavior. The supervisor's one map and orthogonal terminal/containment axes are the sole publication, cancellation, currentness, and containment authority. Durable running without an exact owner fails fast.

Supervisor pre-admission and project-root preparation are the only root activation boundary. Startup uses required concrete `actorStore`; there is no second root reader. Root ownership is installed before recovery or running publication. Child activation exists only through the exact parent-bound port and invocation lease. Every processor is started ready before owner visibility and activated only after successful running publication.

Cancellation claims the exact active suffix synchronously, preserves already-done descendants, aborts only under cancellation authority, publishes deepest-first, and joins one cached owner settlement. Natural release removes the exact owner/relationship from the one map before caller delivery. This is process-lifecycle authority, not a persistence lock, queue, transaction, generation, or currentness mechanism.

Card status behavior is intentionally operation-named rather than one terminal taxonomy. The cards-owned `card-status.ts` implementation exports exactly four small predicates/effects, and `status-api.ts` is their singular cross-package entrypoint: `canCreateChildInStatus` admits backlog, changed, running, blocked, and stopped; `canCancelCardStatus` admits every status except done and cancelled; `acceptsCardNotifications` admits backlog, changed, running, blocked, and stopped; and `analystBriefEditEffect` preserves backlog/running/stopped, reopens blocked/done/failed, and rejects changed/cancelled. Role, root, runtime, type, dependency, and publication gates remain at their owning surfaces. In particular, Analyst create additionally rejects running, while blocked remains unresolved and parent-planner-re-enterable.

Status-to-process admission has one nullable mapper: backlog maps to BACKLOG, changed to CHANGED, blocked to BLOCKED, stopped to STOPPED, and running/done/failed/cancelled to null. It grants no transition authority. The supervisor invokes it only after exact owner absence and one admission read; rejection precedes owner/processor construction. Stopped uses dedicated `activateStopped()` publication.

Each remaining micro-actor receives one explicitly compiled immutable topology and one per-instance callback binding object. Fixed production topologies compile once at module initialization and are reused across instances; callback closures alone carry instance behavior. Topology contains only states and transitions: there is no class-static discovery, reflection, or state-named handler convention. For those actors, `start()` assigns the initial state, invokes `enter` with the frozen start context, and, only when entry returns, starts the pump; it does not invoke `transition`, and a start-entry throw propagates synchronously. An external event transition freezes its context, then invokes `leave`, aborts and clears source-state tasks, assigns the target state, invokes `transition`, and finally invokes `enter`. Unknown events and ordinary non-reentering same-state transitions invoke no callbacks or aborts. Explicit same-state reentry follows the full external-transition order. An event callback failure uses the ordinary lifecycle-settlement failure path, with no fallback dispatch. These queue and lifecycle statements do not apply to `ConversationLLMActor`.

Other status decisions remain exact and local: running-chain membership is `status === 'running'`; dependency completion is `status === 'done'`; descendant completion is done-or-cancelled; activation settlement is done/failed/blocked with a distinct cancellation branch; deletion and Analyst reorder reject running; immediate-parent edit preserves backlog/changed/stopped, reopens blocked/failed, and rejects running/done/cancelled; and projected start admits only backlog/changed/stopped. Planner reorder is deliberately different from Analyst reorder: it may reorder the current running planner parent's children, whereas Analyst reorder rejects a running parent or running member of a requested child subtree.

## 2. Card Identity And Discovery

Card identity is `project` or one-to-five lowercase alphabetic hierarchical segments selected from a deterministic parent-local spreadsheet sequence. Every create starts at `a`; exact candidate namespace creation claims the segment, and only candidate `mkdir` `EEXIST` advances to the next segment. Collision handling never lists siblings or inspects the candidate. Parent, depth, namespace, exact card/record streams, and fixed-role conversation paths are forward-derived. `CardRecord` has no `position`. Backend `listChildren`, logical-path, reorder behavior, and web nested/direct-child projections follow each reached parent's committed cumulative `children` array order; active projections omit retained tombstoned links without changing that order.

One non-root attempt exact-reads and validates its linked parent and existing dependencies, then exclusively claims `.saivage/cards/project/children/<s1>/.../children/<sn>/` for the first candidate whose direct `mkdir` succeeds. `publishInitialChildCard()` constructs the complete card and brief from exact child input; `publishInitialProjectCard()` separately constructs the complete root from only title and brief. Dependency state is immutable after version 1. Existing-card-only dependency creation is cycle-free by construction, so mutation-era service/index cycle preflight does not exist; `validator.ts` alone retains whole-loaded-graph dependency-cycle rejection. The later parent append alone grants linked membership. A failed claimed namespace remains consumed and ignored.

Successful-path visibility checks occur only after the confirmed parent-link append: they may read the child through the parent's link and linked list/tree projection. Readable initial child streams before that link are not accepted membership. If any append or replacement reports an error, its outcome is unknown and neither production nor verification may read, list, probe, retry, reopen, reconcile, reconstruct a reader, or inspect the affected canonical or domain artifacts to infer what committed; only required cleanup of the already-open descriptor remains permitted. Verification proves stopping, ordering, and descriptor cleanup from operation traces and proves effects or their absence from spies. Card-only readers derive the bounded root-to-target chain from the requested ID, validate each reached exact `card.jsonl` once, require the next ID in the active parent's committed `children`, and only then touch the exact `children/<segment>` component. They do not read a brief. Complete initial publication separately proves the required initial brief, and only an explicit authored-record resource reads and validates its selected `brief.jsonl`, `status.jsonl`, or `review.jsonl`. A terminal tombstone is the final row of `card.jsonl`: it makes that card absent from every card-domain detail/history/version/diff/record projection and terminates traversal before descendants. Direct exact-known conversation I/O remains a separate lifecycle-ungated path. Namespace-only, brief-only, temp-only, unlinked malformed, and arbitrary noncanonical entries are silent invisible orphans. They are never scanned for allocation, validated in aggregate, cleaned, warned about, adopted, quarantined, or repaired.

## 3. Direct File Persistence

Saivage-owned persistence is direct stateless synchronous file I/O by the domain or actor owner:

- `card-files.ts` owns direct deterministic child-namespace claiming, complete initial stream publication/proof, exact `card.jsonl` reads, append-only card versions/history, cumulative child links, and terminal tombstone rows.
- `authored-record-files.ts` owns exact append-only `brief.jsonl`, `status.jsonl`, and `review.jsonl` streams. The authored-record slot registry contains exactly the three slots `brief.md`, `status.md`, and `review.md`; canonical `card.jsonl` is a distinct first-class card artifact, not an authored record slot. The initial brief is closed logical version 1; status and review use their strict open/edit/terminal revision transitions. `readAuthoredRecord()` emits the concrete `AuthoredRecordNotFoundError` only for a cleanly absent card or selector after strict direct reads; malformed canonical data, required-file absence, I/O errors, and invariants retain their original failures. Optional runtime, workspace, and tool consumers catch only that concrete type.
- `conversation-file.ts` owns one stable append-only conversation per role session.
- `contracts/app-log.ts` owns the strict three-lane `{type,data}` union for event, control-action, and provider-exchange rows. `persistence/app-log.ts` owns the sole direct synchronous preparation/validation/serialization/append boundary and strict reads, using the current project root directly. Domain producers supply preparation closures and invoke their narrow direct post-commit effects only after successful publication.
- `provider-exchange-log.ts` is the singular latest-provider-exchange selection owner. Each invocation strictly acquires the complete provider-exchange lane once and reduces it once by exact session ID, greatest timestamp, then greatest attempt index, retaining the earlier physical row on an exact tie. Singular exact lookup delegates to that same map implementation; no second filter/sort comparator exists.
- `ResolvedConfigAuthority` owns selected YAML document reads, effective validation, and config mutation orchestration; `config-file.ts` owns canonical atomic replacement.
- `auth-profile-file.ts` and `project-identity.ts` own their single canonical files.
- `runtime/lock.ts` is the exceptional process-exclusion boundary only.

One strict `cardRecordSchema` defines every current `CardRecord`, including card-version, embedded history-snapshot, and tombstone-final fields. The card-stream row schema is the sole structural parser for each raw row at read and write boundaries; `validateCardStream()` consumes only those typed parsed rows and performs identity, history, transition, immutable-field, child-link/reorder, ordering, and tombstone validation without another Zod parse.

The current singular operation grammar has no common patch writer, caller-selected context, optional terminal companion, generic dependency mutation, or broad transition API. `commitActivationOutcome()` is the sole running-to-done/failed/blocked publisher and derives lifecycle, both required status companions, and notification clearing from the non-cancelled outcome and one settlement timestamp. Generic status owns only backlog/blocked/changed-to-running, blocked/done/failed-to-changed, and the six admitted cancellation sources; recovery and stopped activation own their disjoint pairs. Every actual delta has deterministic order and recomputed summary. The eight discriminated history families carry fixed row-local provenance. Replay scans no child stream and proves only row-local facts: notably child-link is runtime-owned, while reorder replay proves the private complete same-membership full-order primitive, not the public operation's historical active-set admission.

The bottom-layer card schema keeps its notification-format invariant locally and imports no card behavior: complete done, failed, and cancelled records require empty `pending_notifications`, while backlog, changed, running, blocked, and stopped may retain them. This exact schema refinement intentionally duplicates the higher-layer notification predicate rather than creating a `schemas -> cards` dependency.

Planner child admission exact-reads the linked target and each dependency in declared order. It never invokes list/tree/index APIs and retains no authorization state. Linked-tree operations start at the exact root and recursively follow committed `children`; their disposable projection validates active dependencies and hierarchy and is discarded with the call. Multi-root deletion uses that one fresh projection to form a subtree union, reject permissions and surviving dependents, and topologically order dependent-before-dependency plus child-before-parent tombstones. This graph is call-local write admission, not persistence coordination.

The complete, duplicate-free cumulative parent `children` snapshot is the sole linked-membership and semantic-order authority, including retained tombstone links. A real active reorder uses one fresh operation-local parent/active-child projection, requires a duplicate-free permutation of the active IDs, and constructs one next parent snapshot with requested active IDs first and all retained non-active links afterward in stable prior order. It appends one parent version and never writes child streams. An active-order no-op has no append or effect, even when retained links are interspersed in the old complete order. Parent-local stream validation admits only a changed, same-length, same-membership permutation declared as a children-only reorder, with no other local field change; identity order, membership change, and piggyback mutation fail. Validation compares consecutive parent snapshots only and carries or derives no active/tombstone classification in history. Thus both the old and new complete parent rows are valid committed prefixes without reorder coordination.

Planner activation validates schema and immediate-child identity, reserves the exact invocation lease, and delegates through the bound parent port. The supervisor validates parent and lease before I/O; owner absence alone authorizes one admission/dependency/status read. It constructs and starts a ready processor, silently installs owner/relationship/lease, performs one running publication, then transfers currentness and activates the processor. Exact same-lease joins perform no I/O.

Dependency and non-activatable-status rejection precede owner and processor construction. They cause no running publication, relationship/currentness change, or execution work and add no scheduler, traversal, propagation, or cancellation behavior.

Every replacement and first JSONL publication calls `replaceFile`. It creates one fresh random UUID same-directory temp exactly once with `O_CREAT | O_EXCL | O_WRONLY`, writes and fsyncs it, renames over the target, and fsyncs the parent. A temporary-path collision or other failure propagates. Crash-left temps remain ignored forever. Publication-temp UUID generation and invocation UUID generation are distinct identity scopes; card identity instead comes from direct parent-local deterministic namespace claims.

All file, directory, append, and lifecycle-lock creation uses ordinary Node defaults filtered only by the process umask. No mode argument, chmod/fchmod, permission probe, or repair exists.

Growing canonical JSONL files use one result-bearing `appendEnvelope()` API: `appended` means write, fsync, and close all succeeded, while `missing` means only that the initial exact-path open returned `ENOENT` before a descriptor existed. Every caller handles both results explicitly. First publication separately calls `lstat` on the exact target exactly once: any successful result is ignored and means already published, only `ENOENT` permits one unchanged replacement attempt, and every other error propagates. It never opens or classifies an existing target, so files, directories, symlinks, FIFOs, sockets, and devices take the same present branch. App log alone may use append `missing` for one first-publication attempt; card, record, and nonempty conversation owners fail fast because their previously read append target must still exist.

Append acquisition uses `O_WRONLY | O_APPEND | O_NOFOLLOW | O_NONBLOCK` and descriptor metadata, never a path probe. The descriptor must be a regular file before any write. Every successful open has exactly one close attempt: an earlier stat/validation/write/zero-progress/fsync error takes precedence over close error, while a lone close error propagates, and close is never retried. The app-log writer validates and serializes only its incoming row and does not read existing bytes. Reader-local semantic indexes, global duplicate checks, and identifiable unterminated-suffix canonicalization remain strict full-read concerns and never authorize or prepare a write. Complete malformed data remains and fails; direct append never truncates an existing suffix.

The inferred strict `LoggedEvent` union and runtime event schema agree on exactly `runtime_diagnostic`, `runtime_actionable_error`, and `mcp_tool_invocation`. The actionable-error envelope is strict. Error events are both runtime kinds and only failed MCP invocations; there is no generic routing metadata, replay-only event kind, content-review lane, or dedicated error lane.

Provider-exchange publication belongs to its agent producer, not generic app-log persistence or the provider-exchange schema. Immediately before strict parse and append, a field-classified projection applies the singular direct text redactor to descriptive contract/provider/model/account, finish/tool, and error text and the singular direct structured redactor to request-parameter values while preserving code-owned property names. It deliberately excludes exact session/source/output identities, generated log identity, attempt indexes, validated timestamps, discriminants, and non-string structure because those fields maintain durable linkage and ordering. Schemas validate the projected singular contract but never sanitize canonical bytes, and `app-log.ts` selects no redaction behavior.

There is no app-log dependency forwarded through Supervisor, `CardActivationOwner`, `CardProcessActor`, or `AgentNodeExecution`. Planner reorder and notification use canonical card/runtime evidence and append no control action. Analyst mutation settlement and Invocation Service retain their independent valid app-log ownership. Historical Planner control-action rows remain readable; current event discriminators and strict replay behavior are unchanged.

`appendAppLogEntry(projectRoot, entryType, prepareEntry, context?)` is the sole app-log publication boundary. The synchronous preparation closure performs identity/time construction, centralized redaction or audit/provider projection, and typed row construction inside the same try as authoritative envelope validation/serialization, owner-directory creation, first publication, and append. Every failure in that interval becomes one `AppLogPublicationError`. Publication failure has precedence over an already-settled operation error, and every reachable catch either rethrows the identical object before classification or performs only volatile containment and then rejects with that object. No retry, second append, fallback, ordinary failed ToolResult/model/card outcome, later attempt, write, or SyncHub hint follows it.

Terminal propagation follows the current ownership graph: direct `ConversationLLMActor` into plain `AnalystSession` or `CardProcessActor`, then the Supervisor's centralized owner/lease graph. CardProcess halts its failed task state without joining its own activation-tracker consumer. Only Supervisor joins after observing the rejected activation. Child leases move through `publication_unknown` to `contained`, never `released`; the retained project owner remains `publication_unknown` and `error/not_ready` until explicit Stop containment. Dynamic execution uses existing direct scopes under the runtime-card, operator-session, and service-infrastructure process roots; terminal cleanup closes/joins only owned volatile scopes and cannot replace the publication error. The exact consuming roots are the global Fastify error handler, the registered Analyst WebSocket message rejection observer, and Supervisor's `activateProcessor()` rejection callback for the project owner. Those roots expose no cause and publish no replacement evidence.

`EventQueryService` is the sole event/error query authority. Each query performs one complete strict event-lane read and then filters/slices. `/api/events` supplies strict oldest-page or newest-tail selection with maximum 1000 and no session/since filters; `/api/debug/errors` is its complete derived error projection. `/api/debug/timeline`, ErrorLog, and duplicate event read models do not exist.

The shared `AgentRole` authority has exactly Analyst, Planner, Executor, and Reviewer. Direct model, temperature, max-token, routing, resolution, and mutation contracts accept only those roles, with `default` admitted only by direct models, temperature, and max tokens. Profile/equivalent/failover model keys remain in their separate arbitrary identity domains. The independent `SkillTargetRole` remains exactly Executor, Reviewer, and Analyst; Planner has no skill provider.

## 4. Card-Process Compilation And Execution

Startup strictly parses required `card_processes.planning` and `card_processes.terminal` and compiles exactly one immutable actor topology/artifact per family before actor construction. Its states are `lifecycle:ready`, `entry:<port>`, `node:<id>`, and terminal `terminal:<port>`; accepted outcomes are `result:<outcome>` events, while `execution:failed` is the code-owned failed route. The compiled definition alone contains source/event/target/reentry topology. A same-node configured edge is explicit external `reenter:true`; business metadata contains node roles/prompts/records and optional transition prompts without duplicate targets or outcomes. Configured terminal reachability is validated before the failure route is added. Entries are exactly `BACKLOG | CHANGED | BLOCKED | STOPPED`; terminal ports are separately tagged `DONE | FAILED | BLOCKED`. Terminal edges cannot carry prompts, prompt identities may be reused, every node is entry-reachable and has a configured terminal path, planning nodes use planner/reviewer, and terminal nodes use executor.

Process prompt artifacts are exact `src/prompts/<card-type>/process/<identity>.md` defaults overridden only by `.saivage/config/prompts/<card-type>/process/<identity>.md`. The build copies the complete source default tree from `src/prompts` to `dist/prompts`; runtime composition explicitly selects the applicable source or packaged bundled root and supplies it to both the role-template and process-prompt registries. The post-build compiled-composition smoke protects the packaged-layout path. Startup also loads each effective role template, requires exactly one `{{contractDescription}}`, rejects the finite obsolete `emit_result.status`/terminal-status/fixed-result-list directives, and renders every configured card-type/role/node pair. This is a strict finite contract check, not a general prose parser. The bundled topology audit changes only the one-pass wording in all seven executor templates; planner/reviewer role-authority prose remains, and there is no startup topology linter.

`CardActivationOwner` retains the selected lifecycle entry and ready `CardProcessActor`. Per-instance `enter` and `transition` callbacks execute the shared family definition. Entry queues its route without I/O; node entry starts one task; transitions invalidate runtime projection. The first node ordinal is 0 and accepted node reentry advances it once. `AgentNodeExecution` retains stabilization, role/transition/node context, correction, record, notification, and configured-entry behavior.

`buildRoleSurface` is the single executable role-composition authority. Its role-discriminated input is narrowed by one exhaustive switch, whose literal provider arrays directly construct each role's providers in executable order; `buildInvocationSurface` preserves that order in the duplicate-free executable map. The separate `surfaceToolDefinitions` projection produces the operational wire array used for autonomous prompt rendering. Planner, Reviewer, and Executor append their sole `emit_result` contract tool only afterward, and that exact terminal-last final array is used for provider invocation and prepared compaction. Analyst prompt, provider, and prepared-compaction arrays remain the same operational terminal-free array.

`SkillCatalog` is the narrow stateless boundary for the exact optional `.saivage/skills/index.json` and selected skill files. On each explicit call it synchronously reads and validates the complete strict current index, filters by the supplied narrow `executor | reviewer | analyst` role, preserves operator order, and either projects only `{name}` rows or reads one exact role-authorized file as `{name,content}`. It retains no cache, matching/ranking logic, watcher, instruction owner, repository lifecycle, or fallback source. Only `ENOENT` for the exact index has empty-catalog semantics; malformed present data and selected-file failures propagate. `createSkillProvider` is the sole executable `skill` definition and the sole owner of the model-facing list/load ToolResult projections. It is installed once for Reviewer, Executor, and Analyst and not for Planner; `mcp_tool_call` remains separately and singularly owned by `mcp-provider.ts`.

The tool-result persistence boundary retains the provider's complete invocation envelope unchanged. For skill success this is exactly `{success:true,data:{skills:[{name}]}}` or `{success:true,data:{skill_name,skill_content}}`; failure remains the generic `{success:false,error}` envelope. `tool-friendly.ts` passes that serialized complete result through the public presenter registry. The registered skill success presenter reads only the complete envelope's `data`: lists render `N skill`/`N skills`, including zero, and named loads render `skill loaded`. The registry classifies failed envelopes through its generic error path before any skill success presenter; there is no bare-payload compatibility projection or skill-specific error path.

One LLM options path carries the supplied ordered tool list to every provider transport. A non-empty list is sent with only `tool_choice: 'auto'` and `parallel_tool_calls: false`; an empty list omits the tool fields. There is no forced-name choice or provider terminal-phase path. New provider-exchange `request_params` retain transport-specific metadata but omit the obsolete `phase` key.

Routing occurs only when the matching activation-owned tracker consumer stages the accepted result or failure. Activation trackers and provider invocation lifecycles remain separate semantic owners over shared low-level contained operations. Terminal order adds terminal entry and process settlement before supervisor-owned publication; tracker and LLM join state remain reachable for containment.

The operator LLM-exchange handler is a separate external operator response/non-disclosure boundary. It independently applies the same singular direct structured redactor to the latest strictly read canonical payload and parses that projection before response, without rewriting persistence or reusing the producer's field-classification ownership. Its failure path emits only a stable generic API body and a stable log event containing the validated session and operation identifiers; no exception object, diagnostic message, malformed value, stack, or project path crosses either operator sink.

## 5. Stable Sessions And Full-Chain Recovery

Stable sessions are exactly `analyst:global` plus planner/reviewer/executor identities whose suffix is a hierarchical card ID. The dependency-low shared identity module owns the literal and role-correlated schemas, types, and parser. `AgentMessage.session_id`, persistence, actor/source classification, generic Agent and chat contracts, direct conversation live-sync frames, and web contracts consume that one authority. Parameterized chat contracts compose the Analyst-only shared schema, while generic Agent route params compose the full conversation union. `ContractRuntime` enforces those request schemas before handler dispatch; handlers do not reparse or compare chat identity. Chat exposes only exact get/send operations. Operation response inventories describe only selected-operation outcomes, while an unmatched HTTP route's ordinary `404` remains framework-owned. Card-role streams live at their card's fixed `conversations/<role>.jsonl`; the singleton Analyst stream is the fixed `.saivage/agents/conversations/analyst%3Aglobal.jsonl`. ## 12. Reset And Failure Model

Durable-format changes require stopping the service, running the current built reset, and then starting the current binary. Directory-owned parent-local spreadsheet claims, the exact two-kind card stream, card records without `position`, complete parent-owned `children` membership/order, immutable card type across every card version, the ordered summary-group payload, minimal strict `applied_policy`, and marker-first/no-preamble Analyst source contract are such cutovers. Successful candidate `mkdir` consumes its segment even if later work fails, and only the parent's committed cumulative `children` snapshot grants and orders membership. Generated streams containing old `card-child-reservation` rows fail strict current-format reads. Every deployment resets its generated roots wholesale before the current binary starts, even when sampled or known card histories appear compatible; no compatibility detection exempts a deployment. Every later card version and tombstone retains lifelong type, so role/session projection cannot change; changed-type streams fail strict validation. Old generated rows, changed-type card histories, and pre-marker or mixed Analyst histories fail strict reads, and there is no migration, marker backfill, compatibility classifier/renderer, format probe, selective repair, or mixed-version operation. `resetOwnedGeneratedRoots()` in `src/persistence/layout.ts` is the singular reset ownership and initial-publication-presence contract: `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work`. Initial publication requires all four exact roots absent; retained partial state names its first blocker and requires stop, current-built reset, then retry. These generated roots are removed as whole trees without descendant inspection. Durable configuration and operator inputs under `.saivage`, including identity, credentials, prompt overrides, skills, and instructions, remain outside that ownership boundary, as do source and canonical documents.

The `.saivage/locks` namespace is the exceptional lifecycle-exclusion boundary, not reset-owned generated persistence. Reset acquires the exact canonical `runtime.lock`, removes the four complete roots, publishes the new `project` root card while still holding the lock, and then uses exact-owner release. A pre-existing exact lock blocks deletion. Lock siblings and every other outside-boundary path are neither discovered nor cleaned. Mixed-version operation and rollback against current-format state are unsupported.

Saivage file persistence does not guarantee no data loss. Interrupted external effects may repeat; notification context may duplicate; concurrent auth refresh may overwrite another change; incomplete card namespaces and publication temps may remain forever. Exact canonical corruption fails clearly for operator repair or reset rather than automatic recovery.

### Agent tools

The inventory lists every tool that each runtime role can potentially be offered by the exhaustive discriminated role builder and, for autonomous roles, terminal contract. The documentation verifier reads only the builder's strict switch cases and direct literal provider-constructor arrays; provider implementations remain the tool-name authority. Executable role composition admits Analyst tools. The conditional Analyst `restart_server` entry is offered only when the concrete authenticated restart capability is available; its safety class is audit metadata, not admission policy.

The Analyst control registry is one ordered, context-bound catalog of executable `ToolDefinition` entries. It is distinct from the Planner control provider, the LLM wire-tool projection, and MCP discovery/wire contracts; those surfaces do not contribute metadata to the Analyst catalog. Analyst mutation composition creates one application service bundle for a turn. Each application operation performs its fresh admission/currentness reads and immediately invokes its card, runtime, configuration, notification, or record owner through that single call.

An audited prepared mutation orders work as optional read-only preparation, invocation signal, intervention readiness when applicable, one fresh operation-owned application mutation, control-action settlement, then a late signal check. Preparation, readiness, and the owning domain service perform current admission; safety class remains audit classification metadata. There is no reservation between preparation and mutation. A returned committed success settles `ok` before late cancellation is honored; cancellation cannot replay or undo the owner effect.
