# System Architecture

This document is the canonical architecture authority for Saivage v3. The current durable-format cutover is reset-only; old binaries, mixed formats, migrations, compatibility readers, bridges, and normalization paths are unsupported.

The supported runtime is Node.js 24 with npm `>=10 <12`, matching `package.json` engines and CI.

## 1. Ownership Model

The runtime is card-centered. The runtime alone dispatches work. Project/goal cards select the compiled planning graph and terminal card types select the compiled terminal graph. Lifecycle entry chooses a configured ordinary node; role order is not code-owned topology.

`CardActor` owns one live card activation. Its synchronous `open | claimed_result | claimed_cancel | claimed_stop` claim decides result, cancellation, and Stop ownership before any await. `CardProcessActor` directly extends the frozen `BaseActor` and directly owns activation tracking, LLM ownership, role handoff and join, projection, and the in-memory sequential graph loop; there is no reusable card-processor base hierarchy. One reusable `AgentNodeExecution` remains its one-node helper, and with three small code-owned role adapters owns role surface, stable session, prompt, correction, record, notification, and node-local cleanup behavior. They return one final activation outcome and never publish terminal card lifecycle. `CardActor` is the sole non-cancellation outcome publisher and owns caller and activation-ownership finalization. The supervisor keeps one retained-actor map for process-local ownership and one exact-live-activation map for running cancellation resolution. A running card without exactly one live owner is impossible and fails fast; callers never fall back to direct cancellation.

Supervisor pre-admission and preparation are the only root activation boundary. Root execution enters `CardActor` only through Supervisor-owned prepared, restarted, or structural-chain lifecycle APIs after the root is running; a root caller on prepared input records execution provenance rather than admission authority. Direct `CardActor.activate()` is exclusively the parent-child boundary and requires the parent planner's mutation capability to admit that exact immediate child. Every card is running before processor execution begins, and `CardActor` performs no actor-local root status write.

Cancellation first revokes provider, tool, child, reviewer, process, and callback admission. The cached actor-local cancellation promise runs `finishCancellation()` as the exact winner boundary: it contains activation-owned processes and exact live descendants, directly publishes the cancelled card, and settles its caller once. For natural result or cancellation settlement outside closing, the actor synchronously delegates its own identity to the supervisor. The supervisor requires that exact actor in both maps and removes both entries; mismatch fails fast. This release means the completed activation no longer has live ownership or a retained runtime projection. It does not certify or wait for the detached micro-actor object to consume an already-queued cosmetic `settled` or `cancel` event. A later legitimate activation constructs a fresh `CardActor` and processor. Already-done descendants remain done. This is process-lifecycle authority and reference release, not a persistence lock, queue, transaction, generation, or currentness mechanism.

Card status behavior is intentionally operation-named rather than one terminal taxonomy. The cards-owned `card-status.ts` implementation exports exactly four small predicates/effects, and `status-api.ts` is their singular cross-package entrypoint: `canCreateChildInStatus` admits backlog, changed, running, blocked, and stopped; `canCancelCardStatus` admits every status except done and cancelled; `acceptsCardNotifications` admits backlog, changed, running, blocked, and stopped; and `analystBriefEditEffect` preserves backlog/running/stopped, reopens blocked/done/failed, and rejects changed/cancelled. Role, root, runtime, type, dependency, and publication gates remain at their owning surfaces. In particular, Analyst create additionally rejects running, while blocked remains unresolved and parent-planner-re-enterable.

Status-to-process admission has one nullable mapper, `cardProcessEntryForStatus`: backlog maps to `BACKLOG`, changed to `CHANGED`, blocked to `BLOCKED`, stopped to `STOPPED`, and running/done/failed/cancelled to null. It grants no transition authority and has only two pre-running callers: Supervisor fresh-root admission and `CardActor.activate()` at the validated immediate parent-child boundary. The Supervisor maps before its root status mutation and remains the sole root owner; `CardActor` maps before the parent callback, then requires that callback to have published running before claiming actor ownership. Stopped uses the dedicated `activateStopped()` write at both boundaries.

Other status decisions remain exact and local: running-chain membership is `status === 'running'`; dependency completion is `status === 'done'`; descendant completion is done-or-cancelled; activation settlement is done/failed/blocked with a distinct cancellation branch; deletion and Analyst reorder reject running; immediate-parent edit preserves backlog/changed/stopped, reopens blocked/failed, and rejects running/done/cancelled; and projected start admits only backlog/changed/stopped. Planner reorder is deliberately different from Analyst reorder: it may reorder the current running planner parent's children, whereas Analyst reorder rejects a running parent or running member of a requested child subtree.

## 2. Card Identity And Discovery

Card identity is `project` or one-to-five lowercase alphabetic hierarchical segments selected from a deterministic parent-local spreadsheet sequence. Every create starts at `a`; exact candidate namespace creation claims the segment, and only candidate `mkdir` `EEXIST` advances to the next segment. Collision handling never lists siblings or inspects the candidate. Parent, depth, namespace, exact card/record streams, and fixed-role conversation paths are forward-derived. `CardRecord` has no `position`. Backend `listChildren`, logical-path, reorder behavior, and web nested/direct-child projections follow each reached parent's committed cumulative `children` array order; active projections omit retained tombstoned links without changing that order.

One non-root attempt exact-reads and validates its linked parent, then exclusively claims `.saivage/cards/project/children/<s1>/.../children/<sn>/` for the first candidate whose direct `mkdir` succeeds. Its exact successful order is namespace claim → closed initial `brief.jsonl` and card-version-1 `card.jsonl` publication → complete-publication proof inside `publishInitialCard()` → fresh parent reread/admission → second complete-publication proof in `CardService` → one cumulative parent `children` append → parent `child_link` history, card, and runtime effects. Candidate-directory creation claims and consumes identity only; complete publication makes the child locally readable; the later single parent append alone grants linked membership and places the child at the end of semantic sibling order. A failure after successful claim ends that call and leaves the namespace consumed; a later independent attempt starts at `a` and advances only across opaque `EEXIST` candidates.

Successful-path visibility checks occur only after the confirmed parent-link append: they may read the child through the parent's link and linked list/tree projection. Readable initial child streams before that link are not accepted membership. If any append or replacement reports an error, its outcome is unknown and neither production nor verification may read, list, probe, retry, reopen, reconcile, reconstruct a reader, or inspect the affected canonical or domain artifacts to infer what committed; only required cleanup of the already-open descriptor remains permitted. Verification proves stopping, ordering, and descriptor cleanup from operation traces and proves effects or their absence from spies. Card-only readers derive the bounded root-to-target chain from the requested ID, validate each reached exact `card.jsonl` once, require the next ID in the active parent's committed `children`, and only then touch the exact `children/<segment>` component. They do not read a brief. Complete initial publication separately proves the required initial brief, and only an explicit authored-record resource reads and validates its selected `brief.jsonl`, `status.jsonl`, or `review.jsonl`. A terminal tombstone is the final row of `card.jsonl`: it makes that card absent from every card-domain detail/history/version/diff/record projection and terminates traversal before descendants. Direct exact-known conversation I/O remains a separate lifecycle-ungated path. Namespace-only, brief-only, temp-only, unlinked malformed, and arbitrary noncanonical entries are silent invisible orphans. They are never scanned for allocation, validated in aggregate, cleaned, warned about, adopted, quarantined, or repaired.

## 3. Direct File Persistence

Saivage-owned persistence is direct stateless synchronous file I/O by the domain or actor owner:

- `card-files.ts` owns direct deterministic child-namespace claiming, complete initial stream publication/proof, exact `card.jsonl` reads, append-only card versions/history, cumulative child links, and terminal tombstone rows.
- `authored-record-files.ts` owns exact append-only `brief.jsonl`, `status.jsonl`, and `review.jsonl` streams. The initial brief is closed logical version 1; status and review use their strict open/edit/terminal revision transitions.
- `conversation-file.ts` owns one stable append-only conversation per role session.
- `app-log.ts` owns strict event, error, unrelated control-action, provider-exchange, and content-review entries.
- `ResolvedConfigAuthority` owns selected YAML document reads, effective validation, and config mutation orchestration; `config-file.ts` owns canonical atomic replacement.
- `auth-profile-file.ts` and `project-identity.ts` own their single canonical files.
- `runtime/lock.ts` is the exceptional process-exclusion boundary only.

`CardService` performs operation-local rereads and invokes these direct functions. `validateCardStream()` accepts exactly contiguous `card-version` rows from version 1 followed by at most one `card-tombstone`; the tombstone is forbidden for root, must be the final physical row, and must exactly preserve the final card. It requires deletion-history `card_id` to equal tombstone `card_id`, deletion-history `changed_at` to equal `deleted_at`, and deletion-history `version_seq` to equal `final_card.version_seq`. It also owns the cross-version invariant that every full card version and tombstone retains the initial row's type. The ordinary `CardPatch` mutation contract excludes both immutable `type` and structurally owned `children`; generic mutation rejects an own `children` property before equal-value pruning for every caller and status. Creation's empty array, dedicated one-ID `child_link` suffix append, and dedicated reorder are the only `children` writers. In autonomous execution, `CardActor` is the sole caller of terminal lifecycle commit for non-cancellation activation outcomes. The supported `setStatus('changed')` transition is the sole terminal-card reopening authority; there is no actor-owned reopening callback, terminal lifecycle repair, or admin-repair path. A disposable `CardIndex` may project one read, but it never authorizes a later write. There are no repositories, generic stores, persistence health latches, writer registries, queues, generations, transactions, repair orchestrators, or durable runtime owners.

The bottom-layer card schema keeps its notification-format invariant locally and imports no card behavior: complete done, failed, and cancelled records require empty `pending_notifications`, while backlog, changed, running, blocked, and stopped may retain them. This exact schema refinement intentionally duplicates the higher-layer notification predicate rather than creating a `schemas -> cards` dependency.

Planner child admission exact-reads the linked target and each dependency in declared order. It never invokes list/tree/index APIs and retains no authorization state. Linked-tree operations start at the exact root and recursively follow committed `children`; their disposable projection validates active dependencies and hierarchy and is discarded with the call. Multi-root deletion uses that one fresh projection to form a subtree union, reject permissions and surviving dependents, and topologically order dependent-before-dependency plus child-before-parent tombstones. This graph is call-local write admission, not persistence coordination.

The complete, duplicate-free cumulative parent `children` snapshot is the sole linked-membership and semantic-order authority, including retained tombstone links. A real active reorder uses one fresh operation-local parent/active-child projection, requires a duplicate-free permutation of the active IDs, and constructs one next parent snapshot with requested active IDs first and all retained non-active links afterward in stable prior order. It appends one parent version and never writes child streams. An active-order no-op has no append or effect, even when retained links are interspersed in the old complete order. Parent-local stream validation admits only a changed, same-length, same-membership permutation declared as a children-only reorder, with no other local field change; identity order, membership change, and piggyback mutation fail. Validation compares consecutive parent snapshots only and carries or derives no active/tombstone classification in history. Thus both the old and new complete parent rows are valid committed prefixes without reorder coordination.

The common planner request order is an exact linked target read → exact dependency reads in declared order with `done` validation → `children.get()`. It never builds or scans a tree/index. `children.get()` may construct and register a `CardActor`, construct its processor, and call the idle processor actor's `start()`; that lifecycle initialization is not processor activation or provider execution. An admitted new activation continues through the parent planner's required mutation capability with `running` status write → exact live-ownership claim → current-leaf transfer → `CardActor` running transition → processor activation/provider work. An admitted running join instead continues with `awaitSettlement()` and its parent `enterChild`/`resumeParent` relationship, without reactivation.

Dependency rejection precedes `children.get()`. It therefore prevents both request-caused lookup-time construction/idle start and every later new-activation or join effect. This guarantee is attributed only to the rejected request: it neither revokes an already-running actor's owner nor stops or freezes its processor/provider work, which may settle independently. The rule adds no scheduler, dependency traversal, status propagation, or cancellation behavior.

Every replacement and first JSONL publication calls `replaceFile`. It creates one fresh random UUID same-directory temp exactly once with `O_CREAT | O_EXCL | O_WRONLY`, writes and fsyncs it, renames over the target, and fsyncs the parent. A temporary-path collision or other failure propagates. Crash-left temps remain ignored forever. Publication-temp UUID generation and invocation UUID generation are distinct identity scopes; card identity instead comes from direct parent-local deterministic namespace claims.

All file, directory, append, and lifecycle-lock creation uses ordinary Node defaults filtered only by the process umask. No mode argument, chmod/fchmod, permission probe, or repair exists.

Growing canonical JSONL files append one newline-terminated strict envelope with non-empty rows. An owning reader may truncate only an identifiable unterminated final suffix of that exact canonical file. Complete malformed data remains and fails.

## 4. Card-Process Compilation And Execution

Startup strictly parses required `card_processes.planning` and `card_processes.terminal`, compiles immutable maps, and resolves every exact process prompt before actor construction. Entries are exactly `BACKLOG | CHANGED | BLOCKED | STOPPED`; terminal ports are separately tagged `DONE | FAILED | BLOCKED`. Ordinary and terminal edge targets use strict tagged objects, terminal edges cannot carry prompts, prompt identities may be reused, and every node must be entry-reachable and have a directed terminal path. Planning nodes may use planner/reviewer; terminal nodes may use executor. Cycles are legal and have no graph counter.

Process prompt artifacts are exact `src/prompts/<card-type>/process/<identity>.md` defaults overridden only by `.saivage/config/prompts/<card-type>/process/<identity>.md`. The build copies the complete source default tree from `src/prompts` to `dist/prompts`; runtime composition explicitly selects the applicable source or packaged bundled root and supplies it to both the role-template and process-prompt registries. The post-build compiled-composition smoke protects the packaged-layout path. Startup also loads each effective role template, requires exactly one `{{contractDescription}}`, rejects the finite obsolete `emit_result.status`/terminal-status/fixed-result-list directives, and renders every configured card-type/role/node pair. This is a strict finite contract check, not a general prose parser. The bundled topology audit changes only the one-pass wording in all seven executor templates; planner/reviewer role-authority prose remains, and there is no startup topology linter.

`CardActor` passes only the pre-running-write lifecycle entry and compiled family to `CardProcessActor`. The actor directly tracks activation and LLM lifecycle while looping ordinary nodes in one activation, and it persists no cursor, node, transition, counter, or history. `AgentNodeExecution` remains the one-node helper: it appends role context, optional immediate transition context, and node prompt in that order; creates the node-specific strict parsed `{outcome,summary}` contract and sole `emit_result` tool; combines it with operational tools in one ordered invocation surface; captures record baselines once; and runs the existing correction loop. Same-role transitions reuse their stable session, while cross-role transitions explicitly change the current LLM owner.

One LLM options path carries the supplied ordered tool list to every provider transport. A non-empty list is sent with only `tool_choice: 'auto'` and `parallel_tool_calls: false`; an empty list omits the tool fields. There is no forced-name choice or provider terminal-phase path. New provider-exchange `request_params` retain transport-specific metadata but omit the obsolete `phase` key.

Graph routing occurs only after one accepted result. Plain text, malformed results, record violations, pending notifications, completion rejection, and stale review remain hidden same-node corrections. The repair loop continues in that node and returns its accepted value directly; it has no restart result. All read-only gates precede claim. A terminal edge claims synchronously, then closes records in configuration order, settles the accepted tool result, cleans node-local resources, and returns the processor outcome for later CardActor publication. An intermediate edge performs close/settle/cleanup without claim and only then enters its target. Executor scope identity is activation ID plus an in-memory node ordinal; corrections reuse one scope, and cleanup completes before the outgoing edge. This internal contract simplification changes no gate or ordering behavior.

## 5. Stable Sessions And Full-Chain Recovery

Stable sessions are exactly `analyst:global` plus planner/reviewer/executor identities whose suffix is a hierarchical card ID. The dependency-low shared identity module owns the literal and role-correlated schemas, types, and parser. `AgentMessage.session_id`, persistence, actor/source classification, generic Agent and chat contracts, `conversation_changed` payload/log schemas, live-sync frames, and web contracts consume that one authority. Parameterized chat contracts compose the Analyst-only shared schema, while generic Agent route params compose the full conversation union. `ContractRuntime` enforces those request schemas before handler dispatch; handlers do not reparse or compare chat identity. Operation response inventories describe only selected-operation outcomes, while an unmatched HTTP route's ordinary `404` remains framework-owned. Card-role streams live at their card's fixed `conversations/<role>.jsonl`; the singleton Analyst stream is the fixed `.saivage/agents/conversations/analyst%3Aglobal.jsonl`. Direct known-session I/O derives the exact path and is not card-lifecycle-gated, so it remains available after tombstone. No session directory is claimed or enumerated. Project-wide inventory derives eligible role candidates from each active card's one lifelong type in a fresh linked-card projection, probes only those exact files, adds exact `analyst:global`, and discards the projection. Those candidates are complete and there is no historical-role discovery; a changed-type card history fails strict stream validation first. `AnalystRuntime` owns at most one lazily created actor, and its operation boundary accepts no identity. There is no resolver, alias, safe-ID checker, identity cast, dynamic actor map, UI normalization, or external-chat package/config/composition surface.

Generic Agent successes are role-discriminated and preserve matching exact identities; conversation rows equal their enclosing identity and LLM-exchange success carries the selected `sessionId`. Raw Vue route input is parsed once through the shared parser before any detail component, store selection, REST call, or live-sync work. The exact union then flows through production props, API methods, stores, SyncClient maps, and subscription calls. Raw conversation frames are parsed before socket mutation or acknowledgement, and the same type flows from persistence through `ReadModelChanges`, `SyncHub`, and `LiveSyncSocket.invalidate`. The conversation publisher deliberately reparses even its typed message identity before emitting `conversation_changed`; the event registry validates the same union. `mapLiveSyncEvent` still does not map that event, avoiding a duplicate path: owner-driven read-model changes remain authoritative for conversation invalidation.

Runtime composition captures autonomous current-role snapshots and the already-created Analyst current-operation snapshot into one validated immutable map before any conversation probe/read. Autonomous exposure is gated by the existing pending operation, active processor state, and one current LLM reference; planner/reviewer handoffs mutate only that reference. Each current LLM owns active or one exact wait barrier. Invocation contexts carry canonical session/source/call/tool identity, and segmented callbacks wrap only unfinished process, public-fetch, or child-settlement promises. `CardActor` remains the sole ordinary/restart structural-child authority; ordinary relationships include invocation identity, while restart relationships do not produce session waiting.

After capture, aggregate acquisition strictly reads every listed conversation and enforces complete snapshot joins. Direct acquisition exact-probes and reads only its requested path, including tombstoned history, and ignores unrelated snapshot completeness. One pure exact-ID projector serves both. Call-row publication precedes barrier installation, so a frozen waiting snapshot safely joins the subsequent synchronous read and cannot be revised by a later transition. Conversation-first capture, per-row recapture, aggregate membership checks for direct reads, synthetic Analyst rows, card-status liveness, public internal-phase mapping, leases, registries, publication boundaries, and persistence generations are absent.

Runtime status has no agent array. The chat handler passes through a present shared Analyst projection and maps only exact absence to null session, empty entries, and inactive activity. The web subscribes immediately, starts detail and list independently, and routes every detail trigger through one store-local latest-request owner. Acknowledgements, aggregate list rows, optimistic messages, and request-local sending state are not authoritative session or activity sources.

Each role, Analyst turn, compactor summary call, repair, and continuation uses a fresh opaque UUID `source_input_id` generated by its live owner. Tool identities derive only from the original source UUID `S` and provider tool-call ID `T`:

```text
${S}:tool-call:${T}
${S}:tool-result:${T}
```

The next provider UUID is unrelated. Provider attempt indexes order attempts within one invocation only. `ProviderConversationProjection.sourceSessionId` is the stable identity of the validated source conversation; `LlmInvocationInput.inputId` is the fresh identity of one logical provider call, and `LlmInvocationInput.sessionId` owns invocation logging and any newly persisted turn rows. For every ordinary persisted planner, reviewer, executor, or Analyst call, `LLMActor` requires invocation session equality with the projection source session before the pre-provider hook and requires it again on the hook result before turn-start append, candidate admission, or provider use. A mismatch fails without relabeling rows or either identity.

Round summarization is the explicit structural exception. Its dedicated provider path persists no invocation or completion rows to the actor conversation, so the synthetic `summary:<round>` invocation label and fresh input UUID remain distinct from the stable actor source session carried by the projection and its rows. Merge summarization renders ordered summaries directly into provider input under the non-conversation `summary:merge` invocation/evidence label; it does not construct an `AgentMessage` or weaken the durable conversation grammar.

Explicit Run follows canonical committed child links to select the complete project-rooted running chain without installing actors. More than one running child or malformed/discontinuous data fails before reset. Participants are handled leaf-to-root. Planning participants stabilize planner then reviewer; terminal participants stabilize executor. Empty, system-only, settled-terminal, and exact settled-recovery sessions are read-only. Tool-pending receives interrupted `outcome_unknown:true` plus notice; provider/text-pending receives the notice only. Unmatched `activate_card` is always ordinary interruption, regardless of a referenced child's status; no child outcome is reconstructed or replayed.

Every non-clean session and settled-recovery recognition binds to the strictly validated latest `activation_open` role/card/session/input association. The notice derives `${inputId}:model-recovered` and its deterministic pre-round and settles only as the final canonical source row after that marker. Malformed association, collision, or newer same-activation work fails directly. Append error permits no same-attempt read or later effect.

After all conversations stabilize, the supervisor calls `stopRunningForRecovery` leaf-to-root, then calls `activateStopped` only for project. The former requires running and has only the reset call site; the latter requires stopped and is also used by planner activation of an exact stopped child. This recovered-chain path explicitly selects `STOPPED`; it does not invoke the nullable mapper for an already-running prepared/restarted/structural chain. Generic setStatus/mutation excludes both running-to-stopped and stopped-to-running. A status append failure leaves a valid partial prefix; a later explicit Run freshly selects the remaining running prefix or stopped project. There is no actor reconstruction, structural wait installation, transaction, rollback, retry, generation, or graph-position recovery.

## 6. Notifications And Terminal Arbitration

Notifications persist only in the target card's ordered `pending_notifications`. The durable request identifies one `card_id`; no role/session recipient or session-delivery result exists. `backlog`, `changed`, `running`, `blocked`, and `stopped` preserve pending context. Only `done`, `failed`, and `cancelled` clear and reject it with `terminal_card`.

Planner, reviewer, and executor share one append-before-remove path. Node-entry context appends the selected ordered bodies before removing their IDs. At each result candidate gate, the node captures one ordered set and, when non-empty, appends failed paired evidence with `pending_notifications`, those exact bodies, and the resolved correction before removing exactly those IDs in `afterAppend`. Any append failure removes nothing; later arrivals are not in that selection and remain for the next candidate. The failed result is an unfinished same-node continuation for recovery classification, never a clean terminal or reviewer deferral.

With no pending context, reviewer semantic currentness may still reject. It discards the stale open review, captures refreshed exact context and its semantic snapshot as one pair, appends that context, replaces the comparison snapshot, and continues the same node. Accepted `revision_required` closes and settles review evidence, cleans the reviewer node, and routes through ordinary graph transition context to the configured planner target.

## 7. Runtime Controls

Runtime lifecycle is process-local. Startup is stopped. `startApp()` derives an immutable `{pid, startedAt}` identity from the exact acquired lifecycle-lock handle and passes it as required data through server and runtime composition to the supervisor; no production clock or process fallback constructs it. Run preparation performs mutation-time full-chain reset and top STOPPED admission and returns one opaque one-shot launch plan while status, run identity, and active leaf remain stopped/null. Launch consumes and validates that plan, installs project ownership, then publishes run identity, running status, and `ActiveCardLeaf` before configured-node execution and the successful Run result. An installed instance is starting, running, pausing, paused, or closing.

Application composition exposes the same `RuntimeControlService` instance as the full `RuntimeApi` and the narrowed runtime-control port. The supervisor remains the mechanics and opaque launch owner, while the application service coordinates intervention readiness without reading or transforming a projection. Analyst tool broadcasts publish their sanitized payload directly to the application event bus. `RuntimeControlService` has no runtime-state field or replacement cache. The supervisor alone owns lifecycle status and gate mutation. Pause returns only whether the frontier already settled; Resume accepts and returns no state. Every runtime-state read is freshly built from supervisor status, injected lock identity, `ActiveCardLeaf`, and the observation clock. Compact status uses the same identity/currentness and the installed actor maps. Neither read enumerates cards, children, ancestry, history, or conversations/sessions; direct reads of already-installed card actors remain valid, while durable running-chain scans stay confined to mutation-time preparation and continuation. Pause uses one boolean and at most one parked frontier; admitted synchronous settlement may finish, but no fresh provider/tool/process/child/reviewer admission begins until Resume.

The operation-specific REST contracts are distinct: Pause, Resume, and `stop_project` declare no request body, while `restart_server` declares the strict exact `{confirmation:'RESTART SERVER'}` body. The three bodyless handlers inspect the raw request first and locally return their declared 400 validation envelope for every defined body before invoking runtime control; this is not a shared `ContractRuntime` parser policy. Clients emit JSON `Content-Type` only with an actually serialized JSON body. Authentication and ordinary headers remain independent, so bodyless Stop retains them without advertising JSON.

Run validates and resets the unique contiguous project-rooted running chain before actor admission. It then installs one fresh process-local project `CardActor` and selects STOPPED; descendants stay stopped until an ordinary live planner explicitly activates one. The micro-actor lifecycle has only initial-state `start()` and no recover or rehydrate entrypoint. For a non-cancellation outcome, `CardActor` synchronously performs one durable publication, finalizes activation fields and queues `settled`, invokes the supervisor's identity-checked natural release from both maps outside closing, and only then resolves the deferred caller. Queued actor-state consumption is presentation cleanup rather than domain authority.

A throw from replacement or a synchronous post-publication callback leaves canonical visibility outcome-unknown. `CardActor` fails in place without retry, reread, reconciliation, further lifecycle write, deferred caller settlement, or natural release, even if a later observer can see the terminal version. A later Stop may contain the claimed result and aggregate-clear process-local ownership without inferring or reporting a durable outcome.

`stop_project` is restartable non-domain containment, never cancellation. It closes global continuation/admission and freezes both complete ownership maps before first-claim classification. Open owners receive one identity-preserved `RuntimeStoppedInterruption`, use aborting tracker revocation, and preserve durable `running` state. Result winners are not reclaimed or aborted: Stop non-abortively closes processor-operation and LLM-invocation admission with that same interruption, permits already-admitted winner delivery, cleanup, and `CardActor` publication to finish, then joins the closed trackers and suppresses later continuation. A cancellation winner is likewise not reclaimed or aborted: Stop starts or joins its cached actor-local cancellation promise and waits for `finishCancellation()` to publish `cancelled` and settle its caller. While the runtime is closing, result and cancellation settlement do not invoke natural release and leave both ownership entries installed for the supervisor. LLM, processor, card, structural-parent, child-tool, and root catches rethrow the exact Stop interruption rather than mapping it to domain failure. Cancellation-settlement, cleanup, and process failures side-report to one Stop-local collector and cannot replace a committed winner. Only after every owner settlement succeeds does the supervisor atomically clear both frozen maps and the current instance; this aggregate clear is separate from per-actor natural release. Otherwise one `RuntimeContainmentError` leaves both full closed maps and the runtime closing. Stop itself writes no card/root outcome or event.

The negative terminal call graph is explicit: `App.stop()`/signals/startup failure/acknowledged restart → sole App terminal coordinator → flat admission closers and cleanup leaves; no edge reaches `stopProject`, cancellation, `RuntimeContainmentError`, or the Stop collector. The coordinator tries every closer synchronously before its first await, then sequentially settles reverse-registration-order leaves through one referenced ten-second bound. Rejection/timeout records only fixed allowlisted component+code data and never skips later leaves. Direct `App.stop()` returns an immutable `ShutdownReport` and does not log; process-boundary adapters log fixed warnings and preserve exit/restart/original-error behavior.

Process cleanup has one `ProcessRunner` and one registry with sibling `runtimeRootScope`, `analystRootScope`, and `mcpRootScope`. The registry owns child-event safety immediately when platform spawn returns and attaches its mandatory `error` listener before inspecting the leader PID. It admits a group only with a positive leader PID; after admission, `ProcessRunner` owns output and user-facing process presentation. A rejected child can therefore emit its asynchronous OS launch error without escaping the already-handled launch failure. For stdio MCP children, stdout remains the protocol channel; the MCP runtime continuously drains and discards child stderr for the child's lifetime. Stderr content is neither retained nor exposed, and the existing empty process-log placeholder remains unchanged. The sole runtime, Analyst, and MCP leaves each perform `close/revoke → one asserted owned-root termination call → initiate/continue joins → combined settlement`; termination starts before any await, so a hanging join cannot postpone it. A nonempty fulfilled `ProcessStopReport.failed` rejects the leaf. A timed-out component can continue only under its own root while later disjoint-root leaves proceed. Project Stop and App runtime cleanup may overlap on the runtime root, tolerating repeated signals and already-exited/missing/removal observations without locks, deduplication, shared promises, registry-wide drains, or collector sharing. LiveSync and Fastify are independent leaves; Fastify close does not dispose LiveSync.

The process tool passes each `run_command` command unchanged as one `bash -c` argument. ## 12. Reset And Failure Model

Durable-format changes require stopping the service, running the current built reset, and then starting the current binary. Directory-owned parent-local spreadsheet claims, the exact two-kind card stream, card records without `position`, complete parent-owned `children` membership/order, immutable card type across every card version, the ordered summary-group payload, minimal strict `applied_policy`, and marker-first/no-preamble Analyst source contract are such cutovers. Successful candidate `mkdir` consumes its segment even if later work fails, and only the parent's committed cumulative `children` snapshot grants and orders membership. Generated streams containing old `card-child-reservation` rows fail strict current-format reads. Every deployment resets its generated roots wholesale before the current binary starts, even when sampled or known card histories appear compatible; no compatibility detection exempts a deployment. Every later card version and tombstone retains lifelong type, so role/session projection cannot change; changed-type streams fail strict validation. Old generated rows, changed-type card histories, and pre-marker or mixed Analyst histories fail strict reads, and there is no migration, marker backfill, compatibility classifier/renderer, format probe, selective repair, or mixed-version operation. `resetOwnedGeneratedRoots()` in `src/persistence/layout.ts` is the singular reset ownership and initial-publication-presence contract: `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work`. Initial publication requires all four exact roots absent; retained partial state names its first blocker and requires stop, current-built reset, then retry. These generated roots are removed as whole trees without descendant inspection. Durable configuration and operator inputs under `.saivage`, including identity, credentials, prompt overrides, skills, and instructions, remain outside that ownership boundary, as do source and canonical documents.

The `.saivage/locks` namespace is the exceptional lifecycle-exclusion boundary, not reset-owned generated persistence. Reset acquires the exact canonical `runtime.lock`, removes the four complete roots, publishes the new `project` root card while still holding the lock, and then uses exact-owner release. A pre-existing exact lock blocks deletion. Lock siblings and every other outside-boundary path are neither discovered nor cleaned. Mixed-version operation and rollback against current-format state are unsupported.

Saivage file persistence does not guarantee no data loss. Interrupted external effects may repeat; notification context may duplicate; concurrent auth refresh may overwrite another change; incomplete card namespaces and publication temps may remain forever. Exact canonical corruption fails clearly for operator repair or reset rather than automatic recovery.
