# System Architecture

This document is the canonical architecture authority for Saivage v3. The current durable-format cutover is reset-only; old binaries, mixed formats, migrations, compatibility readers, bridges, and normalization paths are unsupported.

The exact card stream format is v2. Durable `CardRecord` snapshots contain one lifecycle authority at `lifecycle.status` and omit top-level status, parent, depth, and operator actions. The public ordinary `CardPatch` enumerates only ordinary mutable fields; dedicated semantic lifecycle methods construct a private discriminated lifecycle-write union consumed by one exhaustive writer. The former `CardWriteIntent`, broad lifecycle patch, post-pruning intent assertion, and dual status/lifecycle field set do not exist. Lifecycle history and narrow stopped replay change only `lifecycle` (plus actual status-text companions). Planner and Analyst creation schemas are strict, expose no status input, and delegate canonical backlog lifecycle construction to `CardService`.

Identity derives structural parent/depth but never membership. Disposable `CardIndex` projections follow each reached parent's committed `children` array and filter it to active records. Operator and tool convenience fields are separately named explicit projections. `CanonicalCardFilesReadModel`, through CardService's canonical projections and descriptor-backed snapshot, is the sole `.saivage/cards/**` Files path: it returns exact v2 bytes and propagates strict v1/old-shape failure without generic filesystem fallback. Full-chain recovery remains leaf-to-root with valid partial prefixes, but v2 replay recognizes lifecycle-only stopped transitions.

The supported runtime is Node.js 24 with npm `>=10 <12`, matching `package.json` engines and CI.

## 1. Ownership Model

The runtime is card-centered. The runtime alone dispatches work. Project/goal cards select the compiled planning graph and terminal card types select the compiled terminal graph. Lifecycle entry chooses a configured ordinary node; role order is not code-owned topology.

`CardActor` owns one live card activation. Its synchronous `open | claimed_result | claimed_cancel | claimed_stop` claim decides result, cancellation, and Stop ownership before any await. `CardProcessActor` directly extends `BaseActor` and owns activation tracking, LLM ownership, role handoff and join, and projection; its current actor state is the sole process position and there is no graph loop or cursor. One reusable `AgentNodeExecution` is its one-node helper and owns role surface, stable session, prompt, hidden correction, record, notification, terminal claim, and node-local cleanup behavior. It returns one accepted immutable result and never selects the next state or publishes terminal card lifecycle. `CardActor` is the sole non-cancellation outcome publisher and owns caller and activation-ownership finalization. The supervisor keeps one retained-actor map for process-local ownership and one exact-live-activation map for running cancellation resolution. A running card without exactly one live owner is impossible and fails fast; callers never fall back to direct cancellation.

Supervisor pre-admission and project-root preparation are the only root activation boundary. Root execution enters `CardActor` through the Supervisor-owned prepared-root lifecycle after project is running; a root caller on prepared input records execution provenance rather than admission authority. There is no recovered-descendant installation or restart lifecycle. Direct `CardActor.activate()` is exclusively the parent-child boundary and requires the parent planner's mutation capability to admit that exact immediate child. Every card is running before processor execution begins, and `CardActor` performs no actor-local root status write.

Cancellation first revokes provider, tool, child, reviewer, process, and callback admission. The cached actor-local cancellation promise runs `finishCancellation()` as the exact winner boundary: it contains activation-owned processes and exact live descendants, directly publishes the cancelled card, and settles its caller once. For natural result or cancellation settlement outside closing, the actor synchronously delegates its own identity to the supervisor. The supervisor requires that exact actor in both maps and removes both entries; mismatch fails fast. This release means the completed activation no longer has live ownership or a retained runtime projection. It does not certify or wait for the detached micro-actor object to consume an already-queued cosmetic `settled` or `cancel` event. A later legitimate activation constructs a fresh `CardActor` and processor. Already-done descendants remain done. This is process-lifecycle authority and reference release, not a persistence lock, queue, transaction, generation, or currentness mechanism.

Card status behavior is intentionally operation-named rather than one terminal taxonomy. The cards-owned `card-status.ts` implementation exports exactly four small predicates/effects, and `status-api.ts` is their singular cross-package entrypoint: `canCreateChildInStatus` admits backlog, changed, running, blocked, and stopped; `canCancelCardStatus` admits every status except done and cancelled; `acceptsCardNotifications` admits backlog, changed, running, blocked, and stopped; and `analystBriefEditEffect` preserves backlog/running/stopped, reopens blocked/done/failed, and rejects changed/cancelled. Role, root, runtime, type, dependency, and publication gates remain at their owning surfaces. In particular, Analyst create additionally rejects running, while blocked remains unresolved and parent-planner-re-enterable.

Status-to-process admission has one nullable mapper, `cardProcessEntryForStatus`: backlog maps to `BACKLOG`, changed to `CHANGED`, blocked to `BLOCKED`, stopped to `STOPPED`, and running/done/failed/cancelled to null. It grants no transition authority. The planner tool uses it after parent/dependency validation and before child lookup, so a non-activatable request cannot construct or register an actor. `CardActor.childCardActor()` enforces the same construction invariant: it returns an existing retained actor, fails fast for durable running without that owner, returns null for another non-activatable status, and constructs only an eligible non-running immediate child. Supervisor root admission and `CardActor.activate()` retain their own boundary checks. The Supervisor maps before its root status mutation and remains the sole root owner; `CardActor` maps before the parent callback, then requires that callback to have published running before claiming actor ownership. Stopped uses the dedicated `activateStopped()` write at both activation boundaries.

Each micro-actor receives one explicitly compiled immutable topology and one per-instance callback binding object. Fixed production topologies compile once at module initialization and are reused across instances; callback closures alone carry instance behavior. Topology contains only states and transitions: there is no class-static discovery, reflection, or state-named handler convention. `start()` assigns the initial state, invokes `enter` with the frozen start context, and, only when entry returns, starts the pump; it does not invoke `transition`, and a start-entry throw propagates synchronously. An external event transition freezes its context, then invokes `leave`, aborts and clears source-state tasks, assigns the target state, invokes `transition`, and finally invokes `enter`. Unknown events and ordinary non-reentering same-state transitions invoke no callbacks or aborts. Explicit same-state reentry follows the full external-transition order. An event callback failure uses the ordinary lifecycle-settlement failure path, with no fallback dispatch.

Other status decisions remain exact and local: running-chain membership is `status === 'running'`; dependency completion is `status === 'done'`; descendant completion is done-or-cancelled; activation settlement is done/failed/blocked with a distinct cancellation branch; deletion and Analyst reorder reject running; immediate-parent edit preserves backlog/changed/stopped, reopens blocked/failed, and rejects running/done/cancelled; and projected start admits only backlog/changed/stopped. Planner reorder is deliberately different from Analyst reorder: it may reorder the current running planner parent's children, whereas Analyst reorder rejects a running parent or running member of a requested child subtree.

## 2. Card Identity And Discovery

Card identity is `project` or one-to-five lowercase alphabetic hierarchical segments selected from a deterministic parent-local spreadsheet sequence. Every create starts at `a`; exact candidate namespace creation claims the segment, and only candidate `mkdir` `EEXIST` advances to the next segment. Collision handling never lists siblings or inspects the candidate. Parent, depth, namespace, exact card/record streams, and fixed-role conversation paths are forward-derived. `CardRecord` has no `position`. Backend `listChildren`, logical-path, reorder behavior, and web nested/direct-child projections follow each reached parent's committed cumulative `children` array order; active projections omit retained tombstoned links without changing that order.

One non-root attempt exact-reads and validates its linked parent, then exclusively claims `.saivage/cards/project/children/<s1>/.../children/<sn>/` for the first candidate whose direct `mkdir` succeeds. Its exact successful order is namespace claim → closed initial `brief.jsonl` and card-stream-format-v2 `card.jsonl` publication → complete-publication proof inside `publishInitialCard()` → fresh parent reread/admission → second complete-publication proof in `CardService` → one cumulative parent `children` append → parent `child_link` history, card, and runtime effects. Candidate-directory creation claims and consumes identity only; complete publication makes the child locally readable; the later single parent append alone grants linked membership and places the child at the end of semantic sibling order. A failure after successful claim ends that call and leaves the namespace consumed; a later independent attempt starts at `a` and advances only across opaque `EEXIST` candidates.

Successful-path visibility checks occur only after the confirmed parent-link append: they may read the child through the parent's link and linked list/tree projection. Readable initial child streams before that link are not accepted membership. If any append or replacement reports an error, its outcome is unknown and neither production nor verification may read, list, probe, retry, reopen, reconcile, reconstruct a reader, or inspect the affected canonical or domain artifacts to infer what committed; only required cleanup of the already-open descriptor remains permitted. Verification proves stopping, ordering, and descriptor cleanup from operation traces and proves effects or their absence from spies. Card-only readers derive the bounded root-to-target chain from the requested ID, validate each reached exact `card.jsonl` once, require the next ID in the active parent's committed `children`, and only then touch the exact `children/<segment>` component. They do not read a brief. Complete initial publication separately proves the required initial brief, and only an explicit authored-record resource reads and validates its selected `brief.jsonl`, `status.jsonl`, or `review.jsonl`. A terminal tombstone is the final row of `card.jsonl`: it makes that card absent from every card-domain detail/history/version/diff/record projection and terminates traversal before descendants. Direct exact-known conversation I/O remains a separate lifecycle-ungated path. Namespace-only, brief-only, temp-only, unlinked malformed, and arbitrary noncanonical entries are silent invisible orphans. They are never scanned for allocation, validated in aggregate, cleaned, warned about, adopted, quarantined, or repaired.

## 3. Direct File Persistence

Saivage-owned persistence is direct stateless synchronous file I/O by the domain or actor owner:

- `card-files.ts` owns direct deterministic child-namespace claiming, complete initial stream publication/proof, exact `card.jsonl` reads, append-only card versions/history, cumulative child links, and terminal tombstone rows.
- `authored-record-files.ts` owns exact append-only `brief.jsonl`, `status.jsonl`, and `review.jsonl` streams. The initial brief is closed logical version 1; status and review use their strict open/edit/terminal revision transitions. `readAuthoredRecord()` emits the concrete `AuthoredRecordNotFoundError` only for a cleanly absent card or selector after strict direct reads; malformed canonical data, required-file absence, I/O errors, and invariants retain their original failures. Optional runtime, workspace, and tool consumers catch only that concrete type.
- `conversation-file.ts` owns one stable append-only conversation per role session.
- `contracts/app-log.ts` owns the browser-safe strict unified app-log declarations for event, error, control-action, provider-exchange, and content-review entries. `persistence/app-log.ts` owns only their direct synchronous append/read mechanics and project-root-only context. Domain producers construct rows and own post-commit effects; the observability error producer alone owns its non-durable `ErrorInput` boundary.
- `ResolvedConfigAuthority` owns selected YAML document reads, effective validation, and config mutation orchestration; `config-file.ts` owns canonical atomic replacement.
- `auth-profile-file.ts` and `project-identity.ts` own their single canonical files.
- `runtime/lock.ts` is the exceptional process-exclusion boundary only.

`CardService` performs operation-local rereads and invokes these direct functions. Its common patch writer carries one private ephemeral five-way typed intent for ordinary mutation, set-status, terminal lifecycle commit, recovery stop, or stopped activation. The final writer asserts the real post-pruning patch against that intent; caller-supplied `reason` remains audit prose and never grants lifecycle authority. Trusted lifecycle methods select their runtime actor/surface and fixed reason internally. Terminal commit is a narrow running-only operation whose target is exactly `done`, `failed`, or `blocked`, whose complete strict lifecycle variant must match that target, and whose only optional companion fields are `status_text` and `status_text_updated_at`. In autonomous execution, `CardActor` is its sole production caller for non-cancellation activation outcomes. `validateCardStream()` accepts exactly contiguous `card-version` rows from version 1 followed by at most one `card-tombstone`; the tombstone is forbidden for root, must be the final physical row, and must exactly preserve the final card. It requires deletion-history `card_id` to equal tombstone `card_id`, deletion-history `changed_at` to equal `deleted_at`, and deletion-history `version_seq` to equal `final_card.version_seq`. It also owns the cross-version invariant that every full card version and tombstone retains the initial row's type. The ordinary `CardPatch` mutation contract excludes both immutable `type` and structurally owned `children`; generic mutation rejects an own `children` property before equal-value pruning for every caller and status. Creation's empty array, dedicated one-ID `child_link` suffix append, and dedicated reorder are the only `children` writers. The supported `setStatus('changed')` transition is the sole terminal-card reopening authority; there is no actor-owned reopening callback, terminal lifecycle repair, or admin-repair path. A disposable `CardIndex` may project one read, but it never authorizes a later write. There are no repositories, generic stores, persistence health latches, writer registries, queues, generations, transactions, repair orchestrators, or durable runtime owners.

The bottom-layer card schema keeps its notification-format invariant locally and imports no card behavior: complete done, failed, and cancelled records require empty `pending_notifications`, while backlog, changed, running, blocked, and stopped may retain them. This exact schema refinement intentionally duplicates the higher-layer notification predicate rather than creating a `schemas -> cards` dependency.

Planner child admission exact-reads the linked target and each dependency in declared order. It never invokes list/tree/index APIs and retains no authorization state. Linked-tree operations start at the exact root and recursively follow committed `children`; their disposable projection validates active dependencies and hierarchy and is discarded with the call. Multi-root deletion uses that one fresh projection to form a subtree union, reject permissions and surviving dependents, and topologically order dependent-before-dependency plus child-before-parent tombstones. This graph is call-local write admission, not persistence coordination.

The complete, duplicate-free cumulative parent `children` snapshot is the sole linked-membership and semantic-order authority, including retained tombstone links. A real active reorder uses one fresh operation-local parent/active-child projection, requires a duplicate-free permutation of the active IDs, and constructs one next parent snapshot with requested active IDs first and all retained non-active links afterward in stable prior order. It appends one parent version and never writes child streams. An active-order no-op has no append or effect, even when retained links are interspersed in the old complete order. Parent-local stream validation admits only a changed, same-length, same-membership permutation declared as a children-only reorder, with no other local field change; identity order, membership change, and piggyback mutation fail. Validation compares consecutive parent snapshots only and carries or derives no active/tombstone classification in history. Thus both the old and new complete parent rows are valid committed prefixes without reorder coordination.

The common planner request order is an exact linked target read → exact dependency reads in declared order with `done` validation → target-status admission → `children.get()`. It never builds or scans a tree/index. Non-activatable status rejects before lookup. After admission, `children.get()` may return an existing owner or construct and register an eligible non-running `CardActor`, construct its processor, and call the ready processor actor's `start()`; that lifecycle initialization is not processor activation or provider execution. Durable running without an existing retained owner fails invariant rather than constructing a replacement. An admitted new activation continues through the parent planner's required mutation capability with `running` status write → exact live-ownership claim → current-leaf transfer → `CardActor` running transition → processor activation/provider work. An admitted running join instead continues with `awaitSettlement()` and its parent `enterChild`/`resumeParent` relationship, without reactivation.

Dependency and non-activatable-status rejection precede `children.get()`. They therefore prevent both request-caused lookup-time construction/ready start and every later new-activation or join effect. This guarantee is attributed only to the rejected request: it neither revokes an already-running actor's owner nor stops or freezes its processor/provider work, which may settle independently. The rules add no scheduler, dependency traversal, status propagation, or cancellation behavior.

Every replacement and first JSONL publication calls `replaceFile`. It creates one fresh random UUID same-directory temp exactly once with `O_CREAT | O_EXCL | O_WRONLY`, writes and fsyncs it, renames over the target, and fsyncs the parent. A temporary-path collision or other failure propagates. Crash-left temps remain ignored forever. Publication-temp UUID generation and invocation UUID generation are distinct identity scopes; card identity instead comes from direct parent-local deterministic namespace claims.

All file, directory, append, and lifecycle-lock creation uses ordinary Node defaults filtered only by the process umask. No mode argument, chmod/fchmod, permission probe, or repair exists.

Growing canonical JSONL files use one result-bearing `appendEnvelope()` API: `appended` means write, fsync, and close all succeeded, while `missing` means only that the initial exact-path open returned `ENOENT` before a descriptor existed. Every caller handles both results explicitly. App log alone may use `missing` for one first-publication attempt; card, record, and nonempty conversation owners fail fast because their previously read append target must still exist.

Append acquisition uses `O_WRONLY | O_APPEND | O_NOFOLLOW | O_NONBLOCK` and descriptor metadata, never a path probe. The descriptor must be a regular file before any write. Every successful open has exactly one close attempt: an earlier stat/validation/write/zero-progress/fsync error takes precedence over close error, while a lone close error propagates, and close is never retried. The app-log writer validates and serializes only its incoming row and does not read existing bytes. Reader-local semantic indexes, global duplicate checks, and identifiable unterminated-suffix canonicalization remain strict full-read concerns and never authorize or prepare a write. Complete malformed data remains and fails; direct append never truncates an existing suffix.

The static `LoggedEvent` union and generated runtime event schema agree on all 12 current catalog variants, including conversation changes and the three replay-only appended-record variants. The intentionally open `runtime_actionable_error.actionable_error` remains `Record<string, unknown>` in both layers; UI presentation, not persistence or transport, supplies a fail-safe message when its nested message is unusable.

Provider-exchange publication policy belongs to its agent producer, not generic app-log persistence or the provider-exchange schema. Immediately before strict parse and append, a field-classified `provider.diagnostic` projection redacts descriptive contract/provider/model/account, finish/tool, and error text and recursively projects request-parameter values while preserving code-owned property names. It deliberately excludes exact session/source/output identities, generated log identity, attempt indexes, validated timestamps, discriminants, and non-string structure because those fields maintain durable linkage and ordering. Schemas validate the projected singular contract but never sanitize canonical bytes, and `app-log.ts` never guesses a sink policy.

`InvocationService` directly receives `ReadModelChanges` and alone owns app-log-driven Agent freshness. After each provider-exchange append returns successfully, it strictly checks `session_id` with the shared canonical conversation-session schema and invokes exactly one Agent hint only on success. A synchronous hint observer may strictly reread and fail after the physical commit; that failure propagates immediately without another append, hint, rollback, or later input attempt. Event, error, control-action, and content-review rows, `summary:*` provider evidence, other noncanonical provider identities, and failed appends publish no Agent hint. The internal `control_action_record_appended`, `event_log_record_appended`, and `error_log_record_appended` kinds have no current emit sites, but their exact schemas remain in the v1 catalog so existing complete durable event rows still replay strictly; removing those discriminators requires a reset-only format cutover. `control_action_recorded` remains the post-append control-action domain event.

## 4. Card-Process Compilation And Execution

Startup strictly parses required `card_processes.planning` and `card_processes.terminal` and compiles exactly one immutable actor topology/artifact per family before actor construction. Its states are `lifecycle:ready`, `entry:<port>`, `node:<id>`, and terminal `terminal:<port>`; accepted outcomes are `result:<outcome>` events, while `execution:failed` is the code-owned failed route. The compiled definition alone contains source/event/target/reentry topology. A same-node configured edge is explicit external `reenter:true`; business metadata contains node roles/prompts/records and optional transition prompts without duplicate targets or outcomes. Configured terminal reachability is validated before the failure route is added. Entries are exactly `BACKLOG | CHANGED | BLOCKED | STOPPED`; terminal ports are separately tagged `DONE | FAILED | BLOCKED`. Terminal edges cannot carry prompts, prompt identities may be reused, every node is entry-reachable and has a configured terminal path, planning nodes use planner/reviewer, and terminal nodes use executor.

Process prompt artifacts are exact `src/prompts/<card-type>/process/<identity>.md` defaults overridden only by `.saivage/config/prompts/<card-type>/process/<identity>.md`. The build copies the complete source default tree from `src/prompts` to `dist/prompts`; runtime composition explicitly selects the applicable source or packaged bundled root and supplies it to both the role-template and process-prompt registries. The post-build compiled-composition smoke protects the packaged-layout path. Startup also loads each effective role template, requires exactly one `{{contractDescription}}`, rejects the finite obsolete `emit_result.status`/terminal-status/fixed-result-list directives, and renders every configured card-type/role/node pair. This is a strict finite contract check, not a general prose parser. The bundled topology audit changes only the one-pass wording in all seven executor templates; planner/reviewer role-authority prose remains, and there is no startup topology linter.

`CardActor` passes only the pre-running-write lifecycle entry and compiled family to `CardProcessActor`. Per-instance `enter` and `transition` callbacks execute the shared family definition. Entry callback queues its sole route without I/O; node entry starts exactly one state task; every external ready/entry/node/terminal transition invalidates the runtime projection. The first entry-to-node route reserves ordinal `0`; only accepted node-to-node or explicit self-reentry advances it once. Executor owners are exactly `card-activation:<activationId>:node:0`, then `:node:1`, `:node:2`. `AgentNodeExecution` appends stabilization/role context, optional transition context, and node prompt in that order, derives the generated outcome contract from the definition, and keeps malformed/plain-text/record/notification/reviewer corrections inside that same state, ordinal, LLM session, and tracker operation. Promptless BACKLOG/CHANGED/BLOCKED entry adds no lifecycle wording. STOPPED adds only the fixed discarded-position statement before its required configured prompt.

`buildRoleSurface` is the single executable role-composition authority. Its role-discriminated input is narrowed by one exhaustive switch, whose literal provider arrays directly construct each role's providers in executable order; `buildInvocationSurface` preserves that order in the duplicate-free executable map. The separate `surfaceToolDefinitions` projection produces the operational wire array used for autonomous prompt rendering. Planner, Reviewer, and Executor append their sole `emit_result` contract tool only afterward, and that exact terminal-last final array is used for provider invocation and prepared compaction. Analyst prompt, provider, and prepared-compaction arrays remain the same operational terminal-free array.

One LLM options path carries the supplied ordered tool list to every provider transport. A non-empty list is sent with only `tool_choice: 'auto'` and `parallel_tool_calls: false`; an empty list omits the tool fields. There is no forced-name choice or provider terminal-phase path. New provider-exchange `request_params` retain transport-specific metadata but omit the obsolete `phase` key.

Routing occurs only when the matching activation-owned `ActivationOperationTracker` consumer synchronously stages the accepted result or failure and sends its actor event. Each raw node operation uses that tracker's `run`, and each completion/failure uses the matching `trackConsumer`; no result is staged before consumer admission. Activation trackers and provider invocation lifecycles remain separate semantic owners but compose one shared low-level FIFO contained-operation mechanism for wrapper settlement, consumer acknowledgement, close/revoke, join, callback failure, and abandoned raw reporting. Activation `run` is its admission boundary. Provider invocation `begin` instead admits one exact lease, so that lease's later `runExternal` remains allowed after non-aborting admission close; lease ownership/currentness remains invocation-local. This FIFO contract matches the single operation at each current owner frontier and is not generalized concurrent-operation correlation. Intermediate order is record close → accepted settlement → cleanup → raw return → consumer → actor transition/invalidation → target entry. Terminal order adds terminal entry and process-promise settlement before `CardActor` publication. Terminal state is deferred process settlement, not containment completion: the tracker, captured joining LLM actors, and join state remain reachable until Stop/cancel join outcome reporting. Thus a terminal transition cannot hide a failed consumer, abandoned raw operation, or delayed LLM settlement.

The operator LLM-exchange handler is a separate trust boundary. It recursively applies `operator.api` to the latest strictly read canonical payload and parses that projection before response, without rewriting persistence or reusing the producer policy. Its failure path emits only a stable generic API body and a stable log event containing the validated session and operation identifiers; no exception object, diagnostic message, malformed value, stack, or project path crosses either operator sink.

## 5. Stable Sessions And Full-Chain Recovery

Stable sessions are exactly `analyst:global` plus planner/reviewer/executor identities whose suffix is a hierarchical card ID. The dependency-low shared identity module owns the literal and role-correlated schemas, types, and parser. `AgentMessage.session_id`, persistence, actor/source classification, generic Agent and chat contracts, `conversation_changed` payload/log schemas, live-sync frames, and web contracts consume that one authority. Parameterized chat contracts compose the Analyst-only shared schema, while generic Agent route params compose the full conversation union. `ContractRuntime` enforces those request schemas before handler dispatch; handlers do not reparse or compare chat identity. Operation response inventories describe only selected-operation outcomes, while an unmatched HTTP route's ordinary `404` remains framework-owned. Card-role streams live at their card's fixed `conversations/<role>.jsonl`; the singleton Analyst stream is the fixed `.saivage/agents/conversations/analyst%3Aglobal.jsonl`. Direct known-session I/O derives the exact path and is not card-lifecycle-gated, so it remains available after tombstone. No session directory is claimed or enumerated. Project-wide inventory derives eligible role candidates from each active card's one lifelong type in a fresh linked-card projection, probes only those exact files, adds exact `analyst:global`, and discards the projection. Those candidates are complete and there is no historical-role discovery; a changed-type card history fails strict stream validation first. `AnalystRuntime` owns at most one lazily created actor, and its operation boundary accepts no identity. There is no resolver, alias, safe-ID checker, identity cast, dynamic actor map, UI normalization, or external-chat package/config/composition surface.

Generic Agent successes are role-discriminated and preserve matching exact identities; conversation rows equal their enclosing identity and LLM-exchange success carries the selected `sessionId`. Raw Vue route input is parsed once through the shared parser before any detail component, store selection, REST call, or live-sync work. The exact union then flows through production props, API methods, stores, SyncClient maps, and subscription calls. Raw conversation frames are parsed before socket mutation or acknowledgement, and the same type flows from persistence through `ReadModelChanges`, `SyncHub`, and `LiveSyncSocket.invalidate`. Application composition installs one narrow conversation-entry observer that maps its exact five metadata fields to the validated `conversation_changed` event. `mapLiveSyncEvent` still does not map that event, avoiding a duplicate path: owner-driven read-model changes remain authoritative for conversation invalidation.

Runtime composition captures autonomous current-role snapshots and the already-created Analyst current-operation snapshot into one validated immutable map before any conversation probe/read. Autonomous exposure is gated by the existing pending operation, active processor state, and one current LLM reference; planner/reviewer handoffs mutate only that reference. Each current LLM owns active or one exact wait barrier. Invocation contexts carry canonical session/source/call/tool identity, and segmented callbacks wrap only unfinished process, public-fetch, or child-settlement promises. `CardActor` remains the sole structural-child authority, and each ordinary relationship includes its invocation identity.

After capture, aggregate acquisition strictly reads every listed conversation and enforces complete snapshot joins. Direct acquisition exact-probes and reads only its requested path, including tombstoned history, and ignores unrelated snapshot completeness. One pure exact-ID projector serves both. Call-row publication precedes barrier installation, so a frozen waiting snapshot safely joins the subsequent synchronous read and cannot be revised by a later transition. Conversation-first capture, per-row recapture, aggregate membership checks for direct reads, synthetic Analyst rows, card-status liveness, public internal-phase mapping, leases, registries, publication boundaries, and persistence generations are absent.

Runtime status has no agent array. The chat handler passes through a present shared Analyst projection and maps only exact absence to null session, empty entries, and inactive activity. The web subscribes immediately, starts detail and list independently, and routes every detail trigger through one store-local latest-request owner. Acknowledgements, aggregate list rows, optimistic messages, and request-local sending state are not authoritative session or activity sources.

Each role, Analyst turn, compactor summary call, repair, and continuation uses a fresh opaque UUID `source_input_id` generated by its live owner. Tool identities derive only from the original source UUID `S` and provider tool-call ID `T`:

```text
${S}:tool-call:${T}
${S}:tool-result:${T}
```

The next provider UUID is unrelated. Provider attempt indexes order attempts within one invocation only. `ProviderConversationProjection.sourceSessionId` is the stable identity of the validated source conversation; `LlmInvocationInput.inputId` is the fresh identity of one logical provider call, and `LlmInvocationInput.sessionId` owns invocation logging and any newly persisted turn rows. For every ordinary persisted planner, reviewer, executor, or Analyst call, `LLMActor` requires invocation session equality with the projection source session before the pre-provider hook and requires it again on the hook result before turn-start append, candidate admission, or provider use. A mismatch fails without relabeling rows or either identity.

Round summarization is the explicit structural exception. Its dedicated provider path persists no invocation or completion rows to the actor conversation, so the synthetic `summary:<round>` invocation label and fresh input UUID remain distinct from the stable actor source session carried by the projection and its rows. Merge summarization renders ordered summaries directly into provider input under the non-conversation `summary:merge` invocation/evidence label; it does not construct an `AgentMessage` or weaken the durable conversation grammar.

Explicit Run follows canonical committed child links to select the complete project-rooted running chain without installing actors. More than one running child or malformed/discontinuous data fails before reset. Participants are handled leaf-to-root. Planning participants stabilize planner then reviewer; terminal participants stabilize executor. Empty, system-only, settled-terminal, and exact settled-recovery sessions are read-only. Tool-pending receives interrupted `outcome_unknown:true` plus notice; provider/text-pending receives the notice only. Unmatched `activate_card` is always ordinary interruption, regardless of a referenced child's status; no child outcome is reconstructed or replayed.

Every non-clean session and settled-recovery recognition binds to the strictly validated latest `activation_open` role/card/session/input association. The notice derives `${inputId}:model-recovered` and its deterministic pre-round and settles only as the final canonical source row after that marker. ## 12. Reset And Failure Model

Durable-format changes require stopping the service, running the current built reset, and then starting the current binary. Directory-owned parent-local spreadsheet claims, the exact two-kind card stream, card records without `position`, complete parent-owned `children` membership/order, immutable card type across every card version, the ordered summary-group payload, minimal strict `applied_policy`, and marker-first/no-preamble Analyst source contract are such cutovers. Successful candidate `mkdir` consumes its segment even if later work fails, and only the parent's committed cumulative `children` snapshot grants and orders membership. Generated streams containing old `card-child-reservation` rows fail strict current-format reads. Every deployment resets its generated roots wholesale before the current binary starts, even when sampled or known card histories appear compatible; no compatibility detection exempts a deployment. Every later card version and tombstone retains lifelong type, so role/session projection cannot change; changed-type streams fail strict validation. Old generated rows, changed-type card histories, and pre-marker or mixed Analyst histories fail strict reads, and there is no migration, marker backfill, compatibility classifier/renderer, format probe, selective repair, or mixed-version operation. `resetOwnedGeneratedRoots()` in `src/persistence/layout.ts` is the singular reset ownership and initial-publication-presence contract: `.saivage/cards`, `.saivage/agents`, `.saivage/logs`, and `.saivage/work`. Initial publication requires all four exact roots absent; retained partial state names its first blocker and requires stop, current-built reset, then retry. These generated roots are removed as whole trees without descendant inspection. Durable configuration and operator inputs under `.saivage`, including identity, credentials, prompt overrides, skills, and instructions, remain outside that ownership boundary, as do source and canonical documents.

The `.saivage/locks` namespace is the exceptional lifecycle-exclusion boundary, not reset-owned generated persistence. Reset acquires the exact canonical `runtime.lock`, removes the four complete roots, publishes the new `project` root card while still holding the lock, and then uses exact-owner release. A pre-existing exact lock blocks deletion. Lock siblings and every other outside-boundary path are neither discovered nor cleaned. Mixed-version operation and rollback against current-format state are unsupported.

Saivage file persistence does not guarantee no data loss. Interrupted external effects may repeat; notification context may duplicate; concurrent auth refresh may overwrite another change; incomplete card namespaces and publication temps may remain forever. Exact canonical corruption fails clearly for operator repair or reset rather than automatic recovery.
