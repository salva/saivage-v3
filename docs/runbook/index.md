# Saivage Operator Runbook

Status: current operator procedures for runtime maintenance.

## Activation ownership and runtime halt

Supervisor startup begins in internal `uninitialized`, strictly validates the project root and initial empty ownership/gate state, and transitions its one status field to public `stopped` only after success. Startup failure leaves it uninitialized, rejects Analyst intervention, and prevents server services from returning or a listener from being published; public runtime-status reads are unavailable in that internal state. Do not confuse this process-local admission with HTTP health readiness at `GET /health/ready`.

After startup, Analyst mutation admission is derived at invocation from that one status: `stopped` and settled `paused` admit; `starting`, `running`, `pausing`, `closing`, and `error` reject. Accepted Run first installs a prepared root owner and reports `starting`; the singular ordinary halt can freeze it before launch. Application shutdown permanently closes Run admission. A lifecycle publication that becomes outcome-unknown reaches the fatal boundary and exits before Supervisor halt, cleanup, or a `closing` status. After positive dead-owner verification and explicit manual lock repair, a genuinely new process may use ordinary Run to execute full-chain stopped recovery. Run completely validates the canonical linked running set, then handles each selected card leaf-to-root by stabilizing all of that card's configured sessions and immediately publishing that card stopped before advancing. A `model_recovered` notice has no resume or redispatch authority; descendants become eligible only through later ordinary immediate-parent activation. Startup itself neither performs this topology rejection nor settles cards: explicit Run remains the corrective owner. Ordinary Stop, application close, and actor-main containment continue to use the retained halt and `error` behavior. There is no separate readiness state or initialization flag.

Pause is cooperative and run-scoped. Natural root completion can win from running, pausing, or paused; its stopped transition clears the old Pause request and callback before publication, so a later gate wait cannot emit paused for the old run. Project Stop and application close join one halt identity, interruption, owner snapshot, set of processor joins, and runtime-process termination. Application close additionally closes admission permanently. Concurrent callers never conflict or repeat cleanup. Retained historical Planner control-action rows remain readable, while current Planner reorder/notification operations append no control action.

## Prepared conversation compaction

Before startup, provide `compaction.enabled: true`, `context_utilization_fraction` in `(0,1]` (default `0.80`), `trigger_fraction` in `(0,1]` (default `0.90`), `tail_fraction` in `0..trigger_fraction` (default `0.25`), and one exact structured `summarizer_candidate: { provider, account, model }` emitted by the configured Provider Registry. Removed absolute-budget, completion-reserve, merge/summary, and escalation keys are invalid; stop the service and rewrite YAML to the current singular contract rather than expecting aliases. This policy-only cutover changes no durable format and requires no generated-state reset. `account: null` means the provider-level implicit account; explicit `"_implicit"` and `"_"` remain distinct exact names. Slash-bearing model IDs are ordinary data.

For each participating route, startup binding computes `floor(context_utilization_fraction * contextWindowTokens) - max_tokens` for capacity-eligible configured candidates and freezes the largest positive result for preventive preparation. Actual primary admission measures each candidate's complete serialized request against that candidate's own result; a fitting large candidate can execute while a smaller fallback is excluded. If only the large candidate fits and becomes unavailable, normal wait/failure behavior applies—Saivage does not compact merely to restore the small fallback. Larger windows can materially increase request cost and latency. The fixed summarizer independently computes the same formula with its declared window and 2,000 output tokens (94,000 input tokens for a 120,000-token window at `0.80`). Startup checks only the invariant empty refine wrapper; actual orientation and accumulated history are admitted when used.

Startup acquires lifecycle exclusion before full selected-config/environment validation, then validates before any `--create-runtime` canonical root-card read, cards-directory creation, or initial publication. Invalid compaction configuration or unusable participant capacity releases the lock through ordinary startup cleanup and creates or changes no generated root-card state.

## Startup command inputs

The CLI parses each command's options once, strictly, and uses the resulting typed start inputs for both pre-lock intent and complete environment loading. `init` accepts only `--profile`. `start` accepts only `--host`, `--port`, `--config`, `--project-root`, and boolean `--create-runtime`. `status`, `pause`, `resume`, `stop`, `restart_server`, `reset`, and `help` accept no options. Unknown or inapplicable options, positional arguments, missing values, and every repeated singleton—including equal repetitions and mixed `--name value`/`--name=value` forms—fail before lock or write effects. The [system specification](../spec/system-specification.md#8-lifecycle-lock-and-cli) owns the exact project-root, config-path, host, and port precedence chains and their selected-raw-value validation rule.

Service authors should set only the inputs their deployment owns, keep the project root and selected YAML path explicit where working-directory assumptions would be ambiguous, and pass bearer credentials through the environment or a deployment credential file rather than CLI arguments or URLs. `NODE_ENV`, `LOG_LEVEL`, and `SAIVAGE_API_TOKEN` are independent environment-only inputs, not alternate sources in the four selection chains.

Card admission includes generated `emit_result` even when the configured operational list is empty; Analyst admission excludes it. Correct the current route/provider capabilities or scoped tool list and restart. Credential validity, network availability, and cooldown remain real-invocation concerns, not startup probes. After binding, every configured participating named agent—discovered from every node of every selected compiled graph, with Planner/Reviewer/Executor only the default names—prepares its exact static instruction prefix and installed ordered tools before any durable record, session, transcript, or notification effect. Each card node retains the unchanged full canonical `{cardId,cardType,title,brief}` block from the complete accepted configured bootstrap content and follows it with one retained block containing a minimal label plus the unaltered full prompt selected by the actual compiled process/node. Analyst instead prepares the exact rendered prompt and bounded orientation snapshot before appending the current submission. Initial calls and every tool, notification, repair, pinned, preventive/local-compaction, and authoritative-recovery continuation retain those exact frozen blocks while refreshing only canonical history; they do not reread current card/tree state. A later node prepares anew. The static role instruction/generated outcome contract is sent exactly once at the instruction position, tools remain in their compiled contract, and the frozen blocks follow once in prepared order. Restoring the complete blocks can expose a real request-capacity failure: raise the actor budget or reduce the legitimate prompt/tool/context surface; do not expect previews, truncation, omission, clamping, or an unprepared fallback.

Current-node text is request-only and no longer creates a durable conversation row. Existing node-looking rows remain unchanged ordinary history and are not used to select graph position. One composition-owned boundary separates prepared context from conversation context and labels only the accumulated history as `Historical summary:`; replay alone proves neither transition nor approval. Existing entry/edge/correction/recovery rows and one-time transition handoffs remain durable under their current contracts, and still-applicable requirements do not expire merely because delivery was one-time. These composition bytes participate in exact request admission and in summarizer request overhead; the 16-call bound does not reserve capacity for them or guarantee fit.

Compaction publishes a new immutable JSONL segment and atomically replaces its cumulative conversation index; it never appends metadata to the source segment. The new segment starts with self-contained compacted genesis carrying one accumulated summary, fixed-size coverage and disposition commitments, exactly two nullable bounded required-model-fact slots (latest recovery notice and latest covered refusal), an exact predecessor/tail commitment, and either `between_rounds` or minimal inherited `{marker_id,input_id,active_segment_kind}` continuation. Genesis is operator context, not a transcript row or cursor. Providers receive the derived synthetic accumulated-summary context but never inherited IDs. Validated coverage is the sole omission authority: uncovered summary-only/evidence-only bundles and closed rounds below the trigger remain fully visible, and only successful summary reduction plus validated coverage omits a row. The predecessor remains historical and is never needed to validate, project, compact, or recover current; the next compaction inherits the accumulated summary rather than reopening it. Row omission follows append-order call/result policy authority with fixed per-surface evidence modes—mutable current discovery surfaces are observational, and only the dedicated immutable readers `get_card_version` and `read_record_version` emit canonical locators. Provider tool definitions carry no internal policy; the compiled invocation tool contracts keep it settlement-side, and exact adapter request admission measures the serialized provider request that is actually sent. Exact post-compaction recovery/refusal behavior keeps each code-owned text bounded and newest-only: the latest covered refusal locator resolves to the synthetic compacted fact and a superseded marker is no longer a current locator. The orientation and content commitments are distinct: the Analyst snapshot's complete-observation hash commits to the full strict observation even when the bounded rendering omits branches, while the content hash covers exactly the rendered bytes. Selected-graph participant reserve diagnostics report every configured agent actually participating in the selected compiled graphs, including specialized nodes. Candidate admission remains a deterministic best-effort estimate of one canonicalized complete body (`ceil(UTF-8 bytes / 4)`).

There are two exact protections for prepared configured card-node and Analyst provider turns. Preventive compaction runs before provider I/O when the prepared threshold requires it, including the initial Analyst call and every accepted or rejected-tool continuation after its canonical result and refreshed projection. Separately, exact local admission runs before turn-start and primary I/O for every ordinary route pass: each candidate is built, canonical-serialized, and capability-classified exactly once, and only admitted retained bytes are ever sent. Distinguish terminal ordinary local exact-admission failure from provider-reported context exhaustion. A local admission failure is a pre-provider configuration failure with bounded fixed capability/declared-limit/usable-input/request-size reasons, zero provider attempts for the rejected route pass, and one bounded local compaction already attempted only where at least one capability/output-compatible candidate was size-fixable; it never becomes a provider failure kind. Provider-reported context exhaustion instead has a real recorded provider attempt and at most one exact-admitted authoritative compacted retry using the retained original membership and process-local state: the context-failed member is retried first with the compacted bytes, earlier rate-limited or temporarily unavailable members and later untried members remain viable under existing scheduling, and exhausted members and originally rejected identities are never rebuilt. For an Analyst continuation, the already accepted tool effect, activity broadcast, and one canonical result are outside this provider seam and are never replayed or duplicated. A second context rejection after the authoritative retry, or a second no-fit after the one local compaction, is terminal: there is no third pass, second compaction of either kind, or route-by-compaction retry fan-out. Existing non-context routing/retry behavior is unchanged.

Current `glob` and `grep` calls limit each complete settled success result to the requested 512–32,768-byte envelope and expose stateless `matches.next` continuation. This reduces new search-result amplification but does not prevent compaction caused by accumulated history. Historical search results remain opaque durable JSON and are not rewritten or retroactively bounded; no reset or search-specific repair procedure follows from this current producer change.

The content-policy pin has separate canonical behavior. The pin purely preflights the one refusing candidate; an ineligible or oversized preflight result terminates without local compaction, candidate substitution, wait, or any provider I/O for the pin. After the sole admitted pinned call, every non-refusal failure—including `input_context_exhausted`—terminates without suspension, authoritative compaction, retry, failover, or a third call. The actor alone combines and reindexes the original ordinary-refusal attempts followed by the sole pinned-attempt evidence; that combination is evidence composition, not retained execution state.

Only exact direct structured code/type/param evidence from an eligible parsed HTTP 400, failed Responses terminal object, or Codex error/failed event authorizes this recovery. Message wording, nested markers, malformed responses, generic token language, and output-token exhaustion do not. An error received after an HTTP stream opens retains the actual opened HTTP status, normally 200, even when typed as input-context exhaustion.

For authoritative recovery or local exact admission, successful construction with no smaller selected endpoint returns clean `no_smaller_projection`, publishes no successor, and makes no primary retry. Preventive compaction may continue with a strictly shrinking hard-budget-fitting candidate above its desired trigger; a later genuinely refreshed turn may compact again. Summary prompts target 12,000 UTF-8 bytes normally and 6,000 for the single stronger regeneration, but neither value is a validity ceiling or progress guarantee. Complete nonempty prose remains valid above target and may mention recoverable evidence. Empty/tool/Chat-length output is eligible for one correction; refusal text is never used or regenerated, though an already complete eligible candidate may survive refusal. Unknown/inconsistent Chat completion metadata is terminal. Cancellation, summary-evidence publication/projection, publication-unknown, strict source/projection/hash/invariant, and append failures retain their owning identities. An append or publication-unknown result must not be inspected or retried.

Summary calls use the fixed configured candidate and ordinary Invocation Service transient recovery. Within one compaction, only one refine call is in flight and at most 16 logical calls occur across both endpoints and the at-most-one correction. Correction regenerates the latest genuine fold from its pre-fold inherited summary and identical source ranges with fresh exact admission; it never summarizes rejected text or drops source. The heuristic packer can still fail, 16 calls can take minutes, and neither target nor bound guarantees fit, progress, or quality. Selected Agents and Debug conversation detail continue to show only completed logical calls, in-flight state, and elapsed time. Fixed reason/count/available-measurement diagnostics apply only to owned non-provider construction failures. Required-model-fact slots fold a superseded slot's meaning before replacement, while unchanged slots remain newest-only.

During last-chance recovery, if summary provider exhaustion occurs after summary evidence publication, Saivage publishes the original triggering planner context-failure attempts exactly once under the planner input and then throws the narrow non-provider `LastChanceSummaryProviderUnavailableError` with its unchanged safe generic message and the exact summary failure as cause. Provider exhaustion, including typed capacity/refusal, does not expose construction reason/count diagnostics or enter normal primary-context failure. Triggering-attempt publication failure or uncertainty supersedes it. This source behavior changes no durable format, requires no reset, and performs no deployment action by itself.

Every Analyst submission is one current-format source round. Its first row is the exact system/activity marker `{event:'activation_open',agent_name:<configured-analyst>,input_id,timestamp}` with no `card_id` and no preceding preamble. Ordinary submissions append `[marker, workspace-context system text, operator user text]` in one batch before canonical reread and preventive compaction; confirmed restart appends `[marker, user confirmation]` and stays model-free. The next marker completes the preceding round; the newest remains open unless the furthest selected safe fallback covers a settled atomic prefix. Existing marker-first reset rules are unchanged.

Analyst primary and continuation calls use the configured global Analyst agent's compiled model route. Summary calls remain the distinct direct, nonpersisting exception: they use only the one fixed Registry-validated configured candidate, a 2,000-token completion request, no tools and no exclusive-tool-choice requirement, separate evidence identities, and no self-compaction or replay. There is no manual compact action or live `compacting` phase; selected read-only conversation detail alone may show the ephemeral progress described above.

## Trusted failed-root reopening and restart

Use this dangerous normal-surface procedure only for a diagnosed incident after an explicit determination that ordinary `reopen_card` followed by a new Run is appropriate. Require the current same-format build, a strict failed root, stopped or settled-paused intervention admission, a verified lifecycle owner and its published control authority, and positive evidence that no card process is running. Record deployment identity, incident cause, and incident-specific counts outside this reusable procedure.

From the selected current configuration and the root card type's compiled workflow, derive every distinct named agent that participates in the root process. For each derived participant require the deterministic card-scoped root session `agent:<configured-agent-name>:project`. Add the independently configured `analyst_agent` global session `agent:<configured-analyst-name>:global`. Every member of this derived set must have complete settled canonical conversation state, and the configured global Analyst conversation must specifically have no unmatched final call. Do not enumerate conversation directories or infer participants from bundled default role labels; Planner and Reviewer are examples in bundled defaults, not an exhaustive prerequisite.

Freshly capture the strict canonical active-linked-card projection without enumerating directories. Before each submission, re-establish the failed or changed root state appropriate to that step, the derived complete settled sessions, the unchanged projection, stopped or settled-paused runtime, the same verified lifecycle owner/control authority, and no running card process. Reopening must preserve every projected identity, link, membership relation, and semantic order. Do not read or mutate the root brief; reopening requires no brief content, head, or version assertion.

1. Send one Analyst submission requiring exactly one `reopen_card({cardId:'project'})` call, no read or runtime-control call, and final prose. Wait for known settlement.
2. Audit the complete settled suffix byte-for-byte. Require exactly one matching call/result, no other call/result, and `success:true` with the current root card view carrying ID `project` and lifecycle status `changed`. Require exact root history showing ordinary `failed -> changed`, the unchanged captured active-linked projection, stopped or settled-paused runtime, the same verified lifecycle owner/control authority, no running card process, and the matching low-safety `card.reopen` app-log `control_action` row settled `ok`.
3. Any denial, argument difference, additional call/action, partial propagation, failed or unknown result, unmatched call, unexpected state, or uncertain observation blocks the procedure. Do not retry, repeat a submission, undo or compensate a committed reopen, inspect or patch streams, reset, or infer intent from an unknown outcome.
4. Only after every first-turn check succeeds and no safety Stop was needed, send a separate fresh Analyst submission requiring exactly one bodyless `start_project` call and final prose. Never combine reopen and start. Audit the exact settled call/result plus strict runtime, root lifecycle/history, unchanged active-linked projection, lifecycle-owner/control-authority, process, service-health, and first completed post-reopen root-workflow provider-turn evidence to establish ordinary `changed -> running`. Runtime controls produce no required app-log control-action row.
5. Use supported authenticated bodyless `stop_project` at most once and only as a safety Stop backed by positive evidence that a successful start from a blocked first or second submission left runtime active. For the second submission this includes the expected start followed by an extra call. Require the exact settled supported API/transport result, then strictly verify stopped or settled-paused runtime, the root/history exactly observed without a Stop-fabricated transition, the same lifecycle owner/control authority, and no running card process. Expect no app-log control-action row for this runtime control.

The safety Stop does not undo durable effects. Unknown submission identity, start success, active-state relationship, stop outcome, or settlement authorizes no Stop, repeat, compensation, stream inspection or mutation, reset, or further recovery submission. If positive evidence does not exist, issue no Stop and report the exact blocker and supported observations. This procedure adds no retry, compensation, direct stream mutation, record-only mode, recovery API, or temporary configuration.
