# Saivage Operator Runbook

Status: current operator procedures for runtime maintenance.

## Activation ownership and runtime halt

Supervisor startup begins in internal `uninitialized`, strictly validates the project root and initial empty ownership/gate state, and transitions its one status field to public `stopped` only after success. Startup failure leaves it uninitialized, rejects Analyst intervention, and prevents server services from returning or a listener from being published; public runtime-status reads are unavailable in that internal state. Do not confuse this process-local admission with HTTP health readiness at `GET /health/ready`.

After startup, Analyst mutation admission is derived at invocation from that one status: `stopped` and settled `paused` admit; `starting`, `running`, `pausing`, `closing`, and `error` reject. Accepted Run first installs a prepared root owner and reports `starting`; the singular ordinary halt can freeze it before launch. Application shutdown permanently closes Run admission. A lifecycle publication that becomes outcome-unknown reaches the fatal boundary and exits before Supervisor halt, cleanup, or a `closing` status. After positive dead-owner verification and explicit manual lock repair, a genuinely new process may use ordinary Run to execute full-chain stopped recovery. Ordinary Stop, application close, and actor-main containment continue to use the retained halt and `error` behavior. There is no separate readiness state or initialization flag.

Pause is cooperative and run-scoped. Natural root completion can win from running, pausing, or paused; its stopped transition clears the old Pause request and callback before publication, so a later gate wait cannot emit paused for the old run. Project Stop and application close join one halt identity, interruption, owner snapshot, set of processor joins, and runtime-process termination. Application close additionally closes admission permanently. Concurrent callers never conflict or repeat cleanup. Retained historical Planner control-action rows remain readable, while current Planner reorder/notification operations append no control action.

## Prepared conversation compaction

Before startup, provide `compaction.enabled: true`, a positive operator-selected route-independent `input_budget_tokens`, and one exact structured `summarizer_candidate: { provider, account, model }` emitted by the configured Provider Registry. `account: null` means the provider-level implicit account; explicit `"_implicit"` and `"_"` remain distinct exact names. Slash-bearing model IDs such as `org/summary/model` are ordinary data. Omitted, false, incomplete, malformed, or non-emitted candidates fail startup. There is no generated policy, flattened compatibility spelling, fallback summarizer route, or warning-only mode. Configuration load selects the configured global Analyst agent's compiled named route through `agents.<name>.model_route`; that route requires numeric `temperature` and `max_tokens`, and its `max_tokens` must be no greater than `floor(input_budget_tokens * completion_reserve_fraction)`. The diagnostic reports the selected route request, reserve, budget, and fraction. Raise the input budget or reserve fraction, or lower that route's configured `max_tokens`, then perform a fresh ordinary start; adapters supply no fallback and this is configuration correction, not state recovery.

Startup acquires lifecycle exclusion before full selected-config/environment validation, then validates before any `--create-runtime` canonical root-card read, cards-directory creation, or initial publication. Invalid reserve configuration releases the lock through ordinary startup cleanup and creates or changes no generated root-card state.

A valid config may still fail startup binding when a configured tool has no definition in its exact global/card scope, an explicit expanded model is unavailable, or a participant's complete final surface is capability-incompatible. Card admission includes generated `emit_result` even when the configured operational list is empty; Analyst admission excludes it. Correct the current route/provider capabilities or scoped tool list and restart. Credential validity, network availability, and cooldown remain real-invocation concerns, not startup probes. After binding, Planner, executor, and reviewer prepare their exact activation prompt and installed ordered tools before transcript I/O. Analyst prepares the exact rendered prompt, current project context, installed ordered tools, configured output request, and temperature before appending the current submission. Tool and repair continuations retain that prepared value while refreshing canonical context. Raise the actor budget or reduce the prompt/tool surface when this static-capacity check fails; do not expect clamping or an unprepared fallback.

Compaction publishes a new immutable JSONL segment and atomically replaces its cumulative conversation index; it never appends metadata to the source segment. The new segment starts with self-contained compacted genesis carrying ordered summaries, applied policy, source and retained-row commitments, and either `between_rounds` or minimal inherited `{marker_id,input_id,active_segment_kind}` continuation. Genesis is operator context, not a transcript row or cursor. Providers receive synthetic rendered context but never inherited IDs. The predecessor remains historical and is never needed to validate, project, compact, or recover current. Candidate admission remains a deterministic best-effort estimate of one canonicalized complete body (`ceil(UTF-8 bytes / 4)`).

There are two protections for prepared planner, reviewer, executor, and Analyst provider turns. Preventive compaction runs before provider I/O when the prepared threshold requires it, including the initial Analyst call and every accepted or rejected-tool continuation after its canonical result and refreshed projection. If the first ordinary route pass instead returns strict structured `input_context_exhausted` evidence before accepted provider output, the conversation actor consumes its sole last-chance allowance. That rejection ends the first pass before another candidate. Saivage starts at escalated compaction, may use safe hard fallback, and retries one fresh ordinary route pass only after constructing a strictly smaller projection and appending exactly one canonical row. The retry keeps the same logical input/source identity and does not duplicate source rows. For an Analyst continuation, the already accepted tool effect, activity broadcast, and one canonical result are outside this provider seam and are never replayed or duplicated. A second context rejection is terminal: there is no third pass, second compaction, or route-by-compaction retry fan-out. Existing non-context routing/retry behavior is unchanged.

Only exact direct structured code/type/param evidence from an eligible parsed HTTP 400, failed Responses terminal object, or Codex error/failed event authorizes this recovery. Message wording, nested markers, malformed responses, generic token language, and output-token exhaustion do not. An error received after an HTTP stream opens retains the actual opened HTTP status, normally 200, even when typed as input-context exhaustion.

If forced compaction finds no strictly smaller safe projection, it appends nothing, makes no retry, and ends with the existing final failure projection. Only a transport-successful summary containing tool calls, empty text, or the prohibited recoverable-evidence section reports safe malformed-summary construction failure. Summary provider exhaustion remains exact `ProviderTurnFailure`; cancellation, summary-evidence publication/projection, publication-unknown, strict source/projection/hash/invariant, and append failures retain their owning identities. An append or publication-unknown result must not be inspected or retried. Summary provider exchanges have their own `summary:*` session and fresh source-input identity and are never combined with the triggering input.

Summary calls use the fixed configured candidate and ordinary Invocation Service transient recovery. Exact direct `server_is_overloaded` code/type in supported Codex `error` or `response.failed` events is server-transient even after HTTP 200 opened; the recorded response status remains 200. Diagnose exhaustion from the separate `summary:*` provider-exchange evidence rather than attributing those attempts to the planner input. Within one compaction, only one summary provider call is in flight. Each candidate settles merged raw and reduction work before later individual rounds; failure or abort stops later admission. Empty validated projections use local prose and cause no raw provider call, a wholly empty merged selection causes no merge call, and only successful exact raw selections are reused in a call-local cache. A later escalated candidate may sequentially revisit an older expanded merged prefix after normal individual work; this is expected candidate-local fallback, not concurrent fanout.

During last-chance recovery, if summary provider exhaustion occurs after summary evidence publication, Saivage publishes the original triggering planner context-failure attempts exactly once under the planner input and then throws the narrow non-provider `LastChanceSummaryProviderUnavailableError` with the summary failure as cause. The marker has no attempt, route, candidate, phase, or classification fields and exists only to prevent false planner evidence republication or a fabricated planner model issue. Triggering-attempt publication failure or uncertainty supersedes it.

Every Analyst submission is one current-format source round. Its first row is the exact system/activity marker `{event:'activation_open',agent_name:<configured-analyst>,input_id,timestamp}` with no `card_id` and no preceding preamble. Ordinary submissions append `[marker, workspace-context system text, operator user text]` in one batch before canonical reread and preventive compaction; confirmed restart appends `[marker, user confirmation]` and stays model-free. The next marker completes the preceding round; the newest remains open under ordinary bands. When applying the named marker-first incompatible cutover, existing pre-marker, role-identity, or mixed Analyst conversations are unsupported: stop the service, preserve configuration, credentials, operator inputs, source, skills, instructions, and canonical documentation, run the matching current built `saivage reset`, and start that binary. Do not backfill markers or expect migration, inference, or compatibility classification.

Analyst primary and continuation calls use the configured global Analyst agent's compiled model route. Summary calls remain the distinct direct, nonpersisting exception: they use only the one fixed Registry-validated configured candidate, fixed 2000-token no-tools prose requests, separate evidence identities, and no self-compaction or replay. There is no manual compact action, warning, or live `compacting` phase.

## Runtime controls and lifecycle lock

`status`, `pause`, `resume`, `stop`, and `restart_server` classify `.saivage/locks/runtime.lock` as missing, verified live, positively dead, indeterminate, or malformed. Only verified live delegates, using exactly the record's published non-null origin and disabled/bearer auth mode. Null means only `active lifecycle owner; runtime control unavailable`; do not infer init/start/reset phase. Bearer mode requires `SAIVAGE_API_TOKEN`; disabled mode sends no Authorization header. Connection, auth, response, and schema failures have no config/file fallback.

Missing/dead `status` reports stopped and missing/dead `stop` succeeds with `{status:'stopped',contained:false}`; dead also prints manual abandoned-lock repair. Missing/dead `pause` and `resume` fail no-live. Indeterminate/malformed fail closed. Every existing lock still blocks lifecycle acquisition and is never automatically removed or taken over.

`saivage stop` delegates to `POST /api/runtime/stop-project`. Project Stop is a runtime halt, not cancellation: it never calls `cancel_card` and does not itself write a card/root outcome, ToolResult, provider round, or Stop event. It synchronously publishes intervention-rejecting `closing`, freezes all owners, interrupts child and owner callers, and aborts/disposes processors before awaiting joins. A near-terminal result or cancellation may therefore be abandoned; its durable append may already exist or may be absent. Exact continuation fences prevent any post-freeze publication or release. Complete quiescence returns `{status:'stopped',contained:true}`; this `stopped` status admits later Analyst intervention, while no live runtime returns `contained:false`. Failed halt remains intervention-rejecting `error`, rejects repeated Stop with the retained failure, and requires service restart. After successful halt, Run selects the complete linked running chain, stabilizes eligible sessions and publishes stopped leaf-to-root, then activates only project through STOPPED. Descendants remain stopped until ordinary activation by their immediate parent. Unmatched parent `activate_card` receives ordinary interrupted outcome-unknown settlement even if its child is terminal; no child result or old graph node is replayed. During an uninterrupted run, continuation belongs to each live parent waiting on and resuming after its immediate child. Natural root completion occurs only after that ownership fully unwinds; it finishes stopped and never rediscovers or relaunches a durable leaf. The server, Analyst, MCP resources, and lifecycle lock remain live. Pause is cooperative: `pausing` rejects intervention until the one parked frontier settles and the single status becomes `paused`; Resume changes it to intervention-rejecting `running`.

HTTP Pause, Resume, and `stop_project` must omit the request body and JSON `Content-Type`; every supplied payload receives a 400 response before control mutation. Keep bearer Authorization and ordinary headers when applicable. Only `restart_server` carries JSON, exactly `{confirmation:'RESTART SERVER'}`.

## Server restart

`restart_server` is available only when operator authentication is enabled/published bearer. It requires the exact `RESTART SERVER` confirmation. The acknowledgement means accepted asynchronous intent, not that replacement is running. It enters the App terminal coordinator, never project Stop. Disabled-auth catalogs/UI omit it and direct calls fail `restart unavailable: operator authentication disabled`.

## Terminal application cleanup

The App terminal coordinator first attempts every synchronous admission closer, catching each independently, before awaiting cleanup. The runtime closer permanently closes application admission and starts or joins the supervisor halt; its runtime cleanup leaf awaits that exact operation. A concurrent project Stop therefore joins rather than conflicts, and only one interruption, owner freeze, processor-join set, and runtime-root termination occurs. The coordinator then attempts exactly one runtime, one Analyst, and one MCP component leaf plus independent LiveSync, Fastify, subscription/listener, and lifecycle-lock leaves. Other process-owning components close/revoke and start their root termination before any await, then join owned work; there is no later process-registry drain. A timed-out component can continue only under its root while later disjoint-root leaves proceed.

Each leaf has one referenced ten-second bound. Fast completion clears the timer; a hanging leaf keeps the process alive through the bound, records `cleanup_timeout`, and then permits later leaves. Rejection records `cleanup_failed`; closer failure records `closer_failed`. `ShutdownReport` contains only fixed component/code values. Direct callers must inspect it. It is not an aggregate error, containment proof, or process-exit guarantee and does not change signal/restart behavior.

## Running-card cancellation

Analyst and Planner explicit `cancel_card` route running cancellation through runtime cancellation authority, but their preflight differs. Planner validates only immediate-child identity and delegates owner-first through the exact parent-bound port without reading target status or subtree. Analyst rejects root and preflights the complete requested subtree, rejecting the whole request if any member is done or cancelled. After admission, the Supervisor consults its one owner map before target I/O, synchronously claims the exact target and running descendant suffix, preserves/skips noncancellable stored descendants, rejects a noncancellable requested stored target, and publishes deepest-first. Project Stop and App cleanup never initiate cancellation; the singular halt may interrupt and abandon a cancellation that has not completed before freeze. Durable running without an exact owner is an invariant failure, never a direct-write fallback.

Analyst record mutation is also conjunctive admission, not possession of `write`/`edit` plus a matching `record_writes` glob alone. The current URL must resolve to an active linked card, card-scoped agents cannot cross cards, every operation-required tool must be present, and Analyst lifecycle support plus absence of an open workflow draft are required before content checks and mutation.

## Storage and interruption

Runtime state, actor snapshots, recovery diagnostics, provider availability, and lifecycle-control audits are not durable files. Card, authored-record, and conversation version catalogs are durable authority; each index names immutable versions and its exact current head. Missing, malformed, unreadable, schema-invalid, or identity-mismatched indexed heads fail startup unchanged; no index is shortened and no predecessor is promoted. Conversation heads are growing JSONL segments. Startup alone may truncate bytes after the final newline when the retained nonempty complete prefix fully validates against the current index, genesis, session, and conversation semantics. Complete malformed or invalid content remains unchanged. Ordinary runtime/API/tool reads never truncate or repair. Non-current file loss affects only an explicit selected-version request.

Provider availability begins empty after every service restart and should be interpreted only as current-process routing advice. Auth refresh strictly rereads and replaces the complete canonical auth file after network completion. Concurrent refreshes are last-completed-write-wins and can overwrite another credential change; retry authentication/refresh when that accepted race occurs. Stop during response or body handling aborts before auth replacement.
