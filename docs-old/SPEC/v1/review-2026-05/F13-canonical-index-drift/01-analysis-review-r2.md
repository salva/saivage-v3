# F13 — Reviewer critique (r2)

## Analysis review

1. Keep the corrected concurrency framing; the r1-required separation is mostly addressed. The r2 analysis correctly withdraws the same-process HTTP interleaving claim, treats crash interruption / cross-process writers / synchronous event-bus reentrancy separately, and no longer states boot self-heal as established fact. That satisfies the core of r1 analysis items 1, 2, and 5.

2. Tighten the relationship between F12 and F13 before this can be approved. The analysis now says F12 and F13 share the architectural defect but are not the same proximate failure; that is accurate. However, the later plan says F13 subsumes F12, while F12 r2 says F12 is the single workstream that subsumes F13. The analysis should make one ownership model explicit and consistent with the chosen plan, because implementers otherwise get two incompatible stories for the same [src/cards/card-store.ts](../../../src/cards/card-store.ts) rewrite.

3. Add the schema-level consequences of the proposed history semantics. The analysis says history must become mandatory for `create`, `delete`, `archiveAndDeleteSubtree`, and status updates, but it does not call out that the current [src/schemas/validators.ts](../../../src/schemas/validators.ts#L23) / [src/schemas/types.ts](../../../src/schemas/types.ts#L55) `CardHistoryEntry` has no `entry_id`, no `kind`, and a required `snapshot: CardRecord`. The design and plan later rely on `entry_id` and `kind` while also claiming no history schema change. The analysis should surface that as a concrete model decision, not leave it hidden in implementation.

4. Keep the mutation-path inventory, but separate derived recomputation from card mutation more carefully. The r2 table is much better than r1, yet it lists `recomputeBlocks` as a mutation path that writes projections but then the plan makes projections derived/advisory. State plainly whether `recomputeBlocks()` survives as an API, disappears as dead code, or becomes a no-op projection rebuild helper; otherwise the F12 history semantics table and the deletion inventory disagree.

## Design review

1. Resolve Proposal C against the simpler F12 Proposal B.1 before approving it. Proposal C is a defensible middle ground compared with event sourcing, but the F12 r2 design already proposes a simpler by-id-authoritative design that deletes `cards/index.json`, `depends-on.json`, and `blocks.json` entirely instead of keeping them as derived files. F13 r2 needs to explain why keeping derived files for dashboard/CLI/git ergonomics is worth the extra projection writer, stale-cache failure mode, schemas, tests, and boot regeneration, or else align with F12 and delete the files outright.

2. Rework the cost table; the LOC and risk claims are not credible as written. Proposal C adds `projections-writer`, `state`, `commit-marker`, `apply-mutation`, idempotent ledger append, async store opening, crash-injection harnesses, contract/web updates, and call-site async fan-out, while also retaining derived projection files and their schemas. Calling that roughly `+350 new, -550 deleted` needs evidence. The table should count the actual new modules/tests and compare against the F12 plan's delete-the-projection-files design, not only against full event sourcing.

3. Fix the history idempotence model. The design says there is no schema change to `CardHistoryEntry`, but the commit marker recovery checks whether the last history line already has `history_entry.entry_id`. The current history entry type has no such field. Either add an `entry_id` to the history schema and all API/test expectations, or make idempotence depend on a separate durable marker field that can actually be checked without changing the history line. As written, the design cannot replay history exactly once.

4. Complete JSONL crash semantics. The crash table covers by-id rename vs. history append ordering, but it does not define what happens if the process dies during the history append and leaves a partial final line. Existing [src/persistence/jsonl-ledger.ts](../../../src/persistence/jsonl-ledger.ts#L70) quarantines malformed lines on read and advances the cursor; it does not truncate a partial line before the next append. Recovery must specify truncate/quarantine/fatal behaviour before `appendSyncIdempotent`, or a retry can append after a corrupt unterminated line and preserve audit corruption.

5. Fix multi-card mutation atomicity. Proposal C says `archiveAndDeleteSubtree` uses one marker per card and a crash mid-loop yields a "consistent partial subtree archive". That is not generally true: deleting an ancestor before descendants can leave children whose `parent` points at a missing card, causing the boot hierarchy validation to fail. Multi-card mutations need either one group marker, a descendants-first ordering proof that preserves invariants at every prefix, or a clear fatal/incomplete-operation recovery contract.

6. Define projection-write failure semantics. Because Proposal C keeps `cards/index.json`, dependencies, blocks, and tree children as derived files consumed by dashboard/CLI dumps, a failure after marker unlink but before `writeAllDerivedProjections` finishes is observable until the next successful regeneration. The design says boot fixes stale projections, but not whether the current API mutation returns success, throws, schedules repair, or marks projections stale when projection regeneration fails during a live process.

7. Add explicit comment/docstring discipline. r1 required no new docstrings/comments in untouched code, and the user reiterated the rule. The r2 design does not constrain comments across the new modules and rewritten old modules. Add a rule that existing files should only receive the necessary code changes and no explanatory docstrings/comments unless the touched block genuinely needs one; tests and names should carry the contract.

## Plan review

1. The plan conflicts with F12's plan and must not proceed independently. F13 Step 1-8 is a full competing rewrite of the same card-store surface, while [../F12-card-history-empty/03-plan-r2.md](../F12-card-history-empty/03-plan-r2.md) says F13 r2 should be a one-paragraph pointer with no independent steps. This is a hard blocker: choose one umbrella workstream and delete or collapse the other plan.

2. Fix the async construction strategy. Step 4 says `CardStore` becomes `static async open(...)`, then says "the runtime constructor becomes async" and callers await it. JavaScript/TypeScript constructors cannot be async, and the current [src/runtime/runtime.ts](../../../src/runtime/runtime.ts#L100-L116) constructs `new CardStore(...)` inside a synchronous `Runtime` constructor that is itself constructed synchronously by [src/runtime/active-runtime.ts](../../../src/runtime/active-runtime.ts#L76-L100) and [src/server/server.ts](../../../src/server/server.ts#L124). The plan needs a concrete factory chain (`Runtime.open`, `ActiveRuntime.open`, server wiring, and tests) or a synchronous boot primitive; "callers already do" is false.

3. Fix history-entry schema/test steps before implementation. The plan's F12 closure table writes `kind: 'update'` / `kind: 'deleted'` and requires `entry_id` idempotence, but the current `CardHistoryEntry` schema has neither field. If those fields are added, the plan must update [src/schemas/validators.ts](../../../src/schemas/validators.ts#L23), [src/schemas/types.ts](../../../src/schemas/types.ts#L55), contract fixtures, history route tests, analyst tools, and web history rendering. If they are not added, the plan must remove `kind`/`entry_id` from the proposed semantics and define another exact-once mechanism.

4. Update `initProjectTree`/fresh-state detection in the same step. Step 6 says `initProjectTree` writes by-id only and lets first `CardStore.open` generate derived files, but current [src/persistence/file-tree.ts](../../../src/persistence/file-tree.ts#L111-L118) treats a state without `cards/index.json` as invalid new Saivage state. Without changing `isNewSaivageState`, a freshly seeded project that has not yet opened `CardStore` can be discarded as legacy. The plan must include that check, the `cardIndexSchema` import cleanup, and the fate of `cards/tree` / `cards/dependencies` directories.

5. The validation commands are mostly corrected, but there are still path/script gaps. The root Jest runner and absence of `tests/cards/` are handled. However, the plan should avoid unverified claims like "verified by `list_dir`" inside the spec, should use the exact package scripts from [package.json](../../../package.json) for any web command, and should include `npm run lint` / `npm run docs:verify` in the final sweep because the deletion inventory touches exports, docs, and import boundaries. If F12 remains the umbrella, the F13 plan should inherit F12's validation baseline rather than maintain a second one.

6. Make the dead-code deletion inventory match the chosen source-of-truth decision. If Proposal C keeps derived files, then `cardIndexSchema`, `cardDependencyIndexSchema`, `cardBlocksIndexSchema`, and projection writer tests are not dead code. If the F12 design wins and deletes those files at rest, then F13's derived-projection writer, projection schemas, `cards/tree` output, and related tests should not exist. The current inventory mixes both worlds: it deletes `CardStoreHealth` and `card_history_record_appended`, but leaves ambiguity around projection schemas, `isNewSaivageState`, direct file readers, and dashboard/CLI consumers.

7. Remove rollback language that relies on old code reading post-F13 projections. The rollback section says pre-F13 code reads post-F13 files correctly and derived files are regenerated by old code. That is a compatibility claim. Under the project rule, rollback should mean revert before release or reset local `.saivage` state; do not design or justify bidirectional runtime compatibility between the old projection-authoritative store and the new by-id-authoritative store.

8. Expand crash-injection tests to cover the missing crash points. Step 7 should include partial JSONL line during history append, marker file corruption, orphan temp without marker, projection-write throw after marker unlink, multi-card archive crash after each per-card prefix, and reopen while `isNewSaivageState` sees by-id-only seed state. The current matrix covers many important points but misses the ones that stress Proposal C's new assumptions.

## Coordination check (F12)

1. The umbrella decision is contradictory and blocks approval. F12 r2 explicitly states: "This plan is the single approved workstream for F12 and F13" and "F13's plan-r2 should be a one-paragraph pointer back to this file with no independent steps." F13 r2 says the opposite: "F12 lands inside this work" and provides an eight-step independent plan. This must be resolved by the metaplan owner before either issue can be approved.

2. The two chosen designs are not equivalent. F12 Proposal B.1 deletes `cards/index.json`, `depends-on.json`, and `blocks.json` from the on-disk layout and uses per-card locks plus append-then-rename-with-rollback. F13 Proposal C keeps those files as derived projections, uses a project-wide lock around all card mutations, and introduces commit markers. These are incompatible implementation surfaces, not two descriptions of the same plan.

3. The F13 plan's ordering guidance for F19/F20/F23 is improved but still depends on the umbrella conflict. It correctly names F19/F23 ordering and says F20 is independent, but F12 r2 says F19/F20/F23 must rebase onto F12 once Step 4 lands. A single sequence should state whether card-store rewrite lands under F12 or F13, then pin F19/F23 after that rewrite and leave F20 independent except for optional audit assertions.

4. Do not double-implement F12 closure semantics. Both plans rewrite history semantics, stale tests, `card_history_record_appended`, `CardStoreHealth`, and card-store mutation APIs. Only one should own those changes; the other should reference it and preserve issue-specific acceptance notes. As written, two implementers could both edit [src/cards/card-store.ts](../../../src/cards/card-store.ts), [src/persistence/file-tree.ts](../../../src/persistence/file-tree.ts), [src/projections/ledger-projections.ts](../../../src/projections/ledger-projections.ts), and the same server/web tests with different intended end states.
