# F05 — Envelope-vs-toolcalls orthogonality design review r2

1. **The `terminalTool` event contract is not fully located.**

   What is wrong: the design says the invocation event update is complete once `src/schemas/event-catalog.ts` is extended, and claims downstream consumers pick that schema up at compile time. That is not true for the current codebase: there are separate typed event interfaces and Zod validators that also define `invocation_succeeded`. The design also says analyst invocations emit `terminal_tool: null`, but the current event-catalog role enum does not include `analyst`.

   Evidence: the design's `terminalTool` section updates only `exchangeAttemptSchema` and `invocation_succeeded` in `event-catalog.ts` and explicitly says downstream event consumers pick up the schema change because the schema is the contract ([02-design-r2.md#L303-L335](02-design-r2.md#L303-L335), [02-design-r2.md#L778](02-design-r2.md#L778)). In current code, `InvocationSucceededEvent` still has only `session_id`, `role`, `attempt`, and `duration_ms` ([../../../../src/schemas/types.ts#L155](../../../../src/schemas/types.ts#L155)); `invocationSucceededEventSchema` has the same shape ([../../../../src/schemas/validators.ts#L165](../../../../src/schemas/validators.ts#L165)); and `agentRoleSchema` excludes `analyst` ([../../../../src/schemas/event-catalog.ts#L10](../../../../src/schemas/event-catalog.ts#L10)) even though the design says analyst invocations emit `null` ([02-design-r2.md#L323](02-design-r2.md#L323), [02-design-r2.md#L648](02-design-r2.md#L648)).

   Required change: update the design to name every typed event contract location that must change: `src/schemas/event-catalog.ts`, `src/schemas/types.ts`, and `src/schemas/validators.ts` at minimum, plus any generated/exported web event types if they are not derived. Either add `analyst` to the relevant role schema for these events or remove the claim that analyst invocations emit `invocation_succeeded.terminal_tool = null`. The test plan must cover all these schema surfaces, not only `event-catalog.ts`.

2. **The legacy `{ toolCalls: [...] }` migration inventory is incomplete.**

   What is wrong: the design labels its wrapper producer/reader list as complete and says `parseToolCallMessage` is the sole replacement on every reader path, but it misses a live source reader and several test/fixture sites that hard-code the legacy wrapper. That violates the zero-backward-compatibility requirement because an implementer following the inventory can leave old wrapper parsing and dead tests behind.

   Evidence: the design's complete inventory lists producers/readers and tests at [02-design-r2.md#L272-L301](02-design-r2.md#L272-L301), and the Proposal L deletion/migration order repeats only the adapter/analyst/fake-agent/session/runtime/web presenter/store paths ([02-design-r2.md#L771-L775](02-design-r2.md#L771-L775)). Current code also has `AgentToolExecutor.parseToolCallsFromResponse` parsing `parsed.toolCalls` directly ([../../../../src/agents/agent-tool-executor.ts#L52-L56](../../../../src/agents/agent-tool-executor.ts#L52-L56)); the adapter reaches that helper through `parseToolCallsFromResponse` before the current loop ([../../../../src/agents/agent-adapter.ts#L167](../../../../src/agents/agent-adapter.ts#L167), [../../../../src/agents/agent-adapter.ts#L224](../../../../src/agents/agent-adapter.ts#L224)). Hard-coded wrapper fixtures also exist outside the enumerated test list, for example `toolCallEnvelope()` in [../../../../tests/agents/agent-adapter-force-final-answer.test.ts#L51-L52](../../../../tests/agents/agent-adapter-force-final-answer.test.ts#L51-L52), direct `parsed.toolCalls` parsing in [../../../../tests/utils/runtime-project-planner-control-flow.test.ts#L20-L22](../../../../tests/utils/runtime-project-planner-control-flow.test.ts#L20-L22), and a runtime fallback fixture in [../../../../tests/utils/runtime-executor-fallback-evidence.test.ts#L86](../../../../tests/utils/runtime-executor-fallback-evidence.test.ts#L86).

   Required change: expand the migration inventory to include `src/agents/agent-tool-executor.ts` and every matching test/helper/fixture under `tests/` and `web/src/__tests__/`, including the `tests/utils/*` cases. For Proposal L, `parseToolCallsFromResponse` should be deleted with the old flattened string loop; any remaining tests for it should be deleted or rewritten against the new structured result and `parseToolCallMessage` rejection behavior.

3. **Terminal-protocol rejection ownership is inconsistent with the test plan.**

   What is wrong: the design says the strict terminal-protocol validator runs in the adapter with role-specific expectations, but the Proposal L test plan expects provider gateway `complete()` methods to raise role/turn-limit terminal errors. The gateways do not have role, terminal expectation, or max-turn context in the current contract, and the design does not add that context to their signatures. This makes the exclusivity protocol under-specified and the proposed gateway tests non-executable as written.

   Evidence: the strict gate is specified as `validateTerminalProtocol(result, expectations)` running in the adapter loop before side-effects, with expectations `{ role, terminalToolName, mustBeTerminal }` ([02-design-r2.md#L183-L194](02-design-r2.md#L183-L194)). Current gateway signatures take only `candidate`, prompts/messages/session, and `opts` ([../../../../src/agents/llm-provider-gateway.ts#L26-L37](../../../../src/agents/llm-provider-gateway.ts#L26-L37), [../../../../src/agents/llm-openai-chat-gateway.ts#L52-L55](../../../../src/agents/llm-openai-chat-gateway.ts#L52-L55), [../../../../src/agents/llm-openai-codex-gateway.ts#L34-L40](../../../../src/agents/llm-openai-codex-gateway.ts#L34-L40)). The test plan nevertheless says `OpenAIChatGateway.complete` and `OpenAICodexGateway.complete` should raise `terminal_duplicate`, `terminal_mixed_with_actions`, `terminal_wrong_role`, `terminal_prose_only`, and `terminal_missing_at_limit` ([02-design-r2.md#L670-L686](02-design-r2.md#L670-L686)). The adapter pseudocode then casts the terminal result to `kind: 'tools'` and reads `calls[0]` after validation ([02-design-r2.md#L611-L616](02-design-r2.md#L611-L616)), so the validation boundary must be exact before that cast.

   Required change: choose one owner and make the design/test plan match it. If the adapter owns terminal validation, move the role/limit rejection tests to `validateTerminalProtocol` and `AgentAdapter.invokeAgent`, and keep gateway tests focused on provider wire parsing and request shape. If gateways own the rejection, add the terminal expectations to `LlmCompleteOptions`/gateway signatures and explain how they know the role and terminal limit. In either case, explicitly reject `mustBeTerminal === true` with a non-terminal or empty `kind: 'tools'` result before any `calls[0]` access.

4. **Proposal L's capability surface contradicts itself.**

   What is wrong: the shared substrate adds an `envelopeMode` capability axis and says the router uses it, while the recommended Proposal L deletes `envelopeMode`. The invariants matrix says Proposal L is the same as Proposal F with `envelopeMode` merely unused. This leaves the recommended implementation with two incompatible instructions and weakens the claim that every invariant is satisfied by construction.

   Evidence: the shared capability design adds `envelopeMode`, `toolsMode`, and `exclusiveToolChoiceSupport` and states routing skips unsupported `envelopeMode` requests ([02-design-r2.md#L122-L127](02-design-r2.md#L122-L127)). Proposal L's delete list says to remove the `envelopeMode` axis entirely ([02-design-r2.md#L650-L661](02-design-r2.md#L650-L661)), and the recommendation repeats that removal as a benefit ([02-design-r2.md#L751-L753](02-design-r2.md#L751-L753)). But the invariant matrix still says Proposal L is "Same" as Proposal F for capability support and only leaves `envelopeMode` unused ([02-design-r2.md#L727](02-design-r2.md#L727)).

   Required change: make the recommended Proposal L internally consistent. Either keep `envelopeMode` and explain why it remains despite tools-as-only-result, or remove it from the shared substrate and the invariant matrix for Proposal L, stating that Proposal L's only capability axes are `toolsMode` and `exclusiveToolChoiceSupport`. If Proposal F remains as a non-selected alternative, separate its capability surface from the Proposal L implementation order so the implementer does not carry dead envelope capability code forward.
