## Analysis review

1. Keep the two-store-drift root cause, but correct the pause/resume claim. The core diagnosis is right: [src/runtime/active-runtime.ts](../../../../src/runtime/active-runtime.ts#L175-L194) builds status from in-memory `Runtime.status` / `Runtime.paused` while `currentCardId` comes from persisted `RuntimeState`, and [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L99-L116) keeps `_status` as a separate store. However, the analysis says pause/resume succeeds because [src/runtime/control.ts](../../../../src/runtime/control.ts#L39-L79) mirrors both stores in lock-step. That is not what the code does: [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L610-L611) writes `status: 'paused'` / resumed status to disk, then `pauseRuntimeControl()` / `resumeRuntimeControl()` calls `activeRuntime.getStatus()`, whose `status` is still the stale `_status`, and mirrors that back to disk. Treat pause/resume as another example of the same drift, and add explicit tests for `status` plus `paused` consistency.

2. Tighten the exact F23 path instead of overstating it. The evidence supports an illegal `failed -> active` transition, and [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L706-L715) is a plausible caller because it directly calls `setStatus(card.id, 'active')` / `setStatus(card.id, 'running')`. But the analysis currently says the failed executor branch necessarily returns to that line for the same card. That needs proof, because `appendChildUnwindToolResult()` calls `markActivationComplete()` and should move matching activations out of `pending|claimed|running` before the next `getPendingActivationCards()` pass ([src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L167-L188), [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L687-L696)). Either show the stale/duplicate activation that keeps the failed card eligible, or frame line 706 as a likely route rather than a proven one.

3. Separate two bad status-mutation routes in the analysis. `cardStore.setStatus()` enforces `VALID_TRANSITIONS` and throws on `failed -> active` ([src/cards/card-store.ts](../../../../src/cards/card-store.ts#L1088-L1105)), but `applyPlannerResult()` applies planner-supplied `status` via `cardStore.update()` ([src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L766-L782)), which allows `status` edits on terminal cards without calling `validateTransition()` ([src/cards/card-store.ts](../../../../src/cards/card-store.ts#L564-L576)). The analysis should call out both: one path throws and wedges; the other can silently create illegal planner state.

4. Make the liveness contract operational, not only observational. C1/C3 are useful, but they do not yet state the required recovery action after a terminal child: within one tick, `current_card_id` must be cleared or switched to a non-terminal parent planner run, and within 30s either a planner dispatch is scheduled or runtime becomes non-running. `lastTickAt` alone proves the timer is alive; it does not prove an auto-replan was scheduled.

5. Expand the runtime-state writer inventory if the conclusion is "single writer". The analysis lists the obvious `status`/`current_card_id` writes, but the implementation plan later claims ownership of `current_agent_session_id`, `active_card_run`, `paused`, and related fields too. That inventory must include at least [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L487), [src/runtime/runtime.ts](../../../../src/runtime/runtime.ts#L758), and the fallback freeze/resume routes in [src/server/routes/runtime-config-notes.ts](../../../../src/server/routes/runtime-config-notes.ts#L175-L176), or the design must explicitly narrow the state-machine boundary.

## Design review

1. Proposal B is directionally justified, but the boundary is currently too grand for the actual plan. A runtime-owned state coordinator is a clean architectural response to two-store drift. The phrase "single writer for `CardStatus`" is not accurate while operator routes, analyst tools, and `CardStore` remain direct mutation surfaces; even the design later says non-runtime surfaces keep using `cardStore` directly. Reword the design as "single runtime-layer writer" or broaden the file list and tests to cover every mutation surface.

2. Fix the permission/action model before approving the state-machine API. The plan says runtime execution should call `transitionCard(card.id, 'start')` and, if the card is `failed`, insert `failed -> backlog -> active -> running`. But [src/permissions/card-permissions.ts](../../../../src/permissions/card-permissions.ts#L18-L43) denies `card.start` for `failed` cards and allows `card.restart` instead. The state machine must distinguish `start` from `restart`; otherwise it either bypasses the permission matrix it claims to compose with, or it will deny the exact F23 recovery path.

3. Do not bundle F20 until its status model is specified. The design says the state machine can downgrade false executor failure to `needs_corrections`, but `needs_corrections` is a reviewer result, not a `CardStatus`: [src/schemas/types.ts](../../../../src/schemas/types.ts#L1-L16) and [src/schemas/validators.ts](../../../../src/schemas/validators.ts#L8-L10) do not include it in card statuses. If F20 is bundled, the design must include the schema, permission matrix, UI badge, transition, and API impacts of a new status. Otherwise, keep F20 as a later hook and make F19/F23 safe without it.

4. Resolve the tick-loop design before implementation. A 5s cadence is reasonable for the stated C3 deadline, and there is no existing runtime liveness interval beyond startup/resume `safeTick()` and the unrelated stuck-agent supervisor. But the design proposes both a fixed interval and on-demand ticks after every transition while `safeTick()` still exists for several steps. Specify the lock/debounce behavior, the exact owner of the timer, and the step where `safeTick()` stops dispatching so the new timer does not duplicate dispatch or re-enter `dispatchGoal()`.

5. Do not call Step 3 "no behaviour change" if invariants auto-correct. The design says `tick()` asserts and auto-corrects invariants; the plan says Step 3 wires the machine as a no-op observer that only bumps `last_tick_at`. Those cannot both be true. Pick one: either Step 3 is observe-only and cannot mutate anything except `last_tick_at`, or it is the first behavioral repair step and needs the F19/F23 acceptance tests immediately.

6. Make unit-testability consistent. The design says `RuntimeStateMachine` has no `projectRoot` and performs no I/O, but the plan constructs it with `projectRoot`. Prefer injected `readState`, `writeState`, `cardStore`, clock, scheduler, and logger dependencies, with `Runtime` responsible for adapting project-root persistence. That keeps the module testable and avoids another hidden store boundary.

7. State the comment/docstring discipline explicitly. The proposal adds a new central module and touches old runtime code, but the project guideline forbids new docstrings/comments in untouched code. The design should require self-explanatory event names/types/tests, and only allow comments where the new state-machine logic genuinely needs one.
