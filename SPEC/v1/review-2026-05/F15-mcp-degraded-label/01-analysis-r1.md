# F15 — Analysis (round 1)

## Root cause

`buildServerAvailability` in [src/server/availability.ts](../../../src/server/availability.ts#L78-L96) classifies the MCP component by two boolean predicates:

```ts
const hasRunning = statuses.some((s) => s.status === 'running');
const hasConfigured = statuses.length > 0;
mcp = hasRunning
  ? { state: 'available', source: 'mcp-manager', checkedAt }
  : hasConfigured
    ? { state: 'degraded', source: 'mcp-manager', checkedAt }
    : {
        state: 'degraded',
        source: 'mcp-manager',
        checkedAt,
        diagnostic: { code: 'mcp-manager-empty', summary: 'MCP manager is running with no configured servers.' },
      };
```

The "no servers configured" branch (`!hasConfigured`) reuses the `degraded` enum value that is also produced when servers exist but none are running. The `AvailabilityState` enum only offers four values — `available | degraded | unavailable | unknown` ([src/contracts/operator-api.ts:105](../../../src/contracts/operator-api.ts#L105)) — so there is no neutral term for "MCP intentionally not configured".

## Current behavior

- `/api/mcp/status`, `/api/runtime/status`, `/health/ready`, `/api/state`, and the runtime-state WS envelope all surface `serverAvailability.components.mcp.state = "degraded"` with diagnostic code `mcp-manager-empty` whenever the project ships no MCP server entries (the GetRich v2 default). Confirmed by the captured payload [tmp/saivage-v3-checkers-e2e-artifacts-20260523-phase2/t26-mcp-status.json](../../../../../tmp/saivage-v3-checkers-e2e-artifacts-20260523-phase2/t26-mcp-status.json).
- The Vue dashboard treats `degraded` for MCP as a soft notice (not a banner): [web/src/stores/runtime.ts:117-119](../../../web/src/stores/runtime.ts#L117-L119) builds `availabilityDetail` from the diagnostic summary; the only red-banner pathway is `state === 'unavailable'`. So no UI regression today, but the string "MCP manager is degraded or empty." leaks the conflation into operator text.
- Tests pin the current contract: [tests/server/server-availability-contract.test.ts:88-96](../../../tests/server/server-availability-contract.test.ts#L88-L96) asserts `state === 'degraded'` and `diagnostic.code === 'mcp-manager-empty'`; [tests/server/operator-api-contracts.test.ts:30](../../../tests/server/operator-api-contracts.test.ts#L30) hard-codes the same triplet inside the contract fixture.
- Documentation enumerates only the four current values: [docs/operation.md:75](../../../docs/operation.md#L75) and the prose at [docs/operation.md:241](../../../docs/operation.md#L241) explicitly says operators should "distinguish startup failure, unknown/not-attempted state, and an empty/degraded manager" — i.e. the conflation is acknowledged in the spec.

## Impact

- **Monitoring false positives.** Any external alert rule keyed on `components.mcp.state !== 'available'` or `=== 'degraded'` fires forever on the GetRich v2 deployment (no MCP servers). Phase-2 G2/T26 flagged this on 10.0.3.170.
- **Operator confusion.** Dashboard tooltip text "MCP manager is degraded or empty." reads as a fault.
- **API hygiene.** The enum loses meaning: `degraded` should imply something that ought to be healthy is not. An empty configured set is a design choice, not a failure.
- **No data-loss / no runtime correctness impact.** Pure classification fix.

## Scope (transversality)

- One classifier branch: [src/server/availability.ts:85-95](../../../src/server/availability.ts#L85-L95).
- One enum: `AvailabilityStateSchema` in [src/contracts/operator-api.ts:105](../../../src/contracts/operator-api.ts#L105).
- Mirror type in the web client: [web/src/api/types.ts:550](../../../web/src/api/types.ts#L550).
- Three consumers branch on the value:
  - [web/src/stores/runtime.ts:113-120](../../../web/src/stores/runtime.ts#L113-L120) (`availabilityDetail`).
  - The two test files above plus the embedded zod parse in [web/src/api/contracts.ts](../../../web/src/api/contracts.ts) (which only imports `AvailabilityState` for type re-export).
  - Documentation enums in [docs/operation.md:75](../../../docs/operation.md#L75) and [docs/operation.md:241](../../../docs/operation.md#L241).
- No other code paths consume `components.mcp.state` (verified by grep for `components.mcp` and `mcpComponent` across `src/`, `web/src/`, `docs/`, `tests/`). The dashboard binary at `web/dist/` is a build artifact — regenerated by the deploy step.

## Relationship to F22

F22 makes missing/empty model roles fail-fast at `loadEnvironment`, i.e. configuration errors no longer hide behind a degraded runtime classification. The same principle applies here: "no MCP servers configured" is a deliberate config state, not a degraded one. F15's fix codifies the same separation on the MCP side without touching `loadEnvironment` (MCP-empty is valid and must not crash the process; it is simply not "degraded").

## Non-goals

- Do not introduce a separate degraded-vs-empty distinction inside the MCP manager itself — the classifier is the only place that needs to know.
- Do not retain a backward-compatibility alias for `degraded` on the empty path. Per workspace policy (architecture-first, no backward compatibility), the old value disappears.
