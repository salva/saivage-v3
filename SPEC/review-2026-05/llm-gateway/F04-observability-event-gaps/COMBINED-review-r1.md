# F04 Combined Doc r1 Review

## Findings

1. **Blocker: the proposed strictness guard does not close the schema-vs-emitter drift class.**

   The document's closure depends on B4 making `llm_attempt` and `llm_invocation_summary` non-passthrough ([COMBINED-r1.md#L245](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L245), [COMBINED-r1.md#L274](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L274)). In the current code, though, the event catalog helper is passthrough ([event-catalog.ts#L7](saivage-v3/src/schemas/event-catalog.ts#L7)), `buildLoggedEventSchema` always returns `base.extend(payloadShape).passthrough()` ([event-catalog.ts#L87](saivage-v3/src/schemas/event-catalog.ts#L87), [event-catalog.ts#L97](saivage-v3/src/schemas/event-catalog.ts#L97)), and the standalone validators are built from `passthroughBaseEventSchema` ([validators.ts#L132](saivage-v3/src/schemas/validators.ts#L132), [validators.ts#L164-L167](saivage-v3/src/schemas/validators.ts#L164-L167)). The JSONL writer validates through `loggedEventSchema.safeParse` ([event-logger.ts#L107](saivage-v3/src/observability/event-logger.ts#L107)), so simply wrapping the new registry entries in `.strict()` would not be enough unless the builder and mirror validators preserve that unknown-key policy. This is a blocker because F04's root bug is precisely undeclared payload fields surviving validation.

   Required correction: specify a strict event-schema path end to end. For example, add a strict payload helper or registry metadata, make `buildLoggedEventSchema` preserve strictness for these two kinds, add strict standalone validators for them, and assert extra fields are rejected by `loggedEventSchema`, `loggedEventSchemaByKind.llm_attempt`, `loggedEventSchemaByKind.llm_invocation_summary`, and the direct validators.

2. **Blocker: the B2 emitter instructions can double-count failed attempts.**

   Proposal B defines `llm_attempt` as one event per HTTP call to one candidate ([COMBINED-r1.md#L109](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L109)). But the plan says to replace `invocation_failed` with `emitAttempt({ kind: 'failed', ... })` and also replace both `retry_attempted` sites with `emitAttempt({ kind: 'failed', recovery_action: ... })` ([COMBINED-r1.md#L160](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L160), [COMBINED-r1.md#L210](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L210)). The current adapter emits `invocation_failed` and then, for `retry_same_after_delay`, emits `retry_attempted` for the same failed call ([agent-adapter.ts#L410](saivage-v3/src/agents/agent-adapter.ts#L410), [agent-adapter.ts#L418](saivage-v3/src/agents/agent-adapter.ts#L418)). Translating both old events into `llm_attempt` would produce two failed attempt rows for one HTTP failure, contradicting the cardinality tests ([COMBINED-r1.md#L172](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L172)) and the cross-batch invariant ([COMBINED-r1.md#L267](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L267)).

   Required correction: make the failure branch the only place that emits `llm_attempt[outcome.kind='failed']`, after the recovery decision is known, with `recovery_action`, `retry_delay_ms`, and cooldown fields embedded in that outcome. Delete the old `retry_attempted` emit sites rather than replacing them with separate attempt events. The next row represents the retry: higher `attempt` for outer recovery, or the same candidate with incremented `same_candidate_attempt` for same-candidate retry.

## Advisory Notes

- The exhausted-summary ownership should be tightened. The doc says a thrown recovery loop can be summarized from a caller catch boundary such as [active-runtime.ts#L164](saivage-v3/src/runtime/active-runtime.ts#L164) ([COMBINED-r1.md#L161](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L161)), but `invokeWithRecovery` returns failed attempts on exhaustion rather than throwing ([recovery.ts#L84-L154](saivage-v3/src/agents/recovery.ts#L84-L154)), and the adapter currently throws only after inspecting `lastAttempt` ([agent-adapter.ts#L430-L443](saivage-v3/src/agents/agent-adapter.ts#L430-L443)). B2 should state that `AgentAdapter` emits `llm_invocation_summary[verdict='exhausted' | 'cancelled']` before completing/failing the session and rethrowing.

- Zero-backward-compat posture is otherwise aligned: Proposal B deletes the four old event kinds without aliasing or translation ([COMBINED-r1.md#L103](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L103), [COMBINED-r1.md#L262](saivage-v3/SPEC/review-2026-05/llm-gateway/F04-observability-event-gaps/COMBINED-r1.md#L262)).
