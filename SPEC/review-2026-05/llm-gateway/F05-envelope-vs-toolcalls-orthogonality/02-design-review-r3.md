# F05 - Envelope-vs-toolcalls orthogonality design r3 review

1. Codex terminal `tool_choice` is specified with the chat-completions wire shape.

   (a) What is wrong: Proposal L correctly chooses a tools-only terminal-result protocol, but it defines the internal `LlmToolsOptions.tool_choice` shape as the OpenAI chat-completions nested function-choice object and then says the Codex Responses terminal-only request uses the same shape. That is not provider-correct for the current Codex request builder, whose function tools and function-call history use top-level `name` / `arguments` fields. If implemented as written, the terminal-only Codex path will either forward a chat-only `tool_choice` object verbatim or leave the builder without a defined provider-specific translation. This fails the per-provider wire-shape axis and the approved analysis requirement that `openai-codex` remain a first-class participant.

   (b) Verified evidence: The design defines `tool_choice` as `{ type: 'function'; function: { name: string } }` in [02-design-r3.md#L49-L52](02-design-r3.md#L49-L52), sets that exact shape in the options factory in [02-design-r3.md#L107](02-design-r3.md#L107), says Codex uses the same terminal-only shape in [02-design-r3.md#L177](02-design-r3.md#L177), and makes gateway tests assert that same shape for all providers in [02-design-r3.md#L380](02-design-r3.md#L380). The current Codex request surface defines `CodexTool` with top-level `name` in [../../../../src/agents/llm-openai-codex-gateway.ts#L18](../../../../src/agents/llm-openai-codex-gateway.ts#L18), forwards `opts.tool_choice` verbatim in [../../../../src/agents/llm-openai-codex-gateway.ts#L123-L124](../../../../src/agents/llm-openai-codex-gateway.ts#L123-L124), serializes function-call history as top-level `name` and `arguments` in [../../../../src/agents/llm-openai-codex-gateway.ts#L152](../../../../src/agents/llm-openai-codex-gateway.ts#L152), and builds Codex tools with top-level `name: tool.function.name` in [../../../../src/agents/llm-openai-codex-gateway.ts#L181-L184](../../../../src/agents/llm-openai-codex-gateway.ts#L181-L184). The approved analysis explicitly requires Codex Responses to work without `response_format` in [01-analysis-r2.md#L76-L81](01-analysis-r2.md#L76-L81) and calls out A.1 as matching Codex tool-call transport in [01-analysis-r2.md#L184-L189](01-analysis-r2.md#L184-L189).

   (c) Required change: Define the provider-independent terminal choice separately from provider wire JSON, for example as a terminal tool name or a provider-neutral choice type. Then make `buildOpenAIChatRequest` translate it to the chat-completions nested function-choice object and make `buildOpenAICodexRequest` translate it to the Codex Responses function-choice shape used by that backend. The test matrix must assert the distinct chat and Codex request bodies instead of asserting the chat shape for all providers.

2. The forced-terminal missing-result case has contradictory ownership and can leave action calls under-specified on a terminal-only turn.

   (a) What is wrong: The design says `validateTerminalProtocol` is the adapter-owned validator that runs before any side-effecting tool execution, but it separately describes `terminal_missing_at_limit` as an adapter-driven case while the test plan feeds it directly to `validateTerminalProtocol`. As written, the validator's explicit checks cover prose/empty forced terminal turns, duplicate terminal calls, terminal mixed with actions, and wrong-role terminal calls. A forced terminal turn that returns only a normal action tool has no terminal call, no duplicate, no terminal/action mix, and no other-role terminal. Unless a second adapter check is added, the terminal-only turn is not exclusively validated before side effects.

   (b) Verified evidence: The design puts role/turn validation in the adapter-owned validator and says gateways do not see `role`, `terminalToolName`, or `mustBeTerminal` in [02-design-r3.md#L190-L213](02-design-r3.md#L190-L213). It defines `terminal_missing_at_limit` as adapter-driven in [02-design-r3.md#L227](02-design-r3.md#L227), but then places `terminal_missing_at_limit__rejects_when_forced_turn_returns_action_call` in the direct `validateTerminalProtocol` unit tests in [02-design-r3.md#L391-L407](02-design-r3.md#L391-L407). The implementation order also says `validateTerminalProtocol` must run before any `executeToolCall` or `calls[0]` cast in [02-design-r3.md#L473](02-design-r3.md#L473). The approved analysis requires typed failures for contract mismatches in [01-analysis-r2.md#L254](01-analysis-r2.md#L254).

   (c) Required change: Pick one owner and make it unambiguous. The cleaner architecture is for `validateTerminalProtocol` to reject `mustBeTerminal === true` when the expected terminal tool is absent, including the action-only-tool case, before the adapter can execute anything. If the design intentionally wants the adapter loop to own this because it is tied to `MAX_TOOLS_TURNS`, remove it from direct validator tests and add adapter-loop tests that prove action-only output on a forced terminal turn is rejected before side effects. Do not split the check across both places.

3. The legacy `{ toolCalls: [...] }` migration inventory is still not exhaustive.

   (a) What is wrong: Section 6 claims a complete producer/reader and fixture inventory, but current source still has wrapper-reader call sites and deleted-parser test consumers that are not listed. This violates the zero-backward-compatibility and no-dead-code-preservation axes because an implementer following the inventory can delete/rename helpers and parser exports while leaving imports, readers, or tests behind.

   (b) Verified evidence: The design claims completeness in [02-design-r3.md#L270-L305](02-design-r3.md#L270-L305), lists the web helper rewrite in [02-design-r3.md#L300](02-design-r3.md#L300), and lists deleted parser test files in [02-design-r3.md#L444-L452](02-design-r3.md#L444-L452). It does not list [../../../../web/src/utils/tool-presenters/registry.ts#L1](../../../../web/src/utils/tool-presenters/registry.ts#L1), which imports `readToolCallEnvelope`, or [../../../../web/src/utils/tool-presenters/registry.ts#L21](../../../../web/src/utils/tool-presenters/registry.ts#L21), which calls it. It also does not list [../../../../tests/agents/integration.test.ts#L18-L20](../../../../tests/agents/integration.test.ts#L18-L20), [../../../../tests/agents/integration.test.ts#L39-L41](../../../../tests/agents/integration.test.ts#L39-L41), [../../../../tests/agents/integration.test.ts#L151](../../../../tests/agents/integration.test.ts#L151), [../../../../tests/agents/integration.test.ts#L183](../../../../tests/agents/integration.test.ts#L183), or [../../../../tests/agents/integration.test.ts#L214](../../../../tests/agents/integration.test.ts#L214), which import and exercise parser exports the design says will be deleted. The approved analysis requires no legacy wrapper shim and no stale analyst/tool-call shape in [01-analysis-r2.md#L256](01-analysis-r2.md#L256), and matrix/direct-consumer tests in [01-analysis-r2.md#L258](01-analysis-r2.md#L258).

   (c) Required change: Re-run and record the exact inventory command, then update Section 6 and the implementation order to include every direct and indirect caller/import of `readToolCallEnvelope`, `parsePersistedToolCalls`, `parseToolCallsFromResponse`, and the deleted `result-parser` exports. In particular, add `web/src/utils/tool-presenters/registry.ts` to the web migration and either rewrite or delete `tests/agents/integration.test.ts` parser cases in the same pass as the parser deletion.

4. `terminalTool` / `terminal_tool` is schema-located but not source-plumbed, and the invocation event nullability contradicts itself.

   (a) What is wrong: Section 7 correctly identifies the exchange schema and the three invocation event schema/type locations, but it stops at typed surfaces. It does not specify how the terminal tool value is passed into the exchange recorder or emitted on `invocation_succeeded`. It also says the event field is nullable in the table and non-nullable in the later decision/tests. This is not a harmless documentation nit: the implementation order could update schemas and viewers while live exchange attempts and invocation events still never contain the new field.

   (b) Verified evidence: The design adds `terminalTool` to `exchangeAttemptSchema` in [02-design-r3.md#L338](02-design-r3.md#L338), first says `invocation_succeeded.terminal_tool` is nullable in [02-design-r3.md#L348](02-design-r3.md#L348), then decides the event field is non-nullable in [02-design-r3.md#L358-L364](02-design-r3.md#L358-L364), and later tests that the schema rejects `null` in [02-design-r3.md#L433-L434](02-design-r3.md#L433-L434). It asserts happy-path event content in [02-design-r3.md#L416](02-design-r3.md#L416) and lists only typed-surface updates in [02-design-r3.md#L480](02-design-r3.md#L480). Current runtime emissions in [../../../../src/agents/agent-adapter.ts#L399-L400](../../../../src/agents/agent-adapter.ts#L399-L400) do not include `terminal_tool`. Current recorder request inputs in [../../../../src/agents/llm-recording.ts#L47-L55](../../../../src/agents/llm-recording.ts#L47-L55) and [../../../../src/agents/llm-exchange-recorder.ts#L32-L39](../../../../src/agents/llm-exchange-recorder.ts#L32-L39) have no `terminalTool`, and the exchange attempt is constructed without it in [../../../../src/agents/llm-exchange-recorder.ts#L98-L102](../../../../src/agents/llm-exchange-recorder.ts#L98-L102).

   (c) Required change: Make the invocation event contract consistently non-nullable for planner/executor/reviewer, and explicitly add the emission-site work to the design: `AgentAdapter` must emit `terminal_tool` with the validated terminal tool name on success. For exchange records, add `terminalTool` to the recorder input path (`LlmRecorderRequest`, `BeginExchangeInput`, and attempt construction) or define an equally explicit derivation from `LlmToolsOptions`, and require both chat and Codex gateways to pass it when beginning a recorded exchange. Keep the exchange field nullable only because analyst attempts have no terminal tool.
