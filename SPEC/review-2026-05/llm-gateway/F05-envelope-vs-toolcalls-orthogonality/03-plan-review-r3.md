But the current executor result schema includes `result: z.record(z.string(), z.unknown()).optional()` and is not `.strict()` at the top level ([saivage-v3/src/agents/result-parser.ts](saivage-v3/src/agents/result-parser.ts#L137-L142)). The converter's supported-node list omits `ZodUnknown`, so `zodToJsonSchemaMini(ExecutorResultSchema)` must throw under the plan's own rules; if `ZodUnknown` support is added ad hoc, the same test still cannot assert top-level `additionalProperties: false` while moving the executor schema verbatim, because the plan maps non-strict objects to `additionalProperties: true` ([saivage-v3/SPEC/review-2026-05/llm-gateway/F05-envelope-vs-toolcalls-orthogonality/03-plan-r3.md](saivage-v3/SPEC/review-2026-05/llm-gateway/F05-envelope-vs-toolcalls-orthogonality/03-plan-r3.md#L50), [saivage-v3/SPEC/review-2026-05/llm-gateway/F05-envelope-vs-toolcalls-orthogonality/03-plan-r3.md](saivage-v3/SPEC/review-2026-05/llm-gateway/F05-envelope-vs-toolcalls-orthogonality/03-plan-r3.md#L55)). Fix by making B1 explicit about the target contract: either add `ZodUnknown` conversion and change the executor-schema test expectation to match the moved schema, or intentionally tighten `ExecutorResultSchema` to `.strict()` in B1 and document that as a behavior-changing schema normalization rather than a verbatim move.
